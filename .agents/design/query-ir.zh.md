# 查询 IR 设计（草案 v0）

状态：草案，待讨论。参照了 Rill `runtime/metricsview/query.go` 的 `Query` 结构，按 SupaBI 的定位做了取舍。

## 1. 定位

查询 IR 是「对一个数据集提一个问题」的结构化描述。它是入口层（拖拽、AI、嵌入、数据 API）和查询层之间的唯一契约。

三条原则：

1. **IR 里没有 SQL**。只能通过名字引用数据集里已定义的字段，所有字面量走参数绑定。这是安全边界，也是 AI 输出可校验的前提。
2. **IR 自包含**。仪表盘级筛选、联动条件在进入查询层之前就合并进 IR，查询层不知道「仪表盘」的存在。
3. **IR 只描述要什么数据**。不含权限（服务端按身份注入，客户端无法指定）、不含缓存策略（放在请求信封里）、不含可视化配置（属于图表 Spec）。

## 2. 结构总览

```jsonc
{
  "version": 1,
  "dataset": "ds_orders",              // 数据集 ID
  "mode": "aggregate",                 // aggregate | detail

  "dimensions": [
    { "field": "region" },
    { "field": "order_date", "grain": "month", "alias": "month" }
  ],

  "measures": [
    { "field": "revenue", "agg": "sum" },
    {
      "field": "revenue",
      "agg": "sum",
      "alias": "revenue_yoy",
      "compute": { "type": "compare", "timeField": "order_date", "offset": { "n": 1, "unit": "year" }, "output": "ratio" }
    }
  ],

  "filter": {
    "op": "and",
    "args": [
      { "field": "order_date", "op": "time", "value": { "last": { "n": 12, "unit": "month" } } },
      { "field": "channel", "op": "in", "value": ["app", "web"] },
      { "field": "region", "op": "ne", "value": "测试区" }
    ]
  },

  "having": { "field": "revenue", "op": "gt", "value": 10000 },

  "sort": [{ "by": "month" }, { "by": "revenue", "desc": true }],
  "limit": 1000,
  "offset": 0,
  "timezone": "Asia/Shanghai"
}
```

## 3. 字段说明

### 3.1 `version`

IR 的结构版本号。图表 Spec 里会持久化 IR，加载旧 Spec 时按版本逐级迁移。

### 3.2 `dataset`

数据集 ID。一个查询只针对一个数据集，不支持跨数据集。

### 3.3 `mode`

- `aggregate`（默认）：按维度分组、计算度量。
- `detail`：返回明细行，用于明细表和下钻。此时用 `columns` 代替 `dimensions`/`measures`，不允许 `having`、`filterMeasures` 和 `compute`。`columns` 的每一项是字段的内部 ID；要给这一列另起显示名时写成对象：`{ "field": "amount", "label": "实付" }`。

### 3.4 `dimensions`

| 字段 | 必填 | 说明 |
|---|---|---|
| `field` | 是 | 数据集中字段的内部 ID（`key`）。可以是任何未聚合的字段，不限于维度 |
| `grain` | 否 | 时间粒度，仅 `date`/`timestamp` 类型的字段可用：`year` `quarter` `month` `week` `day` `hour` `minute` |
| `alias` | 否 | 输出列名，默认等于 `field`；同一维度以不同粒度出现两次时必填 |
| `label` | 否 | 这一列给人看的名称，默认是字段的名称。`alias` 是查询内部引用这一列用的标识，`label` 只用于显示 |

### 3.5 `measures`

每一项是一个字段，加上怎么聚合它：

```jsonc
{ "field": "amount", "agg": "sum" }                       // 列名默认是字段的内部 ID：amount
{ "field": "amount", "agg": "avg", "alias": "amount_avg" } // 同一字段再出现时，另给 alias
{ "field": "user_id", "agg": "count_distinct" }           // 维度也可以聚合
{ "field": "arpu" }                                       // 指标：不写 agg
```

- `field` 是度量或维度时，`agg` 必填，取值 `sum` `avg` `min` `max` `count` `count_distinct`；`sum`、`avg` 只能用于数值字段，`min`、`max` 不能用于布尔字段。缺 `agg` 报 `agg_required`。
- `field` 是指标时不写 `agg`，指标的聚合在它自己的表达式里；写了报 `metric_agg`。
- `alias` 是这一列在查询里的名字，省略时取字段的内部 ID。同一查询里的列名不能重复，所以同一字段出现两次时，至少一次要给 `alias`。
- 聚合是结构化的，不接受表达式字符串。

数据集不规定聚合方式（[数据集模型](dataset.zh.md) 6.1），聚合只写在这里。

可以带 `label`，给这一列另起显示名：`{ "field": "amount", "label": "GMV" }`。给了 `label` 的列，名称就是它本身，结果里不再带 `agg`（见 4）。名称的规则与数据集字段的名称相同；同一个查询里的名称可以重复，是否重复由制作者自己把握。

指标还可用 `baseLabel` 指定计算前的聚合名称；结果不重复添加聚合名，但仍携带 `compute` / `comparison` 供界面添加占比、同比、环比或累计说明。动态选项使用此属性；`label` 仍表示最终名称并具有更高优先级。

**派生计算 `compute`**（可叠加在以上两种之上）

| `type` | 参数 | 含义 | 版本 |
|---|---|---|---|
| `compare` | `timeField`、`offset: {n, unit}`、`output: value \| delta \| ratio` | 使用指定时间字段及其明细筛选范围，向前偏移后比较同期 | v1 |
| `percent_of_total` | `within: [维度别名]`（可选） | 占比；`within` 为空表示占全部，否则在这些维度内分组求占比 | v1 |
| `cumulative` | `along: 维度输出名` | 沿这个维度依次累计，其余维度相同的分组各自从头累计 | v1 |
| `rank` | `partitionBy`、`desc` | 排名 | 后续 |
| `moving` | `window`、`agg` | 移动平均等 | 后续 |

**同比、环比的执行口径**

```json
{"field":"revenue","agg":"sum","alias":"growth","compute":{"type":"compare","timeField":"order_date","offset":{"n":1,"unit":"month"},"output":"ratio"}}
```

- `timeField` 必须是数据集日期或时间字段；查询必须包含该字段的有限 `time` 范围（开始、结束均存在）。条件只允许经 AND 连接，不允许 OR、NOT、空日期或其他运算符。`offset.n` 为 1～1000 的正整数，单位为日、周、月、季、年；同比为向前 1 年，月环比为向前 1 月。
- 本期、同期分别重新聚合。只偏移用户筛选中所选时间字段的范围，其他筛选、数据源 SQL、参数和权限行过滤保持不变，避免访问超出权限的数据。
- 同期按相同维度分组，所选时间字段的分组键向前偏移后匹配，其他维度使用包含空值的相等匹配；只返回本期存在的分组。无时间维度的 KPI 和总计比较整个区间。
- `value` 是同期值，`delta` 是本期减同期，`ratio` 是差值除以同期。缺失同期时返回空；同期为零时增长率为空，差值仍有效。负基数不取绝对值。同期值和差值保留指标格式，增长率默认百分比。
- 时间范围先按查询时区、当前时刻及周起始日解析为半开区间，再按日历偏移。月末和闰日截到目标月份末日。区间的结束点不在区间内，所以落在零点的结束点放在"最后一个包含日"偏移后的次日：5 月 1 日至 30 日对比 4 月 1 日至 30 日；若直接偏移结束点 5 月 31 日，它会被截到 4 月 30 日，把这一天漏掉。这样每一天对比的就是分桶时与它配对的那一天，整天的区间也不会为空。落在一天之内的结束点按时刻偏移；若它与起点截为同一时刻，同期范围为空。时间戳的日、周偏移保持当地墙上时间，跨夏令时不固定按 24 小时计算。DATE 字段则使用无夏令时的日历解析和偏移，当前日期仍取查询时区，避免午夜跳变或跳日改变日期值。
- 时间粒度须与偏移对齐：周仅支持整周（含 7 的倍数日），月支持月/季/年，季支持整季，年支持整年。因此周粒度同比需明确选择 52 周，不能用日历年偏移。
- 结果筛选、排序、分页在计算后执行；合计、小计重新计算，不能相加增长率。带结果筛选的合计沿用既有省略规则。动态指标保留计算设置。
- 结果列返回 `compute: "compare"` 及 `comparison: {offset, output}`，供界面生成名称；显式 `label` 时省略这些名称元数据。每个比较指标连接独立同期聚合子查询，尚未共享扫描。

**占比的执行口径**

```json
{"field":"buyers","agg":"count_distinct","alias":"buyer_share","compute":{"type":"percent_of_total","within":["region"]}}
```

分子是当前分组的聚合值；分母对相同数据源、参数、明细筛选和权限行过滤后的数据，用相同指标重新聚合，只保留 `within` 中的分组维度。维度必须使用查询的输出名（有 `alias` 时用别名），不可重复，时间维度沿用原来的粒度和时区。`within` 为空或省略表示总计；选择全部维度时，非零分组的占比为 1。

- `having`、排序、Top N（`limit`）和分页在占比计算后执行，不缩小分母。`having` 引用占比列时按 0～1 的原始比例比较，引用原始指标或 `filterMeasures` 时按该指标比较。
- 不把结果行相加求分母：去重计数、平均值和数据集指标都重新聚合，因此这些占比的和未必是 100%。负数不取绝对值、不截断，比例可以小于 0 或大于 1。
- 只接受数值聚合结果；分子或分母为 NULL、分母为 0 时结果为 NULL。除法按浮点数计算，返回原始比例（如 0.25），结果列默认 `format.style: "percent"`，不继承金额单位、前后缀。
- 结果列带 `compute: "percent_of_total"`，供界面在聚合名称后加「占比」；显式设置 `label` 时省略 `agg` 和 `compute`，完整使用该名称。百分比格式仍保留。
- 合计、小计和移除可空动态维度时，`within` 只保留仍参与分组的维度，然后重新计算比例。总计对非零指标为 100%；不累加各行占比。带 `having` 的合计继续遵循既有省略规则。
- 当前每个占比指标在同一 SQL 中连接一个独立聚合子查询；尚未合并相同分母的扫描。

**累计的执行口径**

```json
{"field":"revenue","agg":"sum","alias":"revenue_running","compute":{"type":"cumulative","along":"month"}}
```

沿 `along` 维度从小到大，把各分组的值依次累计；其余维度取值相同的分组各自从头累计。`along` 必须是查询的输出维度名（有 `alias` 时用别名）。一个分组由全部维度确定，所以其余维度相同的分组里，`along` 的每个取值只出现一次，不会有并列。

- 只接受 `sum`、`count`、`min`、`max` 和数值结果。求和、计数把各分组的值相加，最小、最大取到当前分组为止的最小、最大值，都与对「截至当前分组」的明细重新聚合的结果相同。平均值、去重计数不能由各分组的值得出；数据集指标的表达式系统不解析（[数据集模型](dataset.zh.md) 6.2），不知道能不能相加。这三种报 `cumulative_agg`，不返回一个不对的数；`along` 不是查询的维度时报 `invalid_cumulative`。
- 从查询读到的第一个分组开始累计，也就是筛选范围的起点。「近 30 天」的累计从 30 天前的 0 开始，不包括更早的数据。
- 只在查询返回的分组之间累计，没有数据的分组不补。某个地区三月没有订单，就没有这一行；四月的累计值照样包括一、二月。
- `along` 为空的分组排在最后，它的累计值包括其余维度相同的全部分组。某个分组的值为空时不计入，累计值与前一个分组相同；从第一个分组起都为空时，累计值为空。
- `having`、排序、Top N（`limit`）和分页在累计之后执行，不改变累计值：第二页接着第一页累计，被 `having` 筛掉的分组仍计入后面的累计值。`having` 引用累计列时按累计值比较。结果的行序由 `sort` 决定，与累计的方向无关；按销售额排序时，累计值不一定递增。
- 合计、小计和移除可空动态维度时：`along` 仍在，就在剩下的维度里重新累计；`along` 被去掉了，这一列就是普通的聚合，等于这个范围累计到最后的值，总计就是整个范围的和。不把各行的累计值相加。带 `having` 的合计继续遵循既有省略规则。
- 结果列带 `compute: "cumulative"`，供界面在名称后加「累计」；显式设置 `label` 时省略 `agg` 和 `compute`。格式与不累计时相同：求和、最小、最大带字段的格式，计数不带，不像占比那样改成百分比。
- 一个指标只有一种派生计算，所以没有累计的同比，也没有累计占比。`filterMeasures` 也可以带累计，规则相同。

### 3.6 时间范围

时间范围不是查询的独立属性，而是 `filter` 中的一种条件：操作符 `time`，作用于日期或时间字段。`value` 恰选 `last`、`current`、旧式 `start/end`、`bounds` 或 `special` 一种模式，不能混用；`includeCurrent` 仅修饰 `last`，不能与 `special` 同用。

```jsonc
// 相对时间
{ "field": "order_date", "op": "time", "value": { "last": { "n": 30, "unit": "day" }, "includeCurrent": false } }
// 当前周期
{ "field": "order_date", "op": "time", "value": { "current": "month" } }
// 绝对时间，左闭右开
{ "field": "order_date", "op": "time", "value": { "start": "2026-01-01T00:00:00", "end": "2026-04-01T00:00:00" } }
// 独立设置起止端点：从固定日期开始，到下一个月的起点之前
{ "field": "order_date", "op": "time", "value": { "bounds": { "start": { "fixed": "2026-01-01" }, "end": { "relative": { "n": 1, "unit": "month" } } } } }
// 特殊值，不是时间区间
{ "field": "order_date", "op": "time", "value": { "special": "is_null" } }
```

- 相对时间在服务端按查询时区、工作空间的周起始日解析。
- `last.n` 为正整数；不含当前周期时取此前 N 个完整周期，`includeCurrent: true` 时包含当前完整周期。`current` 表示当前完整周期。
- 时间区间始终左闭右开 `[start, end)`。固定时间是查询时区的本地日期／时间，不带 UTC 偏移；时间戳按实际时刻绑定，日期按日历日期绑定。旧式 `start/end` 可省略一端，但不能两端都空。
- `bounds.start/end` 各自省略时表示该侧无限；`bounds: {}` 表示完全不限。非空端点必须恰设 `fixed` 或 `relative`。`relative.n` 是从**当前周期起点**移动的有符号周期数：`0` 为当前起点，`-1` 为前一期起点，`1` 为后一期起点，范围为 ±1,000,000，结果年份须在 1–9999。结束端不自动包含该周期；含今天的近七天用开始 `n: -6, unit: day`、结束 `n: 1, unit: day`。
- 新式 `bounds` 对 `date` 字段只接受日期或时间部分为零的边界，相对单位只能是日及更粗粒度。DATE 先取查询时区的当前日历日期，再按日历计算并绑定日期字符串，不把日期转换成午夜瞬间，因此午夜夏令时跳变或整日跳过不会改变输入日期；`timestamp` 仍按实际时区解析，可使用小时、分钟及带时分秒的固定边界。日、周、月等按当地日历移动，跨夏令时时不按固定 24 小时折算。
- `special` 仅支持 `is_null`、`not_null`，分别生成 `IS NULL`、`IS NOT NULL`，同时适用于日期和时间戳。
- 三个修饰项不单独构成区间，可与上述任一区间模式同用：
  - `includeNull: true` 同时保留日期为空的行，生成 `((区间) OR 字段 IS NULL)`；不能与 `special` 同用。
  - `grain` 为 `day`、`week` 或 `month`，表示区间由整日、整周或整月组成：起点退到所在周期的开头，终点（不含）进到所在周期的结尾。省略时端点不动。`{ "start": "2026-01-15", "end": "2026-03-10", "grain": "month" }` 即 2026 年 1 月至 3 月。
  - `weekStart` 为 ISO 星期（1 周一 … 7 周日），只决定本条件里的周：`current`/`last`/`bounds` 的周单位和 `grain: week` 的对齐。省略时用工作空间的周起始日。它不影响按周分组的维度，后者仍用工作空间设置。
- 只有修饰项、没有区间的值（如 `{ "grain": "month" }`）在查询 IR 中无效；图表和仪表盘把它当作“全部”，不产生条件。
- 必须写明字段：数据集没有默认时间字段。
- 一个查询可以有多个时间条件，各自作用于不同的字段。
- 早期版本有独立的 `timeRange` 属性，为的是同环比能找到主时间范围。它已删除：图表和仪表盘把时间当作普通筛选器（见 [图表与仪表盘](chart-dashboard.zh.md) 2.3），同环比通过 `compute.timeField` 选择基准时间字段及其普通时间筛选。

### 3.7 `filter` 与 `having`

同一种表达式树。`filter` 只能引用数据集中未聚合的字段，编译为 `WHERE`；`having` 引用本次查询 `measures` 或 `filterMeasures` 的别名，编译为 `HAVING`。引用时间类型的度量时，过滤值按查询时区的本地时间解析，与聚合结果按实际时刻比较，与结果里换算后的写法无关。

`filterMeasures` 的元素结构与 `measures` 相同，用于仅参与聚合过滤的指标，不增加输出列。例如图表仅显示地区和销售额，仍可用订单数筛选地区：

```jsonc
"filterMeasures": [{ "field": "order_id", "agg": "count", "alias": "filter_orders" }],
"having": { "field": "filter_orders", "op": "gte", "value": 10 }
```

这些指标使用图表自身的分组维度，其别名不得与输出或其他筛选指标重复，也不能被排序或可视化当成输出列引用。

节点分两种：

```jsonc
// 逻辑节点
{ "op": "and" | "or" | "not", "args": [ ... ] }
// 比较节点
{ "field": "channel", "op": "in", "value": ["app", "web"] }
```

比较操作符：

| 类别 | 操作符 |
|---|---|
| 相等 | `eq` `ne` `in` `not_in` |
| 大小 | `gt` `gte` `lt` `lte` `between` `not_between` |
| 文本 | `contains` `not_contains` `starts_with` `ends_with` `like` `not_like` |
| 空值 | `is_null` `not_null` |
| 空字符串 | `is_empty` `not_empty` |
| 时间 | `time`（见 3.6） |

`value` 的类型必须与字段类型匹配，校验阶段检查。

`between/not_between` 保留双端包含的数组格式 `[min, max]`，也接受对象 `{ "min": 10, "max": 100, "includeMin": false, "includeMax": true }`；省略包含标记时默认为 `true`。原始 IR 必须提供两个非空端点；图表／仪表盘的 content 层允许单端为空，会按包含标记和是否取反转换为 `gt/gte/lt/lte`，两端都空则移除条件。`not_between` 对整个区间取反；所有比较仍遵循 SQL 的 NULL 语义。

`is_empty/not_empty` 仅适用于字符串，分别比较 `= ''` 与 `<> ''`，均不包含 NULL；NULL 使用独立的 `is_null/not_null`。

`contains/not_contains/starts_with/ends_with` 按字面文本匹配，包括输入中的 `%`、`_`。`like/not_like` 对完整字符串使用模式：`%` 匹配任意长度文本，`_` 匹配单字符，反斜杠转义下一字符；例如 JSON 字符串 `"50\\%"` 匹配字面 `50%`，`"a\\\\b"` 匹配字面 `a\b`。模式经方言转义后仍作为绑定参数，不拼接用户文本到 SQL。

### 3.8 `sort` / `limit` / `offset`

- `sort[].by` 引用输出列的别名（维度或度量）。按时间类型的度量排序时按实际时刻排，而不是按结果里换算成查询时区的本地时间排。
- `limit` 缺省时使用服务端默认值；超过服务端上限时截断，并在结果中标记 `truncated`。

### 3.8.1 `totals`

按更粗的分组再算一遍度量：每一项列出它仍然按哪些维度分组（输出列名），空数组是总计。

```jsonc
"dimensions": [{ "field": "region" }, { "field": "order_date", "grain": "month", "alias": "month" }],
"measures": [{ "field": "revenue", "agg": "sum" }, { "field": "user_id", "agg": "count_distinct", "alias": "users" }],
"totals": [["region"], ["month"], []]
```

- 合计由数据库算，不是把各行加起来：每一项编译成一个分组更少的查询，与主查询同样的条件，所以平均值、去重计数的合计也是对的（两个月各 1 人和 2 人，合计可能是 2 人）。
- 合计覆盖查询读到的全部行，不受 `limit`、`offset` 影响；排序只保留它仍然返回的列。
- 只用于有度量的聚合查询；每项只能引用查询的维度，不能重复，也不能保留全部维度（那就是查询本身）；最多 16 项（带小计的透视表每对行、列层级要一项，行、列各 3 个维度时是 15 项）。
- 查询有 `having` 时不计算合计，结果的 `meta.totalsOmitted` 为 `true`：按结果筛选的条件放到更粗的分组上，意思就变了，而用主查询的分组去筛又不是「合计」。
- 候选接口取值时去掉 `totals`。
- 动态维度留空时，查询少了这个维度：各项合计去掉它，变成按全部剩余维度分组（即查询本身）或与另一项重复的合计不再计算（content 层解析动态选择时完成，前端预览用同样的规则）。

### 3.9 `timezone`

IANA 时区名。影响时间粒度截断、相对时间解析和结果中时间的写法：时间类型的列，包括维度、明细列、时间字段的 `min`/`max` 和时间类型的指标，都以这个时区的本地时间返回。缺省取工作空间设置。

### 3.10 `params`

数据集来源 SQL 可以声明参数，由分析师控制取数逻辑。IR 通过 `params` 传值：

```jsonc
"params": { "biz_date": "2026-10-08", "regions": ["华东", "华南"] }
```

数据集侧的声明：

```yaml
来源 SQL: |
  SELECT * FROM orders
  WHERE dt = {{biz_date}}
  [[ AND region IN {{regions}} ]]
参数:
  - name: biz_date
    type: date
    default: { relative: "today-1d" }   # 支持动态默认值
    required: true
  - name: regions
    type: string
    multi: true                          # 展开为 IN (?, ?, ...)
```

规则：

- `{{name}}` 编译为绑定参数占位符，**不做字符串拼接**，因此参数只能是值，不能是表名、列名或 SQL 片段。
- `[[ ... ]]` 是可选片段：其中的参数没有值时，整段丢弃。
- `params` 里省略的参数用数据集的默认值。显式传 `null`（单值参数）或 `[]`（多值参数）表示不传值，不退回默认值，与筛选的「空表示不限」一致：参数所在的 `[[ ]]` 整段丢弃；参数离不开值（必填，或有写在 `[[ ]]` 外面的占位符）时报 `missing_param`。
- 参数值的来源：图表上固定（`query.params`，或图表上没有控件的参数筛选器）、查看者通过图表的参数筛选器选择（[图表与仪表盘](chart-dashboard.zh.md) 2.11）、或系统变量（如 `{{user.dept}}`，取自当前用户属性，客户端不可覆盖）。仪表盘全局筛选器关联参数尚未实现，系统变量也是。
- IR 中传了数据集未声明的参数，或类型不匹配，校验阶段拒绝。
- 参数值参与缓存键。

### 3.11 字段引用

IR 中所有 `field` 引用的是数据集字段的**内部 ID**（`key`），不是来源 SQL 的列名，也不是名称。三者的关系：

| | 例 | 谁能改 | 改了影响什么 |
|---|---|---|---|
| SQL 列名 | `region_name` | 分析师随时改 | 只需把字段指向新列，图表无感 |
| 内部 ID | `region` | 创建后不可改 | 图表、IR、AI 都引用它 |
| 名称 | 地区 | 随时改 | 只影响展示和表达式的书写 |

`dimensions[].field`、`measures[].field`、`filter`、明细模式的 `columns` 引用的都是字段的内部 ID。各处能用哪些字段：

| 位置 | 可用的字段 |
|---|---|
| `dimensions[].field`、`filter`、`columns` | 未聚合的字段，维度和度量都可以 |
| `measures[].field` | 任何字段：维度和度量带 `agg`，指标不带 |

内部 ID 自动生成，界面上不显示，使用者在界面上始终按名称选择字段；IR 是界面和接口之间的格式，由程序读写。直接编写 IR 的调用方从数据集定义中查到内部 ID。完整定义见 [数据集模型](dataset.zh.md) 5.2。

## 4. 请求信封与结果

IR 之外的执行选项放在信封里，不进入图表 Spec：

```jsonc
{
  "query": { /* IR */ },
  "options": {
    "cache": "default",      // default | refresh | bypass，见 6.6
    "maxAge": 60,            // 可选，秒，只与 default 一起用，见 6.6
    "diagnostics": true,     // 可选，只向数据开发和管理员返回本次查询诊断
    "timeoutMs": 30000,
    "async": false           // true 时返回任务 ID，由 worker 执行
  }
}
```

结果：

```jsonc
{
  "columns": [
    { "name": "month",   "type": "timestamp", "role": "dimension", "label": "下单月份", "grain": "month" },
    { "name": "revenue", "type": "decimal",   "role": "measure",   "label": "销售额", "format": { "decimals": 2, "prefix": "¥" } }
  ],
  "rows": [["2026-01-01T00:00:00", "128000.50"]],
  // 查询要了 totals 时才有，顺序与 totals 相同；by 是这一项保留的维度，列为这些维度加全部度量
  "totals": [{ "by": [], "columns": [{ "name": "revenue", "type": "decimal", "role": "measure", "agg": "sum" }], "rows": [["128000.50"]] }],
  "meta": { "cached": true, "cachedAt": "2026-10-17T09:00:12+08:00", "truncated": false, "durationMs": 42 }
}
```

`meta.durationMs` 包括合计查询的耗时。

`rows` 里的值是 `null`、布尔值、数字或文本。小数是文本，这样不丢位数。超出 ±(2^53 − 1) 的整数也是文本：浏览器读 JSON 时会把它取整，19 位的 ID 末几位会变，回传时什么也匹配不上。列的 `type` 仍是 `integer`。筛选条件里的整数值可以是数字，也可以是这样的文本，所以从结果里选出的值可以原样传回。转换发生在整理结果的地方（`query.Shape`）；缓存和导出里保留的仍是整数。

`label` 和 `format` 来自数据集定义，前端渲染时直接可用。`format` 的结构见 [数据集模型](dataset.zh.md) 5.5：维度、指标和按 `sum`、`avg`、`min`、`max` 聚合的度量列带字段的格式；按 `count`、`count_distinct` 聚合的列不带，计数与原字段的单位无关。由聚合得到的列另带 `agg`（如 `"agg": "avg"`）；指标的列和查询里给了 `label` 的列没有。它的 `label` 仍是字段的名称，由前端按界面语言把聚合方式写进名称，例如「平均(订单金额)」。

按粒度分组的维度列带 `grain`，合计里的维度列也带，前端据此决定日期写到哪一级（[数据集模型](dataset.zh.md) 5.5）。没有粒度的列不带，包括用表达式截断的日期。

仪表盘组件的数据接口可额外返回 `meta.overriddenFilters: string[]`，列出本次被全局筛选接管的图表筛选器 ID，供界面置灰。它由仪表盘层按已解析的动态指标和实际绑定生成，不属于查询 IR，也不改变查询编译器的通用结果。

### 4.1 查询诊断

`POST /query` 的 `options.diagnostics: true`，或 `POST /charts/{id}/data` 的 `diagnostics: true`，使成功结果额外包含 `diagnostics`。仅数据开发和管理员可请求；查看者请求时返回 403。普通取数不返回此字段，诊断信息不进入共享缓存，也不持久化。

- `requestId` 唯一标识本次请求，`requestedAt` 记录发起查询的时间。即使命中缓存，也生成新的请求标识。
- `statements` 按主查询、所请求的合计/小计顺序排列。每项的 `kind` 为 `main`、`total` 或 `subtotal`；小计的 `by` 保留输出维度名。因 `having` 而省略的合计不生成语句条目，沿用 `meta.totalsOmitted` 提示。
- `sql` 与 `args` 直接取自产生本次结果的编译对象，不另行编译。SQL 保留对应方言的占位符，参数以 JSON 数组按占位符顺序返回，包含来源 SQL 参数、筛选值和已经解析的相对日期。这里展示的是传给驱动的 SQL；驱动内部的参数转义和协议转换不在此展开。
- 每条语句分别返回 `durationMs`、`cached`、`shared`、`fetchedAt`、`rowCount`、`truncated`。耗时包含数据源排队；命中缓存时为原查询耗时，不是读取缓存的耗时；`shared` 表示共用了进行中的相同查询。`rowCount` 为返回行数，不含用于判断截断的额外一行。总耗时是各语句耗时之和，混合命中时仍逐项展示。
- 图表编辑器将诊断与同一响应的结果一起更新，底部保留独立的图表定义页签。配置变化而未重跑时标记过期，重跑及取消时标记仍为上次成功结果；新查询失败则清除旧结果与诊断。取消和晚到的响应不会覆盖当前结果。

## 5. 处理流程

```
IR
 → 结构校验      JSON Schema，版本迁移
 → 语义校验      字段是否存在、类型是否匹配、grain 是否用在时间维度上
 → 权限注入      列权限：引用了不可见字段则拒绝；行权限：追加过滤条件
 → 逻辑计划      展开 compute（如 compare 展开为主查询 + 偏移查询）
 → 方言编译      生成 SQL + 绑定参数
 → 缓存 / 执行
 → 结果整形      类型归一化、附加 label 与 format
```

基础形态编译结果：

```sql
SELECT DATE_TRUNC('month', t.created_at) AS month,
       t.region_name                     AS region,
       SUM(t.amount)                     AS revenue
FROM ( /* 数据集来源 SQL */ ) t
WHERE /* 行权限 */ AND /* filter */
GROUP BY 1, 2
HAVING SUM(t.amount) > ?
ORDER BY month, revenue DESC
LIMIT 1000
```

`compare` 的编译方式：主时间范围和偏移时间范围各生成一个聚合子查询，按非时间维度（以及平移后的时间维度）关联。

`cumulative` 的编译方式：在分组查询外面用窗口函数，按其余维度分区（没有其余维度时不分区），沿 `along` 排序（空值在后，写法由方言给出），窗口从分区的第一行到当前行。求和、计数的累计都是对各分组的值求和，最小、最大用 `MIN`、`MAX`。窗口函数不能写在 `WHERE` 里，所以有累计时外面再包一层，`having` 写在这一层：

```sql
SELECT month, region, revenue_running
FROM (
  SELECT g.month, g.region,
         SUM(g.revenue) OVER (PARTITION BY g.region ORDER BY g.month
                              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS revenue_running
  FROM ( /* 上面的分组查询，不带 HAVING */ ) g
) c
WHERE revenue_running > ?
ORDER BY month, region
LIMIT 1000
```

动态维度／指标的 `selections`、级联筛选的依赖和当前选择均在 content 层先解析。动态选择只能引用作者保存的候选 ID，解析后替换维度／指标定义并保持输出 alias；级联候选查询应用已配置祖先或反向匹配条件，然后使用同一 IR 编译。查询层不接收动态选择器或仪表盘级联配置，也不按跨数据集同名字段猜测关联。

候选涉及 `HAVING`（包括固定或全局结果筛选）时，服务端内部投影先按图表原分组求出合格分组，再以 NULL 安全相等关联原始行、取不同候选值；保留原日期粒度与明细条件。候选搜索只作用于外层，原图表排序/分页不会限制合格分组。内部投影不接受客户端 JSON，也不写入 Spec；缓存按编译后的 SQL 和参数取键（见 6.3），因此自然区分这种投影，不对公开 IR JSON 取键。

## 6. 缓存与并发

状态：已实现，代码在 `internal/qcache`（缓存与合并）、`internal/datasource/limit.go`（并发限制）、`internal/api/cache.go`（接入）。

### 6.1 目标与范围

- 同一个仪表盘被很多人打开、或被反复刷新时，相同的查询不重复压到数据源上。
- 一个数据源同时执行的语句有上限，超出的排队，而不是一起压过去。
- 不改变权限语义：命中缓存时看到的数据，与不命中时完全相同。

| | 缓存 | 并发限制 |
|---|---|---|
| 图表、仪表盘取数（含合计），筛选候选，查询接口，图表、仪表盘、数据集的草稿预览，权限预览 | 是 | 是 |
| 数据探索、`LIMIT 0` 试执行、库表结构、连接测试 | 否：要的是此刻的结果，或者本身不是取数 | 是 |

一句话：经过查询编译器的语句走缓存；对数据源执行的所有语句都受并发限制。

### 6.2 缓存在哪一层

缓存的是**一条编译好的语句在数据库上的执行结果**：在权限注入、方言编译之后，在结果整形之前。

- 键来自编译后的 SQL 和绑定参数（6.3），不来自 IR、请求体或用户。
- 值是数据库返回的原始结果：列的实际类型和行。`label`、`format`、`agg`、`compute` 等列信息每次按当前的数据集定义重新附加，所以改字段名称、改显示格式不需要让缓存失效，也不会读到旧名称。
- 合计的每一项是单独一条语句，各自缓存（见 3.8.1）。同环比、占比和累计编译进同一条 SQL，随它缓存。

### 6.3 缓存键

对下面各项按类型编码后取 SHA-256：

| 组成 | 作用 |
|---|---|
| 键格式版本 | 改变缓存内容的格式时整体作废 |
| 数据源 ID | 同样的 SQL 在不同数据源上不是同一份数据；数据源属于工作空间，所以也隔开了工作空间 |
| 数据源版本（设置的修改时间，与连接池重开用的相同） | 改连接设置、改数据时区之后，旧结果全部作废 |
| 编译后的 SQL | 已经包含数据集的来源 SQL、筛选、行级权限条件、时区换算、`LIMIT n+1` |
| 绑定参数，带类型 | 筛选值、数据集参数、由用户属性解析出的值、相对时间解析出的端点；带类型是为了区分 `1` 和 `"1"` |

不进入键的：用户、角色、图表、仪表盘。因此数据范围相同的人共享缓存；行级规则不同的人 SQL 或参数不同，不会共享。

- **相对时间**在编译时解析成具体端点，「近 7 天」过了零点自然换成新的键，不会把昨天的范围当成今天的。
- **来源 SQL 里不确定的部分**（`NOW()`、`CURRENT_DATE`、随机数）不在键里能看出来，只能靠有效期兜底。

### 6.4 与数据权限的关系

- **缓存在权限注入之后**，所以权限的任何变化（改规则、改用户属性、加入或移出用户组、改角色）都会改变 SQL 或参数，下一次查询立即生效，不需要清缓存。
- 列级权限在编译阶段拒绝引用不可见字段的查询，被拒绝的查询走不到缓存。
- 不允许在 IR、请求或接口响应的层面另加缓存：那样会绕过上面两条。实现上缓存只在 `query` 和数据源之间这一处。
- 命中只说明「数据范围相同的人在有效期内问过同一个问题」，不带出别人能看到而自己看不到的数据。

### 6.5 有效期

- 默认值在「系统管理 → 通用设置」里设置，默认 10 分钟，可选 1 分钟到 24 小时；存在元数据库，各实例读到同一个值，每次查询时读，改了只影响之后写入缓存的结果（[启动配置](configuration.zh.md) 第 10 节）。整个实例不缓存用启动配置 `--query-cache=off`（6.8）。
- 数据源可以覆盖：「结果缓存」选「跟随默认」「不缓存」或 1 分钟到 24 小时之间的值。业务库上要看实时数据的数据源选「不缓存」。存为数据源的一列，修改它与修改其他设置一样会让该数据源已有的缓存作废。
- 从数据库返回结果时开始计时，到期即失效；命中不延长有效期。
- 数据集、图表级别的有效期暂不做（见 [暂缓事项](../backlog.zh.md)）。

### 6.6 刷新

请求信封里的 `options.cache`（第 4 节）：

| 取值 | 读缓存 | 写缓存 | 合并相同查询（6.7） |
|---|---|---|---|
| `default` | 是 | 是 | 是 |
| `refresh` | 否 | 是，替换旧的 | 是 |
| `bypass` | 否 | 否 | 否 |

- 图表、仪表盘、数据集预览的取数接口不暴露完整信封，请求体加 `refresh: true`，对应 `refresh`。`bypass` 只在查询接口上提供，用于排查问题。
- 编辑器里作者手动点的「运行」（图表编辑器）和「刷新」（数据集预览）用 `refresh`；改了字段后自动重跑的用 `default`，定义变了键自然不同。
- 仪表盘查看态的「刷新」按钮刷新全部图表；图表菜单里已有的「刷新图表」只刷新这一张。手动查询模式下点「查询」用的是 `default`：它是应用条件，不是要求重新取数。
- 能看这个仪表盘的人都能刷新，包括普通用户，否则他们拿不到新数据。刷新造成的压力由合并和并发限制兜住。
- **最长可接受时效**（用于仪表盘的定时刷新，见 [图表与仪表盘](chart-dashboard.zh.md) 3.9）：`default` 可以附带 `maxAge`（秒，1–86400）。缓存中的结果，其语句开始执行的时间（取得时间减去执行耗时，含排队）距今不足 `maxAge` 才使用；更旧的按 `refresh` 处理，查数据库（仍合并相同查询）并替换缓存。从开始执行算而不从返回算：一条要跑 10 秒的语句，一个间隔之后再问时按返回时间算还不到间隔，按开始时间算正好一个间隔，不会被误当成新结果。查询接口放在 `options.maxAge`，只能与 `cache: default` 或不写 `cache` 一起用；仪表盘的组件取数和筛选候选接口（已保存的和草稿的）在请求体加 `maxAge`，不能同时带 `refresh: true`。不符合时返回 400 `invalid_request`。`maxAge` 比有效期（6.5）长时没有额外作用，过了有效期的结果本来就不在缓存里。日志里带 `maxAge` 的语句多记一项 `maxAgeS`。
- 结果的 `meta` 加两项：`cached` 表示是否来自缓存，`cachedAt` 是这份结果从数据库返回的时间（ISO 8601，带时区偏移）。带合计的结果，全部来自缓存才算 `cached`，`cachedAt` 取其中最早的。命中时 `durationMs` 是当初执行的耗时。图表上显示「数据更新于 N 分钟前」，悬停可见具体时间。

### 6.7 合并相同的查询

- 同一个实例里，键相同的查询正在执行时，后到的请求等它的结果，不再执行一次。九点钟几十人打开同一个仪表盘，每张图只查一次。
- 合并只在实例内，用 Redis 时也一样：跨实例合并要分布式锁，等锁的实例还得轮询结果，第一版不做。所以 N 个实例时，同一个查询最多同时执行 N 次，之后都从 Redis 读。
- 合并的请求只占一个并发名额。
- 共享的执行用它自己的上下文：一个等待者离开（关掉页面）不会取消它，所有等待者都离开、或超时，才取消语句。
- 页面会取消不再需要的请求，这时的离开和关掉页面一样算。这包括：仪表盘图表的取数，在它的条件变了或它被卸载时；筛选的候选值，在新的搜索取代它或控件被卸载时；数据源的表清单，在换成显示另一个数据源时。否则每改一次筛选，之前的查询都会跑到结束，占着名额和排队位置，仍然需要的查询只能排在它们后面。代价是：从 A 切到 B 再切回 A 时，如果 A 在结果保存下来之前被取消了，就要重新执行。
- 客户端已经离开的请求不算错误：回答 499 `canceled`（没人会读到），日志里只有每条语句都会记的那一行（见下文）。需要审计的查询如果已经到了数据源，照样记录，记作失败，错误为 `canceled`。事件的记录和对象名称的查询都不随请求结束而中止，和所有事件的记录一样（[权限设计](access-control.zh.md) 7.4）。
- 出错的结果不缓存：当时在等的请求都收到这个错误，下一个请求重新执行。
- 数据源设为「不缓存」或 `--query-cache=off` 时仍然合并：同时在跑的相同查询，结果本来就相同。

### 6.8 存储

缓存的存储可以配置，`--query-cache`（`SUPABI_QUERY_CACHE`）：

| 取值 | 存在哪 | 适合 |
|---|---|---|
| `memory`（默认） | 每个实例的进程内 LRU | 单实例部署；不想多维护一个组件 |
| `redis` | 外部 Redis，各实例共用 | 多实例部署 |
| `off` | 不缓存 | 排查问题，或数据源都要实时数据 |

两种存储的语义相同：同样的键、有效期、刷新和合并规则，上层只依赖一个接口（读、写、带有效期）。一个部署里的所有实例应使用同一种存储。不做本地加 Redis 的两级缓存：那样在一个实例上刷新后，其他实例本地的旧结果仍会被读到，刷新就不可靠了。

估算的单个结果超过 8 MB 时不缓存（默认最多 10000 行，列多时可能很大），两种存储相同。

**`memory`**

- 按估算的字节数限总量：`--query-cache-size`，默认 256 MB，超出时淘汰最久未用的。
- 每个实例各自缓存：多实例部署时命中率按实例数下降；在一个实例上刷新，只替换这个实例上的结果，其他实例上的旧结果到期才失效。重启后缓存清空。

**`redis`**

- 连接用 `--redis-url`（`SUPABI_REDIS_URL`），如 `rediss://:密码@host:6379/0`；与元数据库一样，建议通过环境变量传，密码不出现在进程列表里。支持 `rediss://`（TLS）。
- 键是 `supabi:qc:` 加 6.3 的摘要，前缀可用 `--redis-key-prefix` 改，便于和其他应用共用一个 Redis。每个键用 `SET ... PX` 带上有效期，到期由 Redis 删除。
- 总量不由 SupaBI 控制，`--query-cache-size` 对它不起作用：部署时给 Redis 设 `maxmemory`，淘汰策略用 `volatile-lru` 或 `allkeys-lru`。部署文档给出推荐配置。
- 值用带类型的二进制编码（区分整数和浮点数：JSON 会把超过 2^53 的整数变成浮点），较大的结果压缩后再存。
- **Redis 不可用时不影响查询**：读写缓存有短超时（如 200 毫秒），失败或超时就当作未命中，直接查数据源并记警告日志，查询不报错。`/readyz` 不检查 Redis。
- Redis 里存的是查询结果，即业务数据，明文存放。Redis 应只对 SupaBI 开放并设密码；它和元数据库一样属于需要保护的组件。
- 刷新替换的是共用的那份，所有实例随即读到新结果。
- 本地开发的 `make dev-up` 带一个 Redis；缓存的测试对两种存储各跑一遍同一套用例。

### 6.9 并发限制

- **每个数据源、每个实例**同时执行的语句不超过 N 条，默认 8；数据源设置里可改为 1–64。默认值小于驱动的连接池上限（10），使排队发生在我们这一层，能计时、能拒绝，而不是在连接池里无声地等。
- 限制包在数据源连接外面，对这个数据源执行的所有语句都受限（6.1 的表），即连接的 `Query`、`Describe`、`Tables`；测试连接的 `Ping` 不受限，否则数据源忙时测试会误报。命中缓存和合并等待的请求不占名额。修改并发上限会重开这个数据源的连接池。
- 先到先得。排队的时间计入查询超时（默认 60 秒，[启动配置](configuration.zh.md) 10.7）。
- 每个数据源最多排队 100 条；再多时立即返回 `datasource_busy`（503），界面提示数据源繁忙、稍后重试。在排队中超时报 `queue_timeout`（504），执行中超时报 `timeout`（504），便于判断是数据源慢还是排队长。
- 一张图的合计逐项执行，同一时刻只占一个名额（与现在相同）。
- 多实例时，一个数据源实际的并发上限是实例数 × N，用 Redis 做缓存时也一样：并发限制不经过 Redis，第一版不做跨实例的共享限额。
- 不区分用户：一个人打开一个图表很多的仪表盘，可以占满队列。按用户的公平性，以及以后定时任务与交互查询的优先级，暂不做。

### 6.10 观测

- 每条语句记一行日志：数据源、键的前 12 位、是否命中、是否合并、排队时间、执行时间、行数。读写 Redis 失败时另记警告，同一种错误限频记录，避免 Redis 宕机时刷满日志。审计在执行语句的地方（与查询诊断同一时刻）记下 SQL、参数、耗时、行数和是否命中缓存，一次取数请求的全部语句合成一条查询事件，见 [权限设计](access-control.zh.md) 7.3。
- 不在第一版做指标导出和缓存管理界面。

## 8. 已决定

1. **聚合方式写在查询里**，限六种基础聚合，不接受表达式。早先度量可以省略聚合、按数据集的默认聚合计算，另有 `adhoc` 写法为这一次查询指定聚合；数据集不再有默认聚合后，两种写法合并为 `{ field, agg }`，旧写法不再接受。
2. **数据集 SQL 支持参数**，见 3.10。
3. **字段引用用内部 ID（`key`）**，创建后不可改，与 SQL 列名、名称解耦，见 3.11。

实现中确定的细节：

- **未指定排序时按维度顺序升序**，保证同一查询每次返回的行序一致。
- **判断结果是否被截断**：SQL 实际多取一行，超出则截断并标记 `truncated`。
- **度量列的类型以数据库实际返回为准**，维度列的类型以数据集声明为准。
- **过滤值的类型在编译阶段校验**，不合法的值不会到达数据库。时间戳的过滤值按查询时区的本地时间解析。
- **文本匹配均使用绑定参数**。字面匹配与 `like/not_like` 通配模式有不同语义，方言负责转换转义字符，见 3.7。
- **数据源连接默认只读**（会话级只读事务），作为只读账号之外的第二道防线。

已知限制：

- 日期筛选尚不支持分区最近有数日期、交易日／工作日、自定义周历及在筛选控件中按多种日期粒度选取；现有周起始日设置继续适用。查询维度的 `grain` 及动态维度候选的日期粒度切换已支持，与上述筛选控件能力不同。
- 来源 SQL 中的 `[[` 和 `]]` 被解释为可选片段，与 PostgreSQL 的多维数组字面量（如 `ARRAY[[1,2],[3,4]]`）冲突。
- 来源 SQL 里哪些是字符串、带引号的名称和注释，是按标准 SQL 的规则判断的，不是按数据源自己的规则（[数据集模型](dataset.zh.md) 第 4 节说两者应当一致）。数据库读法不同的地方，`{{name}}`、`[[ ]]` 和 `;` 可能被错当成文字或 SQL，这时 SQL 会被拒绝或运行失败；值仍然是绑定的，不会返回错误的结果。这些情况是：MySQL、StarRocks、Doris 和 ClickHouse 上用反斜杠转义的引号（`'it\'s'`），改成双写引号即可；MySQL 上的 `#` 注释，改用 `--` 即可；PostgreSQL 上的 `$$ … $$` 字符串。
