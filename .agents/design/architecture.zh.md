# 架构总览

状态：已讨论确认的部分。细节见 [查询 IR](query-ir.zh.md)、[数据集模型](dataset.zh.md)、[图表与仪表盘 Spec](chart-dashboard.zh.md)、[权限与工作空间模型](access-control.zh.md)、[启动配置](configuration.zh.md)；暂缓的事项见 [暂缓事项](../backlog.zh.md)。

## 1. 产品定位

- 开源产品，全部功能以 Apache 2.0 协议开源，不区分开源版和企业版；支持私有化部署。
- 面向两类人：数据开发（分析师、工程师和报表制作者，用 SQL 建数据集，拖拽做图表和仪表盘）和业务用户（看仪表盘，以后向 AI 提问）。对应的角色见 [权限与工作空间模型](access-control.zh.md) 4.1。
- AI、拖拽、嵌入、数据 API 是同一套内核之上的不同入口，不各自实现查询逻辑。

## 2. 逻辑分层

```
入口层     拖拽编辑器 │ AI 助手 │ 嵌入 SDK │ 数据 API
              └─────────────┬─────────────┘
规格层     仪表盘 Spec │ 图表 Spec │ 筛选与联动        声明式 JSON，存元数据库
                            │
查询层     查询 IR → 权限注入 → 方言编译 → 执行与缓存   系统内核
                            │
数据集层   来源(SQL 或选表) │ 参数 │ 字段(维度、度量)   分析师维护
                            │
数据源层   连接管理 │ 驱动与方言

平台基础   认证 │ 资源权限 │ 工作空间 │ 审计          横切所有层，通过接口接入
```

依赖方向只能自上而下。

## 3. 核心约束

1. **所有入口产出同一种声明式描述**。拖拽、AI、API 都生成 Spec 和查询 IR，不直接写 SQL。AI 生成的是 Spec，因此可校验、可在编辑器里继续修改、自动受权限约束。
2. **只有查询层能生成和执行 SQL**。权限、缓存、审计只在这一处实现。
3. **只生成 SQL，不解析 SQL**。用户写的来源 SQL 作为子查询整体包裹；列信息和表达式校验靠 `LIMIT 0` 试执行。
4. **Spec 是唯一事实来源**，带版本号，加载时逐版本迁移。
5. **服务无状态**。状态全部在 Postgres、Redis、对象存储中。
6. **平台基础通过接口接入**。认证、权限、审计各有接口，增加一种实现（如 OIDC 登录、列级权限）不改上层代码。

## 4. 一次查询的路径

```
前端生成图表 Spec（含查询 IR）
 → 结构校验、语义校验（字段是否存在于数据集）
 → 按当前用户注入行列权限
 → 展开派生计算（同环比等）
 → 编译为目标数据库方言的 SQL
 → 查缓存，未命中则执行
 → 结果整形后返回，前端按 Spec 渲染
```

## 5. 运行时

```
浏览器(React)        宿主系统(嵌入 / API)
      └──────────┬──────────┘
        supabi 单二进制，按启动参数决定角色
        ┌────────┼────────┐
       api     worker   scheduler
        └────────┼────────┘
  Postgres     Redis     对象存储     用户数据源
```

| 角色 | 职责 |
|---|---|
| `api` | HTTP 接口、查询编译、同步查询 |
| `worker` | 异步查询、导出、订阅推送的实际执行 |
| `scheduler` | 时间触发的任务：订阅推送、数据告警、缓存预热、元数据同步、清理、物化刷新。只负责投递任务，不执行 |

当前 worker 已实现数据探索 SQL 和仪表盘图表数据的 CSV/XLSX 后台导出，以及文件清理，scheduler 为有导出记录的组织每小时投递一次过期导出清理任务；队列使用 Postgres 的租约与原子领取机制，完成结果的「新结果」标记与完成状态在同一事务中写入 Postgres。导出文件放在数据目录或 S3 兼容的对象存储中。具体规则见 [导出设计](exports.zh.md)。其他任务类型尚未实现。

- 小规模部署一个进程跑全部角色；规模大时各角色独立扩容。
- scheduler 多实例时靠 Postgres 任务队列保证同一任务只触发一次。
- 前端构建产物嵌入 Go 二进制，单文件交付。

| 依赖 | 用途 | 是否必需 |
|---|---|---|
| Postgres | 元数据、任务队列 | 必需 |
| Redis | 查询结果缓存 | 可选，最小部署可关闭 |
| 数据目录 | 默认存放导出文件 | 导出放在对象存储时不需要；放在本地且多实例时需挂载共享卷 |
| 对象存储 | 导出文件（`--export-storage=s3`），S3 或兼容的实现 | 可选 |

## 6. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 后端 | Go，模块化单体 | 单二进制、内存占用低、编译型，适合私有化；内部按模块划清边界，以后可拆服务 |
| 前端 | React、TypeScript、Vite，pnpm 工作区；路由用 React Router，多语言用 i18next | 见第 11 节 |
| API | REST + OpenAPI | 由接口定义生成前端类型；工具链简单，便于调试和嵌入方接入 |
| 元数据库 | Postgres，驱动用 pgx | |
| 数据库迁移 | 自研的轻量迁移器 | 迁移文件嵌入二进制，只进不退，校验已应用文件未被改动，用数据库锁保证多 pod 同时启动时只执行一次 |
| 资源 ID | 类型前缀加随机串，如 `ds_3f8k2m9q0x7c1b5n4d6h` | 在日志、URL、Spec 中自带类型信息 |

Go 的两个短板及应对：

- **长尾数据源驱动**：数据源做成接口，以后可挂 JDBC 桥接进程。
- **多方言 SQL 解析**：见核心约束第 3 条，设计上绕开。

## 7. 开源协议

- 协议是 Apache 2.0，见仓库根目录的 `LICENSE`。全部功能开源，没有闭源的企业功能：SSO、列级权限与脱敏、审计、多租户、嵌入都在同一个代码库里，按 [权限与工作空间模型](access-control.zh.md) 第 8 节的范围逐步实现。
- 早先的方案是 AGPL 3.0 加闭源企业版（open core）。2026-10-17 改为现在的方案：企业的法务普遍接受 Apache 2.0，嵌入到其他产品里也没有障碍，也不必维护开源版与企业版的边界。代价是协议不阻止别人拿去托管售卖。
- 只有一个 Go 模块、一个入口 `cmd/supabi`。启动逻辑在 `internal/app`，代码都在 `internal/` 下，不对外提供 Go 包。
- 外部贡献用 DCO（提交带 `Signed-off-by`）还是 CLA，在接受第一个外部贡献之前决定。
- 不复制 AGPL、GPL 等 copyleft 项目的代码，它们与 Apache 2.0 不兼容；新增依赖前确认其许可证可以随 Apache 2.0 分发。

## 9. 数据源的可扩展性

首批支持：MySQL、PostgreSQL、ClickHouse、Doris/StarRocks。Presto/Trino 在初版之后。目前已全部实现：PostgreSQL、MySQL、ClickHouse、StarRocks、Doris，以及 Trino（见 9.3），都通过同一套一致性测试。不内置分析引擎，见 9.2。

MySQL 需要 8.0 或更新版本：生成的 SQL 用到窗口函数（累计）、`CAST(… AS DOUBLE)`（占比、同环比的差值和增长率、`TO_FLOAT`）和 `REGEXP_LIKE`，连接时还要设会话变量 `transaction_read_only`。测试连接时读服务器版本，低于 8.0 就判为失败并说明原因；版本读不到时，按失败的方式认出常见的旧服务器：加密连接握手失败（用旧 OpenSSL 编译的 5.7 只接受 Go 默认不再提供的 RSA 密钥交换），或者服务器不认识 `transaction_read_only`（5.7.20 之前）。这些失败带错误码，界面按语言说明。只在测试连接时检查，已有的数据源照常保存和查询。MariaDB 的版本号与 MySQL 不同，不按版本判断。是否支持 5.7 见 [暂缓事项](../backlog.zh.md)。

目标是新增一种数据库时只需实现接口并通过测试，不改查询编译器、不改前端。为此：

1. **驱动接口保持小**：连接与探活、带取消的查询执行、元数据列举（库、表、列）、物理类型到逻辑类型的映射、返回方言。
2. **方言按能力拆成几个小接口**（标识符转义、时间函数、类型转换、分页、占位符风格等），提供 ANSI 默认实现，各数据库只覆盖有差异的部分。
3. **能力声明**：方言声明自己是否支持窗口函数、CTE 等。编译器据此选择写法或给出明确错误，而不是生成一条会失败的 SQL。
4. **一致性测试套件**：同一组查询 IR 用例对每个驱动运行并比对结果。新数据库通过这套测试即视为接入完成。
5. **连接配置由驱动声明**：驱动提供配置项的结构描述，前端据此自动渲染连接表单。
6. **表的标识从一开始就是三段**（catalog、schema、table），为 Trino 这类多 catalog 引擎预留。驱动列举表时给出每张表所在的层级：PostgreSQL 是数据库和 schema 两层，Trino 是 catalog 和 schema 两层，MySQL、StarRocks、Doris、ClickHouse 是数据库一层。
7. 协议兼容的数据库共用驱动、各自实现方言：Doris 和 StarRocks 复用 MySQL 协议驱动。两者共用一个方言，只在 `date_trunc` 的参数顺序上区分。

第 4 条的测试套件在 `internal/conformance`。接入一种新数据库的步骤：在 `internal/dialect` 实现方言，在 `internal/datasource/<名称>` 实现驱动并在其测试中调用 `conformance.Run`，在 `internal/app` 中引入该驱动包，在 `compose.yaml` 中加上测试用的数据库服务。

### 9.1 数据库之间保留下来的差异

套件保证相同的查询在各数据库上得到相同的值，但以下差异来自数据库自身，目前没有抹平：

| 差异 | 说明 |
|---|---|
| 数值的表示 | 整数列求和在 PostgreSQL 返回整数，在 MySQL 返回小数；值相同，接口返回的类型不同 |
| 文本比较是否区分大小写 | 取决于数据库和列的排序规则。MySQL 默认不区分，PostgreSQL 区分，影响等值过滤、`contains` 和分组 |
| 文本排序的顺序 | 取决于排序规则，中文尤其如此 |
| 布尔类型 | MySQL 的布尔是 `TINYINT(1)`，会被识别为整数 |
| 夏令时切换时刻 | MySQL 以数据时区的本地时间比较，夏令时回拨的那一小时无法区分先后；PostgreSQL 按绝对时刻比较，没有这个问题 |
| 小数相除的精度 | ClickHouse 的小数除法保留被除数的小数位，`350.25 / 2` 得 `175.12`；Trino 取两数中较多的小数位并四舍五入，得 `175.13`。数据集里用原生 SQL 写的比率类度量需要自己转成浮点数再除，标准表达式的 `/` 已经处理过 |
| 文本匹配的写法 | ClickHouse 用 `position`、`startsWith`、`endsWith`，其余用 `LIKE`。对使用者无差别 |
| ClickHouse 的时间都是时刻 | `DateTime` 存的是时刻，时区只影响显示。数据时区在这里的作用是：数据集 SQL 里不带时区的时间文本按它解析 |
| ClickHouse 没有布尔比较结果类型 | 比较表达式返回整数 0 或 1 |
| ClickHouse 对没有行的最值返回类型的默认值 | 不是 NULL，时间是 1970 年。字段的 `min`/`max` 和标准表达式里的 `MIN`/`MAX` 已改写为 `minOrNull`/`maxOrNull`；用原生 SQL 写的指标要自己这样写 |
| StarRocks、Doris 和 Trino 没有只读会话 | 无法在连接上强制只读，只能依靠数据库账号的权限。它们的参数由客户端转义后拼入语句，而不是服务端绑定 |
| Trino 的名称不分大小写 | 加了引号也一样，结果的列名都是小写。数据集的两个列名只差大小写时会冲突 |
| Trino 不把文本当作日期或数字 | 平台绑定的参数已经按类型转换；数据集 SQL 里自己写的值要写成 `DATE '2026-01-01'` 或 `CAST(… AS date)` |
| StarRocks 和 Doris 只有不带时区的时间类型 | 与 MySQL 的 `DATETIME` 相同，按数据时区的本地时间处理 |
| MySQL 需要时区表 | 服务器未加载时区表时拒绝连接并给出提示，而不是返回错误的结果 |

数据集的来源 SQL 是用数据源自己的方言写的，本来就不可移植。计算字段用 [标准表达式](expressions.zh.md) 书写时可以移植，用原生 SQL 书写时不可以。

### 9.2 不内置分析引擎，不做文件上传

2026-10-19 移除了上传数据和内置的 DuckDB 引擎。此前可以上传 CSV、Excel 或 Parquet 文件，每个文件转成 Parquet 后成为一张表，由每个实例内嵌、并被锁成不能联网也不能加载扩展的 DuckDB 查询。移除的原因：

- 上传的表只存在于 SupaBI 自己的引擎里，不能和用户数据库中已有的数据关联分析，用处有限。
- 为了让数据集 SQL 读不到别的工作空间和服务器上的文件，引擎必须锁定；多实例部署因此要么共享卷，要么另做缓存同步，代价和价值不相称。
- DuckDB 需要 CGO：二进制约 84 MB，交叉编译需要对应平台的 C 工具链。移除后二进制不依赖 CGO。

以后需要把文件或其他系统的数据带进来时，做成数据集成：把数据写进用户自己使用的 OLAP 数据库（如 ClickHouse、StarRocks、Doris），再像其他表一样通过数据集分析，就能和已有数据一起用。尚未设计，见 [暂缓事项](../backlog.zh.md)。

### 9.3 Trino

2026-10-21 实现。

**范围**

- 支持 Trino 和基于它的发行版（如 Starburst）。不支持 PrestoDB：两者分家后协议头不同，Trino 的 Go 驱动连不上它，见 [暂缓事项](../backlog.zh.md)。
- 需要 Trino 418 或更新版本：一致性测试在 418 和 483 上都通过，更早的版本没有测过。测试连接时读服务器版本，低于 418 就判为失败并说明原因，做法与 MySQL 相同；已有的数据源照常查询。
- 驱动用官方的 `trino-go-client`。它是纯 Go 实现，二进制仍不依赖 CGO。取消查询时驱动会通知 Trino 结束它，满足 `Conn` 对取消的要求。
- 只支持用户名和密码登录。驱动只在 HTTPS 下发送密码，填了密码却没选 HTTPS 时，连接直接报错并说明原因。Kerberos、JWT 和 OAuth2 见 [暂缓事项](../backlog.zh.md)。
- 每条查询都带上来源 `supabi`，Trino 的管理员能在查询列表里认出来，作用与 PostgreSQL 的 `application_name` 相同。
- 类别是 OLAP。

**连接配置**

| 设置 | 说明 |
|---|---|
| `host` | 必填 |
| `port` | 默认 8080 |
| `user` | 必填。不带密码时，Trino 只把它当作身份，不做校验 |
| 密码 | 可选；填了就必须用 HTTPS |
| `secure` | 是否用 HTTPS，默认否 |
| `catalog` | 可选，语句里不写 catalog 时用它 |
| `schema` | 可选，语句里不写 schema 时用它；要先填 `catalog` |

**库表结构：列出全部 catalog**

- 表所在的层级是 catalog 和 schema 两层，树上第一层是 catalog。
- 逐个 catalog 读 `system.jdbc.columns`（带列的注释），表的注释另从 `system.metadata.table_comments` 读。先读默认 catalog，其余按名称排序，不列 `system`。读满 `MaxCatalogColumns`（5000 列）就停下，和其他数据库一样标为被截断。
- 某个 catalog 读失败时（比如它背后的数据库连不上，或者账号没有权限），跳过这个 catalog，其余照常列出。否则一个坏掉的 catalog 会让整棵树都打不开。
- 表名按语句里要写的样子给出：默认 catalog、默认 schema 里的表只写表名；默认 catalog 里其他 schema 的表写 `schema.table`；其他 catalog 的表写全名 `catalog.schema.table`。为此 `datasource.Table` 和接口里的 `SourceTable` 增加了可选的 `catalog`，含义与 `schema` 相同：不写也能找到这张表时为空。数据探索里点表名，插入的就是这个名字。
- Hive 这类 catalog 表很多时，读一遍可能很慢，受查询超时的限制。

数据集的选表来源（`type: table`）只有 `schema` 和 `table`，这次没有加 `catalog`。界面上的数据集都由数据探索里的 SQL 生成，选表来源只在接口里有。因此在 Trino 上，选表来源只能指向默认 catalog 里的表，其他 catalog 的表要写成 SQL 来源，见 [暂缓事项](../backlog.zh.md)。

**方言和驱动**

| 方面 | Trino 的情况 | 做法 |
|---|---|---|
| 时间 | 会话时区可以设置 | 把会话时区设为数据时区，与 PostgreSQL 同一个思路：把值转成 `timestamp(6) with time zone` 就得到时刻，不带时区的列按数据时区解释，带时区的列本来就是时刻。精度 6 保住数仓常存的微秒，又是 Trino 算得快的短时间类型 |
| 截断和平移 | `date_trunc` 的周从周一开始；`date_add` 加月时，当月没有的日期收到月底 | 从周日开始的周，照 PostgreSQL 的做法先往后挪一天，截断后再挪回来 |
| 分页 | `OFFSET` 必须写在 `LIMIT` 前面 | 方言增加 `Page`，编译器通过它写 `LIMIT` 和 `OFFSET` |
| 以文本绑定的参数 | 编译器把日期、按本地时间读的时间和要保留全部位数的小数绑定成文本。别的数据库按用处把文本读成日期或数字，Trino 不会，`date >= varchar` 直接报错 | 方言增加 `TextAs`，Trino 给这些参数加上 `CAST`，其他数据库原样不变。数据集 SQL 里的 `{{参数}}` 也一样按参数的类型转换 |
| 参数怎么送到 Trino | 驱动本来是把参数写成字面量，放在 `EXECUTE … USING` 后面。但这样发送时，Trino 报的错误位置不对（418 和 483 都会把首行的列偏移加到每一行上），带参数的语句也不能 `EXPLAIN` | 由驱动自己把参数写进语句再发送。字面量的写法用官方驱动的 `Serial`，与它写在 `USING` 后面的完全相同；语句里哪些 `?` 是参数，由 `sqlrefs.Placeholders` 按词法找出，字符串、引号里的名称和注释里的 `?` 不算。服务器报的错误位置再换算回原来的语句 |
| 除法 | 整数相除得整数；小数相除时，结果的小数位取两数中较多的那个，再四舍五入 | 平台的 `/` 先把不是浮点数的被除数转成 `decimal(38, 10)` |
| 只读 | 没有只读会话。只读事务可以用，但每条查询要多两次往返，提前关闭结果还会让事务中止 | 不开事务。SQL 总是作为子查询包裹，写操作放不进去；最终靠 Trino 账号的权限，与 StarRocks、Doris 相同 |
| 名称大小写 | 名称加了引号也不区分大小写，结果的列名都是小写 | 编译器按位置读结果，不受影响 |
| 字符串函数 | 没有 `LEFT`、`RIGHT`、`CHAR_LENGTH`，也没有 `ends_with` | 用 `substr` 和 `length` 写出 |
| 中位数 | 只有近似的 `approx_percentile`，而且不插值 | 不提供，与 MySQL 相同 |
| 语句的文本 | 字符串里没有反斜杠转义，没有用 `$` 引起的字符串，`#` 也不开始注释 | `Lexis` 的三项都为否 |

保留下来的差异写在 9.1 节的表里。

**本地环境和测试**

- `compose.yaml` 里的 Trino 服务在 `olap` profile 里，平时不启动（JVM 要占 1～2 GB 内存）；`make test-olap` 一并测试它。
- 两个 catalog 的配置在 `dev/trino/catalog`：`memory` 给一致性测试建表、删表；`postgres` 用 postgresql 连接器、以只读账号读本地开发 Postgres 里的示例数据，不用另外载入，容器重启后也还在。
- 一致性测试平时跑 Trino 483。418 在 2026-10-21 手动跑过一遍，全部通过。

**前端**

页面逻辑没有改，只补了这几处：类型名称和 Logo；`catalog`、`schema` 两个设置项的名称；数据探索和数据源页上的表名带上 catalog；SQL 格式化用 `sql-formatter` 自带的 Trino 方言。编辑器的语法高亮用标准 SQL，自动补全还不认 catalog，见 [暂缓事项](../backlog.zh.md)。

## 10. 多语言与多时区

两者都是事后补救代价很高的横切要求，从第一行代码起遵守。

### 10.1 多语言

| 范围 | 做法 |
|---|---|
| 界面文案 | 前端全部走语言包，不写死字符串。首批简体中文和英文 |
| 后端错误 | 接口返回错误码加参数，由前端翻译；后端不返回写死的自然语言文案 |
| 服务端生成的内容 | 订阅邮件、推送消息、导出文件的表头在服务端渲染，后端也需要语言包，按接收人的语言生成 |
| 数字、日期、货币的显示 | 数据集字段和图表里存结构化的数值格式（[数据集模型](dataset.zh.md) 5.5），前端按用户的区域设置渲染（千分位、小数点、月份名等） |
| AI 助手 | 按用户语言回答；数据集字段的 `label`、`description`、`synonyms` 是它理解多语言提问的依据 |
| 语言设置 | 用户级偏好，缺省取组织默认值，再缺省取浏览器语言 |

用户自己创建的内容（仪表盘标题、字段显示名等）的多语言翻译 v1 不做，见 [暂缓事项](../backlog.zh.md)。

### 10.2 多时区

涉及四个不同的时区，必须分清：

| 时区 | 含义 | 设置位置 |
|---|---|---|
| 存储时区 | 元数据库中的时间戳 | 一律 UTC |
| 数据时区 | 用户数据库里不带时区的时间列，实际表示哪个时区 | 数据源上设置，可在数据集字段上覆盖 |
| 查询时区 | 按天、按月分组时以哪个时区为界；「今天」「最近 7 天」指哪个时区的 | 工作空间默认值，仪表盘可覆盖；即查询 IR 的 `timezone` |
| 用户时区 | 界面上「创建于」「上次刷新」等系统时间如何显示 | 用户偏好，缺省取浏览器时区 |

规则：

1. **查询时区默认跟随工作空间，而不是查看者**。否则同一张仪表盘上的「昨日销售额」会因人而异。仪表盘可以单独选择「使用查看者的时区」。
2. **时区换算在数据库内完成**：按粒度截断时间之前，先把数据时区转换为查询时区。这是方言接口必须实现的能力。
3. `date` 类型不做时区换算。
4. 相对时间和动态参数默认值（如 `today-1d`）都按查询时区解析。
5. 定时任务（订阅、告警）的计划时间带时区，并正确处理夏令时。
6. 查询结果中的时间以查询时区的本地时间返回，不带偏移量，前端不再换算。维度、明细列、时间字段的 `min`/`max` 和时间类型的指标都是如此。聚合和按时间度量排序都按实际时刻，最后才把结果换算成本地时间：夏令时回拨时墙上时间会重复，按本地时间取最大值可能取到较早的时刻。MySQL、StarRocks 和 Doris 没有时刻类型，按数据时区的本地时间聚合和排序，见 9.1 中夏令时一行。
7. 查询时区是查询 IR 的一部分，因此自动参与缓存键。

与时区相近的区域性设置：**每周起始日**（周一或周日），工作空间级，影响按周分组，同样由方言接口处理。

**第一周**也是工作空间级的设置：哪一周算一年的第 1 周，只用于把按周分组的值写成「第几周」（[数据集模型](dataset.zh.md) 5.5）。它不进入查询，也不参与缓存键：按周分组只用每周起始日，第几周是前端从这一周的第一天数出来的。保存为 `firstWeekDays`，即第 1 周至少要有几天在当年：

| `firstWeekDays` | 规则 | 2026 年第 1 周（周一开始） | 2027 年第 1 周（周一开始） |
|---|---|---|---|
| 4（默认） | 至少 4 天在当年。周一开始时就是 ISO 8601 | 2025-12-29 ~ 2026-01-04 | 2027-01-04 ~ 01-10 |
| 1 | 1 月 1 日所在的周 | 2025-12-29 ~ 2026-01-04 | 2026-12-28 ~ 2027-01-03 |
| 7 | 第一个完整的周 | 2026-01-05 ~ 01-11 | 2027-01-04 ~ 01-10 |

第 1 周之前的几天属于上一年的最后一周。工作空间设置里，「第一周」放在「每周起始日」后面，空间管理员修改，已有的工作空间按默认值。

## 11. 前端约束

技术栈：Vite、React、TypeScript。底层组件库用 shadcn/ui（基于 Radix 原语和 Tailwind CSS），底层图表库用 ECharts，但两者都不允许被业务代码直接使用。

### 11.1 图表：必须完全封装

图表 Spec 是我们自己定义的声明式结构，会被持久化、被 AI 生成、被版本迁移。ECharts 的配置对象不得出现在 Spec、接口或业务代码中。

```
图表 Spec + 查询结果  →  适配器  →  ECharts 配置  →  渲染
```

- 适配器是唯一认识 ECharts 的地方。更换或增加渲染引擎只需新增适配器。
- Spec 表达不了的效果，通过扩展 Spec 解决，不提供「直接写 ECharts 配置」的后门，否则 Spec 不再可移植、可校验。
- 表格、透视表、指标卡不依赖 ECharts，由我们自己的组件实现，同样由 Spec 驱动。

### 11.2 组件：统一出口，分层封装

硬性规则：业务代码只能从我们自己的组件包引入组件，不得直接引入 Radix、shadcn 生成的代码或组件包用到的其他底层库。用 lint 规则强制。

组件包内部分三层：

| 层 | 范围 | 属性定义 |
|---|---|---|
| 基础组件 | 按钮、输入框、选择器、弹窗、标签页、提示、下拉菜单、图标等高频组件 | 完全自定义，只暴露我们需要的属性，不继承底层库的类型 |
| BI 领域组件 | 字段选择器、过滤条件编辑器、结果表格、仪表盘栅格等 | 完全自定义，基于基础组件组合 |
| 复杂组件 | 表单、后台管理列表用的表格、日期选择、树等 | 初期薄封装：属性是底层库属性的收窄子集，随使用逐步收紧为自定义 |

- 设计变量（颜色、间距、圆角、字号）由我们定义，再映射为 shadcn 的 CSS 变量（`styles.css`）。暗色模式和白标都依赖这一层。
- 代码编辑器（来源 SQL、计算字段表达式）同样只从组件包引入。底层用 CodeMirror，它的配色取自设计变量，体积较大，所以在第一次显示时才加载。
- 复杂组件采用薄封装是有意的取舍：表单和表格的接口面非常大，一开始就全部重新定义会严重拖慢进度，且容易做成功能不足或原样透传的空壳。
- shadcn 的组件由它的 CLI 生成到 `packages/ui/src/shadcn/`，尽量保持上游原样，当作仓库里的底层库：shadcn 生态的组件（如 AI Elements）按路径引用彼此，上游的修复也能用 CLI 重新生成后吸收。我们的封装放在它外面，对外的属性由封装定义。
- Tailwind 只用于组件包内部，类名带 `tw:` 前缀，也不启用它的全局重置（preflight）。业务样式仍是普通 CSS，前缀保证业务的类名不会和 Tailwind 的工具类相撞。业务 CSS 要调整组件外观，只能通过封装根元素上的 `lb-*` 类名，不能依赖底层库内部的结构。
- 测试打开下拉框、菜单等弹出层时使用 `@supabi/ui/testing`，不依赖底层库触发弹出的具体事件。

### 11.3 包结构

| 包 | 内容 | 依赖 |
|---|---|---|
| `ui` | 组件与设计变量 | 底层组件库 |
| `charts` | 图表 Spec 类型、适配器、渲染组件 | 底层图表库 |
| `app` | 管理端与编辑器 | `ui`、`charts` |
| 嵌入 SDK（后续） | 只含仪表盘渲染 | `charts` 和 `ui` 中渲染所需的部分 |

嵌入 SDK 要运行在宿主页面里，对体积和样式隔离敏感，这是把 `charts` 独立成包、并让渲染路径尽量少依赖底层组件库的原因。

### 11.4 按需加载

- 登录页和顶栏在首屏加载；我的仪表盘、工作台、数据探索、系统与空间设置各自在第一次打开时才下载。普通用户看仪表盘只下载仪表盘和图表的代码，不下载编辑器；ECharts 只在打开图表时下载。代码编辑器原本就是第一次显示时才加载。
- `ui` 包声明只有 CSS 有副作用（`package.json` 的 `sideEffects`），没用到的组件不进首屏。因此组件的样式会随所在的代码块加载，可能排在 `app.css` 之后：覆盖底层库样式的规则写在组件自己的 CSS 里，跟在底层库样式后面，不放在 `app.css`。
- 部署新版本后，旧版本的代码块不再存在，已打开的页面切换到未加载的区域时取不到文件。页面这时自动刷新一次换成新版本；刷新后仍然失败才显示错误。
- 2026-10-19 的构建：首屏 JavaScript 从 2,262 KB（gzip 708 KB）降到约 849 KB（gzip 约 276 KB）。

## 12. 工作台

顶栏依次提供「我的仪表盘」「工作台」「数据探索」「空间设置」。我的仪表盘是读者的只读入口，左侧按文件夹列出仪表盘（不显示空文件夹），右侧显示选中的仪表盘；窄屏上列表和仪表盘分成两屏（[图表与仪表盘 Spec 设计](chart-dashboard.zh.md) 3.16）。数据探索负责 SQL 编写和试运行；工作台管理数据集、图表、仪表盘和数据源。数据探索和工作台只对数据开发和管理员开放，二者均使用当前工作空间的数据源和权限。

设置按管理范围分成三个入口。头像菜单的「系统管理」集中维护全局用户、全局用户组和全部工作空间；「个人设置」管理本人的账号和密码。顶栏导航的「空间设置」包含基本设置、成员与访问、用户属性，标题显示当前空间名称。数据开发进入空间设置时只看到只读的用户属性；系统管理限系统管理员，且不依赖当前工作空间。系统管理的空间列表可进入某个空间的同一套设置，不再与当前空间配置混在一页。

用户和用户组统一归组织，空间保存对它们的授权及自定义用户属性，不提供空间用户组或全局自定义属性。三类设置的路由及权限边界见[权限与工作空间模型](access-control.zh.md) 2.1–2.2。

工作台的布局参照代码编辑器，外观是「岛屿」式：侧边面板、编辑器、底部面板各是一块圆角的面，浮在同一块底色上，彼此留有间隙，间隙就是拖动调整大小的把手；顶栏、图标条、状态栏属于底色本身。我的仪表盘和三类设置页面用同样的外观，设置页见[权限与工作空间模型](access-control.zh.md) 2.2.1。

```
┌ 顶栏 ─────────────────────────────────────────────┐
├──┬────────────┬───────────────────────────────────┤
│图│ 侧边面板    │ 编辑器                             │
│标│ 当前部分里  │                                   │
│条│ 有什么可开  ├───────────────────────────────────┤
│  │            │ 底部面板：结果、预览、引用          │
├──┴────────────┴───────────────────────────────────┤
│ 状态栏：路径 · 行数与耗时 · 未保存                   │
└───────────────────────────────────────────────────┘
```

| 部分 | 侧边面板 | 编辑器 |
|---|---|---|
| 仪表盘、图表、数据集 | 文件夹树，可新建、重命名、移动、删除，支持拖拽 | 各自的编辑器 |
| 数据源 | 名称列表 | 详情或新建表单 |

- **数据探索没有脚本资源**。路由是 `/explore`，左侧独立面板放数据源选择和库表结构，右侧是查询标签页与 SQL 编辑器，下方是结果、执行计划和运行历史。无个人/工作区脚本分类、文件夹或保存按钮。标签、SQL 草稿和运行历史按账号与工作空间保存在当前浏览器，主动关闭查询时确认丢弃草稿。
- **SQL、数据源与参数属于数据集**。探索页可以直接创建数据集草稿；从数据集打开 SQL 编辑时，带入原表单当前草稿并显示所编辑的数据集名称。「应用并返回数据集」只更新原表单的 SQL、数据源与参数，随后在数据集统一校验并保存修订。没有独立的 SQL 资源或修订历史。
- **血缘依赖数据集自己的 SQL**。层次为数据源 → 表 → 数据集 → 图表 → 仪表盘；找不到表名的 SQL 直接关联数据源。
- **SQL 只在数据探索里写**。数据集编辑器只做配置：字段的名称、类型、维度或度量、计算字段，以及预览。新数据集由数据探索里的 SQL 生成；修改已有数据集的 SQL 也回到数据探索，改完再应用回数据集。数据探索执行 SQL 的方式与数据集相同（作为子查询包裹、只读、限制行数），没有另一条执行路径。
- **工作台一次只开一个资源**，不做多标签页。来回切换靠搜索面板（Ctrl+K / ⌘K）：不输入时列出最近打开的资源。离开有未保存修改的编辑器会先询问。数据探索作为独立页面，在应用打开期间保留查询标签、SQL 草稿和结果，切换顶栏入口后再回来仍在；刷新后恢复标签和草稿，结果需要重新运行。
- **侧边面板、编辑器旁的面板、底部面板、状态栏属于外壳**，内容由当前页面填入，因此各个编辑器的结果区域位置和行为一致。面板可以收起和拖动调整大小，状态保存在浏览器里。
- **引用关系**在底部面板里：数据源被哪些数据集使用，数据集被哪些图表和仪表盘使用，图表被哪些仪表盘使用。

### 关联资源的浏览器标签页

编辑器中的关联跳转（引用、血缘、来源数据集、来源图表、来源 SQL，以及由现有资源创建图表或数据集）在新浏览器标签页打开，保留当前编辑现场。侧栏、列表和搜索等主导航仍在当前标签页切换。链接使用真正的链接和 `target="_blank"`，同时保留浏览器的右键、复制链接和快捷键行为。

数据集的「编辑 SQL」也在新标签页打开。SQL 编辑页将结果回传给原来的数据集表单，只替换 SQL、数据源及参数，保留未保存的名称和字段修改；只有原表单确认收到后才关闭 SQL 编辑窗口并返回原表单。原表单关闭时明确提示无法回传，不能宣称应用成功。SQL 不放在 URL 中。每个回传窗口保留自己的 SQL 标签集合，切换查询或其他页面后刷新，仍恢复该窗口的标签与草稿。
