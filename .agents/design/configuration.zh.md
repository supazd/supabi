# 启动配置

启动配置原先只能用命令行参数或 `SUPABI_*` 环境变量设置，三项密钥只能用环境变量。本设计增加 YAML 配置文件，作为部署时主要的配置方式；环境变量和命令行参数保留，用来覆盖个别项。

状态：已实现。第 10 节把全组织只该有一个值的六项搬进了系统管理，第 11 节在启动时核对密钥。

## 1. 目标

- 服务器上的服务通常用配置文件：Spark 的 `spark-defaults.conf`、Hadoop 的 `*-site.xml`、Trino 的 `etc/config.properties`。一个文件包含一套环境的全部配置，容易阅读和审阅，可以纳入版本管理，在机器和环境之间迁移。
- 配置中心（Nacos、Apollo、Consul）和 Kubernetes 的 ConfigMap 都能把配置落成文件，文件是对接它们最通用的形式。
- 多个实例共用一份文件，需要一致的部署环境（`data-dir`、S3、Redis）自然一致。全组织只该有一个值的设置不在启动配置里，存在元数据库，见第 10 节。
- 现有用环境变量和参数部署的方式继续可用。

## 2. 指定配置文件

```bash
supabi serve --config /etc/supabi/supabi.yaml
```

- 用 `--config` 或环境变量 `SUPABI_CONFIG` 指定，两者都有时 `--config` 优先。容器镜像可以设好 `SUPABI_CONFIG`。`serve` 和 `migrate` 都支持。
- **不自动查找默认位置**。不指定就不读任何文件，配置全部来自环境变量、参数和默认值。自动查找会出现「不知道读的是哪个文件」的情况，在容器里还可能读到镜像里意外带进去的文件。启动日志写明读取的文件路径。
- 指定的文件不存在或不能读取时拒绝启动。文件可以为空。
- 相对路径按进程的工作目录解析，文件里的相对路径（如 `data-dir`）也一样，与参数和环境变量相同，同一个值不因写在哪里而含义不同。生产环境建议都写绝对路径。

用 systemd 部署时：

```ini
[Service]
User=supabi
ExecStart=/usr/local/bin/supabi serve --config /etc/supabi/supabi.yaml
```

## 3. 文件格式

```yaml
http-addr: 0.0.0.0:8080
database-url: postgres://supabi:PASSWORD@db.internal:5432/supabi
secret-key: KEY_FROM_SUPABI_GENERATE_KEY
data-dir: /var/lib/supabi

export-storage: s3
s3-endpoint: https://s3.example.com
s3-bucket: supabi-exports
s3-path-style: true
s3-access-key-id: ACCESS_KEY
s3-secret-access-key: SECRET_KEY

query-cache: redis
redis-url: redis://:PASSWORD@redis.internal:6379/0
```

- **平铺，不分层级**。键名就是参数名去掉 `--`，环境变量名是 `SUPABI_` 加上键名转大写、连字符换成下划线。同一项在三处只有一套拼法规则，`supabi serve -h` 里的说明直接适用于文件。

  | 文件中的键 | 命令行参数 | 环境变量 |
  |---|---|---|
  | `http-addr` | `--http-addr` | `SUPABI_HTTP_ADDR` |
  | `export-workers` | `--export-workers` | `SUPABI_EXPORT_WORKERS` |
  | `secret-key` | 无 | `SUPABI_SECRET_KEY` |

- 可以写的项是全部 18 个参数，加上三项密钥 `secret-key`、`s3-access-key-id`、`s3-secret-access-key`。以后新增的参数自动可以写在文件里，名称遵守同样的规则。
- **值一律按文本读取**，再交给与命令行参数相同的解析和校验，所以不受 YAML 自身类型推断的影响：`auto-migrate: false`、`export-workers: 4`、`query-cache-size: 256MB` 都按参数的规则理解。引号可加可不加。
- 只接受「键: 单个值」。写成列表或嵌套时报错；`roles` 与参数一样写成 `api,worker`。
- `key:` 后面不写值，等同于没有这一行，即这一项未设置。要设成空字符串，写 `""`。
- 以下情况拒绝启动，报错带文件路径和行号：
  - 不认识的键，防止拼错的项被静默忽略：`supabi: /etc/supabi/supabi.yaml:7: unknown setting "exprot-workers"`
  - 同一个键出现两次
  - 值的格式不对：`supabi: /etc/supabi/supabi.yaml:12: invalid value "two" for export-workers: parse error`
  - 已经搬进系统设置的键，见 10.5
  - 顶层不是「键: 值」的映射

## 4. 密钥

- 三项密钥，以及带密码的 `database-url`、`redis-url`，都可以写在文件里。原先只许用环境变量，是因为命令行参数会出现在进程列表里；写在文件里没有这个问题。
- 密钥仍然没有命令行参数。
- 文件包含密钥时，建议权限设为 `600`，属主为运行服务的用户。程序不检查文件权限：Kubernetes 挂载的 Secret 和 ConfigMap 默认就是 `0644`，检查会在常见的部署方式里误报。
- 配置文件要放进版本库或配置中心、但密钥不想跟着走时，文件里不写这几项，改用环境变量提供（例如 Kubernetes 把 Secret 注入为环境变量）。环境变量优先于文件，文件里不需要写占位符。

## 5. 优先级

**命令行参数 > 环境变量 > 配置文件 > 程序默认值**

- 文件是一套环境的基准配置；容器平台用环境变量覆盖个别项；临时排查时用参数覆盖。与 Spark 用 `--conf` 覆盖 `spark-defaults.conf` 同理。
- 拆分部署时，所有实例共用一份文件，每个实例只用 `--roles` 或 `SUPABI_ROLES` 指定自己运行的角色。
- 值为空的环境变量（`SUPABI_X=`）视为未设置，与文件中 `key:` 不写值一致。
- 文件里设置了、却被环境变量或参数覆盖的项，启动时各写一行日志，只写键名和来源，不写值，免得「改了文件却不生效」时无从查起：

  ```
  level=INFO msg="config file setting overridden" key=roles by=--roles
  level=INFO msg="config file setting overridden" key=database-url by=SUPABI_DATABASE_URL
  ```

## 6. 环境变量改为严格校验

现在时长、布尔、整数类的环境变量格式不对时，程序静默使用默认值。例如 `SUPABI_EXPORT_TIMEOUT=15` 漏了单位会变成 15 分钟，`SUPABI_AUTO_MIGRATE=flase` 会当成 `true`。改为与参数和文件相同的校验，格式不对时拒绝启动，并指出变量名：`supabi: invalid value "15" for SUPABI_EXPORT_TIMEOUT: parse error`。

本设计只有两处行为与现在不兼容：

- 带着格式错误的环境变量也能启动的部署，升级后会启动失败，需要改正这个值。
- 值为空的字符串类环境变量，以前表示空字符串，现在表示未设置。只有 `SUPABI_REDIS_KEY_PREFIX=` 这一种写法结果会变：以前是不加前缀，现在是默认的 `supabi:`。

## 7. 示例配置

- 示例配置内嵌在程序里，用 `supabi example-config` 打印：

  ```bash
  supabi example-config > /etc/supabi/supabi.yaml
  ```

  只拿到二进制文件或容器镜像也能得到示例，不依赖发行包的目录结构。
- 每项都有一段英文注释，写明用途和默认值，按基本、日志、导出、S3、查询缓存分组。
- 必填的 `database-url` 和 `secret-key` 保持未注释、不写值，不填就启动会给出明确的报错。其余项注释掉并写出默认值：不修改的项会跟随新版本的默认值，而不是固定在复制示例时的版本。
- 用测试保证示例包含全部配置项，注释里写的默认值与程序一致。
- README 的「运行」一节改为以配置文件为主。环境变量和参数作为覆盖方式介绍。

## 8. 实现要点

- 用 `go.yaml.in/yaml/v3` 解析成节点树，保留行号用于报错。这个库已经作为间接依赖出现在 `go.mod` 里。
- 文件和环境变量里的值都通过 `flag.FlagSet.Set` 写入，与命令行参数共用同一套解析和校验。三项密钥不注册为命令行参数，单独处理。
- 所有配置项名称有一张统一的清单，由它推出文件键名和环境变量名，测试检查对应规则。

## 9. 不做

| 事项 | 原因 |
|---|---|
| 自动查找默认位置的配置文件 | 见第 2 节 |
| 运行中重新加载配置 | 监听地址、元数据库、存储和角色都不能在运行中切换。只重载一部分，就要逐项规定哪些能立即生效，容易误解。改配置后重启进程即可：Kubernetes 用滚动重启，配置中心推送后由它的客户端或部署工具重启 |
| 直接对接配置中心（内置 Nacos、Apollo、Consul 客户端） | 它们都能把配置落成文件。内置客户端要为每一家写代码，还会让启动依赖配置中心是否可用 |
| 多个配置文件、include、按环境的 profile | 一套环境一个文件。密钥与其他配置分开，靠环境变量实现，见第 4 节 |
| 在文件里引用环境变量（`${VAR}`） | 环境变量本来就覆盖文件，文件里不写这一项即可 |
| 检查配置文件的权限 | 见第 4 节 |
| 分层的键（`export:` 下面写 `max-rows:`） | 平铺能让同一项在文件、参数、环境变量里遵守同一套拼法规则；分组用示例里的注释表达 |
| 单独的校验命令（不启动，只检查配置） | 启动时已经完整校验。以后需要在推送配置前预先检查时再加 |

## 10. 系统设置

### 10.1 哪些配置放在哪里

- **启动配置**只放两类：每台机器、每个进程自己的（监听地址、角色、目录、日志、导出的并发数、缓存的内存上限、是否自动迁移），以及连上元数据库之前就要用的（`database-url`、`secret-key`）。前一类在不同实例上不同，本来就是对的。
- **全组织只该有一个值的**存进元数据库，由系统管理员在「系统管理 → 通用设置」里改。

这几项原先也在启动配置里，各实例各读各的，值可能不同，结果就看碰巧由哪个实例执行：每小时的维护任务只由一个实例执行，审计保留多久，看这一小时轮到谁；一次导出最多多少行，看任务被哪个 worker 领走。共用一份配置文件只是约定，挡不住某个实例用环境变量或参数改掉。存进库里就只有一份。

搬进系统设置的六项：

| 设置 | 原来的启动配置 | 默认值 | 界面上的单位和范围 |
|---|---|---|---|
| 导出文件保留 | `export-retention` | 24 小时 | 小时，1 到 8760（一年） |
| 导出超时（每次尝试） | `export-timeout` | 15 分钟 | 分钟，1 到 1440（一天） |
| 导出行数上限 | `export-max-rows` | 2,000,000 | 行，1 到 100,000,000 |
| 导出文件大小上限 | `export-max-size` | 512 MB | MB，1 到 1,048,576（1 TB） |
| 审计保留 | `audit-retention` | 180 天 | 天，0 到 36500，`0` 表示永久保留；AI 用量记录也用它（[AI 助手](ai-assistant.zh.md) 13.5） |
| 查询缓存默认有效期 | `query-cache-ttl` | 10 分钟 | 分钟，1 到 1440 |

下限与原来的启动参数相同，只是按界面上的单位取整。原来没有上限，现在的上限只为挡住写错的值（如多打几个 0），也让时长不会超出程序能表示的范围。查询缓存的有效期改为与数据源的「结果缓存」可选的范围相同（[查询 IR](query-ir.zh.md) 6.5）。

### 10.2 存储和生效

- 元数据库里一张 `system_settings` 表，每个组织一行，与 `ai_settings` 相同。每项一列，空值表示用程序的默认值：没改过的项跟随新版本的默认值，与示例配置里注释掉的项同理（第 7 节）。没有这一行时全部用默认值。
- 每次用到时从库里读，改了立即生效，不用重启，各实例读到的一样，与 AI 模型的配置相同（[AI 助手](ai-assistant.zh.md) 3.1）：

  | 设置 | 何时读 | 对已有的影响 |
  |---|---|---|
  | 导出超时、行数上限、大小上限、文件保留 | 每次尝试开始时；文件完成时按读到的保留期算出到期时间 | 正在执行的尝试按开始时读到的值执行完；重试时重新读。已完成的文件按原来的到期时间 |
  | 审计保留 | 每次维护任务开始时 | 调短后，下一次维护（一小时内）删除超出的审计事件和 AI 用量记录 |
  | 查询缓存默认有效期 | 每次查询时（数据源没有单独设置时） | 已缓存的结果按写入时的有效期到期 |

- 导出中心显示的限制（[导出设计](exports.zh.md) 4.3）也从这里读。
- 导出存到 S3 时，分片大小原来按启动时的文件大小上限算，改为每次尝试按读到的上限算。

### 10.3 页面

- 「系统管理」的导航栏最后加一项「通用设置」（`/settings/system/general`），只有系统管理员能看和改。
- 布局与空间的「基本设置」相同（[权限设计](access-control.zh.md) 2.2.1）：单列，每项左边是名称，右边是输入框和单位，说明写在下方；分「导出」「审计」「查询」「工作空间」「登录」「AI 助手」「MCP 服务」七组（「工作空间」「登录」两组和「查询」里的超时、行数见 10.7，「MCP 服务」见 10.8，「AI 助手」见 10.9）。输入框留空表示用默认值，占位文字就是默认值。有修改才能保存；有未保存的修改时，离开页面先确认。
- 超出范围的值不能保存，原因写在输入框下方。
- 调短审计保留期时，保存前先确认：「保存后一小时内，将删除 N 天之前的审计事件和 AI 用量记录，删除后不能恢复。」从永久保留改为有期限也算调短。其他几项直接保存。

### 10.4 接口和审计

- `GET /system/settings` 返回每项的值（没设置时为空）和默认值；`PUT /system/settings` 整体保存，空值表示用默认值。只有系统管理员能调。
- 保存记一条 `system_settings.update` 事件，详情写改前和改后的值。审计加一个类别「系统 `system`」（[权限设计](access-control.zh.md) 7.1）。

### 10.5 从启动配置中删掉

- 六项的参数、环境变量和配置文件的键一起删掉，不保留覆盖：留着覆盖，各实例又可能不同。
- 仍然给了这几项时拒绝启动，并说明搬到了哪里，免得以为还在生效：

  ```
  supabi: /etc/supabi/supabi.yaml:9: export-max-rows is now set in System administration > General in the web interface, the same for every instance; remove it from the config file
  supabi: SUPABI_AUDIT_RETENTION is now set in System administration > General in the web interface, the same for every instance; unset it
  ```

  命令行参数同样处理。只检查这六项的环境变量，其他不认识的 `SUPABI_*` 环境变量照旧不检查。
- 开发阶段没有要迁移的部署，启动配置里原有的值不自动写进库。
- 示例配置去掉这六项；「审计」一组只有 `audit-retention`，整组去掉。`export-workers` 留在「导出」组，`query-cache-size` 留在「查询缓存」组。

### 10.6 留在启动配置、但各实例要一致的

导出存储和 S3 的各项、查询缓存的方式和 Redis 的各项、本地存储时共用的 `data-dir`，各实例也要一致，但留在启动配置：

- 它们和 `database-url` 一样描述部署环境，S3 的凭证可能来自机器上的 IAM 角色（[导出设计](exports.zh.md) 4.2）。
- 客户端在启动时建好，启动时就检查存储能不能访问；放进库里，就要能在运行中换掉客户端。
- 中途换存储，旧文件留在旧的地方（同上）。
- 它们是基础设施的连接，不属于某个功能：Redis 现在只放查询缓存，以后接口等数据也可能用；S3 参数同样是通用的（同上）。用到分布式锁、共享计数之后，各实例换地址的时刻不同，一部分连旧的、一部分连新的，状态就乱了。`export-storage`、`query-cache` 依赖这些连接，也跟着留下，否则页面上选了 `redis` 而实例没配 `redis-url`，又多一种出错情况。

不一致的后果比上面六项轻：导出存储不同时下载失败，查询缓存的方式不同时只是不能共用缓存，结果不会错。仍靠共用配置文件保持一致。在系统管理里列出运行中的实例、发现不一致时提示，见 [暂缓事项](../backlog.zh.md)。

### 10.7 原来写死的值

下面几个值写死在代码里，既不在启动配置，也不在系统设置：超过 60 秒的查询只能改代码解决，公司要求 8 小时无活动退出也做不到。它们同样是全组织一个值，搬进系统设置，存储、接口、审计与 10.2、10.4 相同。新迁移给 `system_settings` 加列，空值表示用默认值。

| 设置 | 列 | 默认值 | 界面上的单位和范围 |
|---|---|---|---|
| 查询超时 | `query_timeout_seconds` | 60 秒 | 秒，1 到 3600 |
| 默认返回行数 | `query_default_rows` | 1,000 | 行，1 到 100,000，不能大于上限 |
| 返回行数上限 | `query_max_rows` | 10,000 | 行，1 到 100,000 |
| 登录会话有效期 | `session_lifetime_hours` | 168 小时（7 天） | 小时，1 到 8760（一年） |
| 已删除工作空间保留 | `workspace_retention_days` | 30 天 | 天，1 到 3650（十年） |

连接超时（10 秒）仍然写死：只用于「测试连接」，这么久连不上基本是地址或网络有问题。进程停止时的等待（15 秒）也不搬：它属于每个进程，要改时放进启动配置。

| 设置 | 何时读 | 对已有的影响 |
|---|---|---|
| 查询超时 | 每条语句开始时。查询、保存数据集时的校验、解释语句、读字段和读表都用它 | 正在执行的语句按开始时读到的值。导出用自己的超时 |
| 默认行数、上限 | 每次编译查询时 | 行数写在 SQL 里，SQL 是缓存键的一部分，改了以后不会读到按旧行数缓存的结果 |
| 会话有效期 | 登录时，以及每次续期时（同一会话最多五分钟一次） | 见下 |
| 空间保留 | 每次维护任务开始时，以及系统管理的空间列表算永久删除日期时 | 日期按 `deleted_at` 算，不单独存，已删除的空间也按新值 |

**查询超时**：SupaBI 的 HTTP 服务没有写超时，调大不会被自己掐断；前面有反向代理时，代理的超时要一起调大（nginx 的 `proxy_read_timeout` 默认 60 秒），输入框下方写明。

**行数**：

- 全部行都取回实例内存再发给浏览器，翻页只翻取回的行（[图表与仪表盘](chart-dashboard.zh.md) 2.7），所以上限到 100,000 为止。单个结果超过 8 MB 不缓存（[查询 IR](query-ir.zh.md) 6），调大后这样的结果每次都查数据库。输入框下方写明，要更多行用导出。
- 保存时默认行数不能大于上限，按生效的值比较，留空的一方用它的默认值。
- 上限管所有走查询的取数：筛选项（500）、数据集预览和 SQL 工作台（1000）这些自己定了行数的，调低上限后也按上限返回，并照常提示结果不全。
- 小计和合计不用默认行数，直接用上限：它们不带自己的行数，按默认行数截断时分组会缺，也没有提示。
- 写图表的人也要知道这两个值：编辑器的输入框要检查范围、占位文字写默认值，现在写死在前端。`GET /system/settings` 只有系统管理员能调，所以放进已登录时的 `GET /auth/session`。页面打开后值可能过期，只影响提示，服务端照常按最新的值执行；管理员保存系统设置后重新读一次，自己马上看到新值。
- 已保存图表的 `limit` 大于新上限时，图表照常打开，按上限返回（编译时已取两者中较小的）。编辑器的输入框提示超出范围；结果被截断的提示现在只在没写 `limit` 时显示，改为写了 `limit` 但超过上限时也显示，否则作者以为拿到了全部的行。

**会话有效期**：

- 含义不变：这么久没有活动就退出，有活动时续期。
- 调长后，下一次续期起按新值。
- 调短时，保存的同一个事务里把每个会话的 `expires_at` 改为 `LEAST(expires_at, last_seen_at + 新有效期)`：这是安全设置，闲置的会话不能留着旧的到期时间。保存的人刚有过活动，不会被退出。最坏的结果是重新登录，不弹确认。

**空间保留**：

- 调短时保存前先确认，与审计保留相同（10.3）：「保存后一小时内，已删除超过 N 天的工作空间将连同其中的全部内容永久删除，不能恢复。」同时调短审计保留时，确认框里两件事都写。
- 删除工作空间的确认框里写死的「30 天后」改为当前的值：这个列表页只有系统管理员能进，直接读 `GET /system/settings`。

**页面**：「查询缓存」组改名「查询」，放查询超时、默认返回行数、返回行数上限和缓存默认有效期（标签由「默认有效期」改为「缓存默认有效期」）；新增「工作空间」「登录」两组。

### 10.8 MCP 服务

是否允许连接 MCP 客户端（[AI 助手](ai-assistant.zh.md) 第 14 节）全组织一个值，运行时可能要改，所以是系统设置，存储、接口和审计同 10.2、10.4。新增一个迁移给 `system_settings` 加列，空值表示用默认值。

| 设置 | 列 | 默认值 | 界面 |
|---|---|---|---|
| 允许 MCP 客户端 | `mcp_enabled` | 关闭 | 开关，放在新增的「MCP 服务」组 |

- MCP 和 OAuth 端点每次收到请求时读取。关掉后下一个请求立刻被拒绝；授权保留，重新打开后照常可用（[AI 助手](ai-assistant.zh.md) 14.6）。
- 默认关闭：数据会发给用户客户端所用的模型，这个模型不是管理员选的。开关下方的说明写明这一点。
- 打开和关闭都直接保存，不弹确认框：两个方向都不删除任何东西。

### 10.9 AI 助手

AI 助手有两个值原来写死在代码里：对话占到模型上下文多少时压缩（[AI 助手](ai-assistant.zh.md) 第 6 节），和一条回答最多调用几次工具（12.4）。管理员可能想调低来省钱，也可能想调高来回答要查很多次的问题；两者全组织一个值，所以是系统设置，存储、接口和审计同 10.2、10.4。新增一个迁移给 `system_settings` 加列，空值表示用默认值。2026-11-05 定。

| 设置 | 列 | 默认值 | 界面中的单位和范围 |
|---|---|---|---|
| 上下文压缩阈值 | `assistant_compress_percent` | 80% | 可用上下文的百分比，50 到 95 |
| 每个回答的工具调用上限 | `assistant_max_tool_calls` | 60 | 次，0 到 1000，`0` 表示不限制 |

- 两者都在每条回答开始时读取一次。进行中的回答沿用当时读到的值，下一条回答用新值。
- **上下文压缩阈值**和原来写死的 80% 一样管两件事：回答前何时压缩对话较早的部分（第 6 节），回答中何时不再给工具（12.4）。
  - 低于 50% 时，压缩后原样保留的部分（最多可用上下文的四分之一）加上摘要就接近阈值：几乎每条回答都要先压缩，一条回答查一两次就没有工具了。
  - 高于 95% 时，按字数估算留的余量太小，供应商会开始以上下文超长拒绝调用。
  - 压缩模型一段读多少，仍是它自己可用上下文的 80%。这是给估算留的余量，不是何时压缩的选择。
- **每个回答的工具调用上限**：查数、计算、画图都算在内，和原来一样。设为 `0` 时，一条回答在模型不再调用工具、上下文到了上面的阈值、或者用户停止时结束。每一轮都要把整个上下文重新发一遍，所以输入框下方的说明写明次数越多花费越多。上限只用来挡住写错的值。
- 只管 AI 助手。MCP 客户端自己跑循环（[AI 助手](ai-assistant.zh.md) 第 14 节），SupaBI 不数它的调用次数。
- 两者都直接保存，不弹确认框：不删除任何东西。
- **页面**：新增「AI 助手」组，放在「MCP 服务」前面。

## 11. 密钥校验

`secret-key` 加密库里的数据源密码和 AI 供应商的 API 密钥，只能放在启动配置里：和库放在一起，拿到一份数据库备份就能解开全部密码。

各实例的密钥不同，后果最重：B 解不开 A 存的密码，查询失败；B 新存的密码 A 也解不开，两边各存一半，事后很难理清。现在要到用密码时才发现，改为启动时就发现：

- 元数据库里存一个校验值，就是用密钥加密的一段固定文字，放在 `secret_key_check` 表里。整个安装只有一个：密钥属于整个安装，不按组织分。
- `serve` 在迁移之后、启动各角色之前核对，每个角色都核对，因为每个角色都要求 `secret-key`。用当前密钥解得开就继续，解不开就拒绝启动：

  ```
  supabi: secret-key is not the key this database was set up with; start every instance with the same secret-key
  ```

  `migrate` 不用密钥，不核对。
- **还没有校验值时**（新库，或这一版之前建的库）：库里已经有加密的值时，先用当前密钥解开其中一个，解不开同样拒绝启动；解得开，或者库里还没有加密的值，就写入校验值。两个实例第一次同时启动时，只有先写入的生效，后写的一方读出已有的校验值再核对。

**密钥丢了**：以前丢了密钥还能启动，重新填写密码就行；有了校验就启动不了。为此加一个命令：

```bash
supabi clear-secrets --config /etc/supabi/supabi.yaml --yes
```

- 清掉库里全部加密的值（数据源的密码、AI 供应商的 API 密钥）和校验值。数据源和供应商本身保留，由管理员重新填写密码和 API 密钥。之后用新的密钥启动，写入新的校验值。
- 不带 `--yes` 时只列出会清掉几个数据源的密码、几个供应商的 API 密钥，不执行。
- 执行前要停掉所有实例：还在运行的实例拿着旧密钥，会继续用旧密钥存密码。
- 只用 `database-url`，不需要 `secret-key`。

更换密钥（用旧密钥解开、用新密钥重新加密全部值）这一步不做，见 [暂缓事项](../backlog.zh.md)。
