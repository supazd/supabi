# 数据集模型设计（草案 v0）

状态：草案，待讨论。与 [查询 IR](query-ir.zh.md) 配套，IR 中引用的字段、参数都在这里定义。

## 1. 定位

数据集是一张带语义标注的逻辑表：

- 由数据分析师或工程师创建和维护。
- 属于且只属于一个数据源，不存数据，查询时编译下发。
- 图表、仪表盘、AI、数据 API 只依赖数据集，不直接接触物理表。
- 行列权限、缓存策略都挂在数据集上。

## 2. 结构总览

```jsonc
{
  "specVersion": 1,
  "id": "ds_8f3k2m",
  "name": "订单分析",
  "description": "已支付订单，按下单时间统计。退款订单不在此数据集。",
  "datasource": "src_prod_mysql",

  "source": {
    "type": "sql",                       // sql | table
    "sql": "SELECT o.id, o.created_at, o.amount, o.user_id, o.status, r.region_name\nFROM orders o JOIN regions r ON o.region_id = r.id\nWHERE o.dt >= {{start_date}}\n[[ AND r.region_name IN {{regions}} ]]"
  },

  "params": [
    { "name": "start_date", "type": "date", "label": "起始日期",
      "default": { "relative": "today-90d" }, "required": true },
    { "name": "regions", "type": "string", "label": "地区", "multi": true }
  ],

  "fields": [
    // 维度
    { "key": "order_id",   "label": "订单号",   "column": "id",          "type": "string",    "role": "dimension", "hidden": true },
    { "key": "order_date", "label": "下单时间", "column": "created_at",  "type": "timestamp", "role": "dimension" },
    { "key": "region",     "label": "地区",     "column": "region_name", "type": "string",    "role": "dimension",
      "synonyms": ["区域", "大区"] },
    { "key": "status",     "label": "订单状态", "column": "status",      "type": "string",    "role": "dimension" },
    { "key": "user_id",    "label": "用户 ID",  "column": "user_id",     "type": "string",    "role": "dimension" },
    { "key": "amount_tier", "label": "金额档位", "type": "string", "role": "dimension",
      "expr": "CASE WHEN ${amount} >= 1000 THEN '高' WHEN ${amount} >= 100 THEN '中' ELSE '低' END" },

    // 度量
    { "key": "amount",      "label": "订单金额", "column": "amount",  "type": "decimal", "role": "measure",
      "format": { "decimals": 2, "prefix": "¥" } },
    { "key": "paid_amount", "label": "已付金额", "type": "decimal", "role": "measure",
      "expr": "CASE WHEN ${status} = 'paid' THEN ${amount} END", "format": { "decimals": 2, "prefix": "¥" } },
    // 指标
    { "key": "order_count", "label": "订单数",   "type": "integer", "role": "metric", "expr": "COUNT(${order_id})" },
    { "key": "buyers",      "label": "购买人数", "type": "integer", "role": "metric", "expr": "COUNT(DISTINCT ${user_id})" },
    { "key": "arpu",        "label": "客单价",   "type": "decimal", "role": "metric",
      "expr": "SUM(${amount}) / NULLIF(COUNT(DISTINCT ${user_id}), 0)",
      "format": { "decimals": 2, "prefix": "¥" }, "description": "销售额除以购买人数" }
  ],

  "cache": { "ttlSeconds": 300 }
}
```

这是存储和接口中的形式。其中的 `key` 是内部 ID，界面上不出现：使用者看到的是名称（`label`），表达式里写的也是名称，见 5.2 和 6.4。

## 3. 来源 `source`

| `type` | 内容 | 适用 |
|---|---|---|
| `table` | `schema` + `table` | 直接用一张表或视图，无需写 SQL |
| `sql` | 一段 `SELECT` 语句，可含参数 | 需要 join、清洗、预聚合 |

约束：

- 必须是单条只读查询。连接数据源使用只读账号是第一道防线；系统侧只做基础检查（单语句、以 `SELECT` 或 `WITH` 开头）。字符串、带引号的名称和注释里的分号是文字，不算语句结束：数据里常有分号，会用 `=` 或 `LIKE` 去查。
- 来源 SQL 用数据源自己的方言书写，系统不解析、不翻译，编译时作为子查询整体包裹。
- 唯一会去读来源 SQL 的地方是血缘：从中找出 `FROM` 和 `JOIN` 后面的表名，用来在血缘图上画出数据集读了哪些表（`internal/sqlrefs`）。这不是解析，读不出来只是图上少一张表，不影响保存和查询。
- 输出列名必须唯一。

## 4. 参数 `params`

| 属性 | 说明 |
|---|---|
| `name` | 在 SQL 中以 `{{name}}` 引用 |
| `type` | `string` `integer` `decimal` `boolean` `date` `timestamp` |
| `label` | 显示名 |
| `multi` | 为真时接受数组，展开为 `(?, ?, ...)` |
| `default` | 固定值，或 `{ "relative": "today-1d" }` 形式的动态值 |
| `required` | 为真且无默认值时，查询必须传值 |

规则见查询 IR 文档 3.10：参数编译为绑定参数，只能替换值；`[[ ... ]]` 为可选片段；`{{user.xxx}}` 为系统变量。

参数没有可选值列表。下拉里有哪些选项，由用到它的图表各自决定（[图表与仪表盘](chart-dashboard.zh.md) 2.11）。

**什么时候用参数。** 只在筛选器做不到时才用。只为缩小范围的条件（单表的 `dt = {{biz_date}}`、日期范围）不需要参数：把那一列输出出来，在图表里用字段筛选器。筛选条件加在数据集 SQL 外层，数据库会把它推进 SQL 里：2026-10-22 在开发库上用 EXPLAIN 看过，PostgreSQL 上带 join 的明细 SQL 走了时间索引、先按天聚合的 SQL 在聚合前就过滤，ClickHouse 上先聚合的 SQL 用上了主键范围（Trino、StarRocks、Doris 没看过）。查看者还能用上候选、日期范围、全局筛选、联动和下钻。筛选器做不到的情况：

1. **同一个值用在 SQL 的几处。** 两张按 `dt` 分区的快照表 join，两边都要 `dt = 同一天`；外层筛选只作用在输出的那一列上。
2. **必须恰好一个值。** 全量快照分区表的每个 `dt` 都是一整份快照，不选或选了几天，数字就重复累加。参数可以在数据集上规定必填、单值，用这个数据集的图表都得遵守；筛选器是「空表示不限」，要靠每张图的作者自己设好。
3. **条件要在聚合、去重或窗口函数之前生效，那一列又不在输出里。** 「截至某天每个用户的最近一笔订单」写成外层筛选，就成了「最近一笔订单在那天之前的用户」，意思不同，数据库也不会把它推进去。「所选期间下单满 3 次的用户数」、留存和复购也是这样。
4. **值参与计算而不是筛选。** 按截至日算账龄，或者目标值、汇率。

**参数在哪里声明。** 参数跟着 SQL 走，所以在数据探索里声明：SQL 中写了 `{{名称}}`，编辑器右侧就出现「参数」区，列出每个参数，可以改显示名、类型、是否多值、是否必填和默认值；SQL 里没有参数时这个区不出现。参数声明随查询草稿暂存在浏览器，创建数据集或应用回数据集时与 SQL 一起带过去，最终与字段配置一起保存为数据集的一个修订。

- 「参数」区的最上面有一行灰色的说明：「只为缩小数据范围时不需要参数：把这一列输出出来，在图表里用筛选器。」多数人写参数是为了按日期取数，这一行提示改用筛选器；真正需要参数的情况见上文。
- 参数是一个值，不加引号：写 `status = {{status}}`。
- 只有 SQL 本身才会被当成参数来读。写在字符串、带引号的标识符、注释里的 `{{...}}` 和 `[[ ]]` 都是普通文字，和数据库对它们的理解一致：`'{{status}}'` 就是内容为 `{{status}}` 的字符串（它可能正是数据里的一个取值），不是参数，右侧也不会列出它；被注释掉的一行不会再要求给参数填值。这样写错时也看得出来：引号里的占位符不出现在参数区。
- 新出现的参数类型是文本、没有默认值。
- 默认值按类型填写；日期可以填 `today`、`today-1d` 这样的相对值，保存为 `{ "relative": ... }`。填的不是该类型的合法值时提示，并暂不作为默认值。
- 把占位符从 SQL 里删掉，参数就不再声明；在同一次编辑里再写回来，之前设的显示名、类型、多值、必填和默认值还在。
- 名称不合法的占位符（大写、数字开头等）单独列出并说明规则。
- 执行查询、生成数据集、把 SQL 应用回数据集时，参数随 SQL 一起带过去；数据集编辑器不编辑参数。
- 这里编辑类型、是否多值和默认值。SQL 里看不出一个参数是否多值，所以在参数旁勾选「多值」：多值参数在 SQL 中写 `IN {{名称}}`，不加括号，执行时展开为 `(?, ?, ...)`；默认值用逗号分隔填写。取消勾选即恢复为单值。
- 显示名留空时使用 SQL 参数名；设置显示名不改变 SQL 中的占位符。数据集侧同时展示显示名、SQL 参数名、多值和必填标记、默认值。
- 勾选「必填」后，未提供值时仍使用默认值；无默认值或显式提交空值（单值参数的 `null`、多值参数的空列表）时必须提供值，即使参数只在 `[[ ]]` 中使用。取消必填不改变 SQL 语法：在可选片段外的参数仍需值或默认值。
- 单独修改显示名或必填设置也属于 SQL 草稿修改，应用回数据集后才进入数据集草稿，正式保存后生成修订。打开或刷新未修改的参数配置不会因属性顺序不同误报未保存。

## 5. 字段 `fields`

数据集里只有字段这一种东西。每个字段是维度、度量、指标三者之一：

- **维度**用来分组、筛选、排序，例如地区、下单时间。
- **度量**是每一行上的数值，例如订单金额。度量放进图表时会被聚合。
- **指标**是表达式里已经聚合好的数值，例如客单价。指标放进图表时直接使用。

字段的值要么直接取自来源 SQL 的一列，要么由表达式算出，后者称为计算字段（5.3）。指标只能是计算字段。

| 属性 | 必填 | 说明 |
|---|---|---|
| `key` | 是 | 内部 ID，创建时自动生成，之后不可改，界面上不显示。见 5.2 |
| `label` | 是 | 名称，使用者看到和书写的唯一名字，可随时改。见 5.2 |
| `column` | 二选一 | 来源的列名（界面上称「物理字段名」），照来源给出的名字原样保存，不带引号 |
| `expr` | 二选一 | 计算字段的表达式，见 5.3 |
| `type` | 是 | 逻辑类型，见 5.1 |
| `role` | 是 | `dimension`、`measure` 或 `metric`。度量只能是数值字段；数值的维度和度量可以互相转换。见 6 |
| `description` | 否 | 业务含义，同时作为 AI 上下文 |
| `synonyms` | 否 | 同义词，帮助 AI 和搜索匹配 |
| `format` | 否 | 数值和日期的显示格式，见 5.5 |
| `hidden` | 否 | 不在图表字段选择列表中展示，但仍可被已有图表和其他字段的表达式引用；不改变数据权限 |
| `group` | 否 | 字段列表中的分组名 |

### 5.1 逻辑类型

`string` `integer` `decimal` `float` `boolean` `date` `timestamp`

各数据库的物理类型在驱动层映射到这七种。无法映射的类型（数组、JSON、二进制等）v1 按 `string` 处理或标记为不支持。

### 5.2 名称、内部 ID 与物理字段名

`column` 和 `expr` 是两个属性而不是一个，一个字段恰好有其中之一。早先只有 `expr`，靠「长得像不像标识符」来猜它是列名还是表达式：中文列名、带空格或符号的列名都会猜错，被当成表达式原样拼进 SQL。现在不猜：

- `column` 永远是名字，不是 SQL。编译查询时由数据源的方言加引号（PostgreSQL 用双引号，MySQL 和 ClickHouse 用反引号，转义规则也各不相同），所以列名里有什么字符都可以，接入新的数据库时只需要在它的方言里写明怎么加引号。
- `expr` 永远是 SQL，原样使用，哪怕它只是一个名字。表达式要用到某一列时，引用读那一列的字段（`${名称}`），而不是自己写列名和引号。
- 界面和接口都不拼引号。

一个字段有三个名字，各管一件事：

| | 属性 | 例 | 界面上 | 能否修改 | 作用 |
|---|---|---|---|---|---|
| 名称 | `label` | 订单金额 | 显示，可编辑 | 随时改 | 给人看；表达式里按它书写 |
| 物理字段名 | `column` | `amount` | 显示，只读 | 可改为指向另一列（见 5.4） | 字段的值从来源 SQL 的哪一列取 |
| 内部 ID | `key` | `amount` | 不显示 | 不可改 | 图表、仪表盘、查询 IR、其他字段的表达式靠它引用这个字段 |

使用者只需要理解前两个。内部 ID 的存在是为了让另外两个都可以改：改名称不影响任何引用，来源 SQL 改了列名时把字段指向新列即可，图表无感。

**名称的规则**

- 在一个数据集内唯一，维度和度量一起算，比较时忽略大小写和首尾空白。表达式按名称引用，所以不能重名。
- 1 到 100 个字符，不能包含 `{`、`}` 和换行。除此之外不限，可以用中文、空格。
- 检测出的新列，名称默认取列名。

**内部 ID 的规则**

- 格式：小写字母开头，只含小写字母、数字、下划线，最长 63 个字符。它同时用作生成 SQL 中的列别名，所以取各数据库都不需要转义的形式。
- 在数据集内唯一。
- 创建时自动生成：由列名（计算字段则由创建时的名称）转成上述格式；转不出有意义的结果时（例如全是中文）用 `f_` 加一段随机字符。重复时加数字后缀。
- 不保证可读，也不保证与名称或列名一致：名称改了、字段指向了别的列，它都不变。任何逻辑不得依赖它的字面含义。
- 界面上不出现。接口、查询 IR、图表和仪表盘的定义中仍然用它（见 [查询 IR](query-ir.zh.md) 3.11）；直接调用接口的使用者从数据集定义中查到它。

同一列可以对应多个字段（「复制字段」），它们物理字段名相同，名称和内部 ID 不同。常见用途是同一列既当维度又当度量，例如「用户 ID」是维度，复制出的「购买人数」是按去重计数聚合的度量。

### 5.3 计算字段

字段不读某一列时，用 `expr` 写一段表达式，如上例的 `amount_tier`、`paid_amount`、`arpu`。计算字段同样分维度和度量。引用其他字段时写 `${名称}`：

```sql
CASE WHEN ${订单金额} >= 1000 THEN '高' WHEN ${订单金额} >= 100 THEN '中' ELSE '低' END
```

表达式有两种写法，由字段的 `syntax` 区分：

- `"syntax": "standard"`：用平台自己的函数书写，在每种数据库上含义相同，编译查询时才写成该数据库的 SQL。系统读得懂它，保存前就能指出错误，类型也由它推出。新建的计算字段默认用这种写法。见 [标准表达式](expressions.zh.md)。
- 不写 `syntax`：用数据源方言书写，原样拼进 SQL。换数据源时需要改写。

存储时名称被换成内部 ID，即 `${amount}`；编辑时再换回当前的名称。因此被引用的字段改名后，表达式里显示的名称跟着变，不需要手动修改。转换规则见 6.4。

计算字段没有物理字段名，界面上该列显示为「计算字段」，并提供编辑表达式的入口。

### 5.4 字段从哪来

系统不解析 SQL，靠试执行得到列信息：

```sql
SELECT * FROM ( <来源 SQL，参数取默认值> ) t LIMIT 0
```

从返回的列元数据拿到列名和类型，然后：

- 新出现的列：自动生成字段建议，分析师确认或调整。名称取列名，内部 ID 按 5.2 生成，类型取映射结果。数值类型的列归为度量，其余归为维度。列名是 `id` 或以 `_id` 结尾的数值列多半是编号而不是数量，归为维度。
- 已有字段的 `column` 指向的列不存在了：字段保留并标记为失效，不自动删除。分析师可以把它指向另一列（从检测到的列中选），或者删除它。存在失效字段时不能保存。
- 列类型变了：提示确认。

来源 SQL 里的列改了名，表现为「一个字段失效，同时多出一个新列」。把失效字段指向新列、丢弃多出来的字段建议，字段的名称、内部 ID 和所有引用都保持不变。系统不猜测哪一列是改名而来的。

### 5.5 显示格式 `format`

数值和日期字段可以带一个显示格式，决定它的值在表格、透视表的表头、指标卡、坐标轴、图例、提示框和数据标签上怎么写，查看数据和数据集的预览也用它。格式只影响显示，不参与查询。图表可以按列覆盖它，见 [图表与仪表盘](chart-dashboard.zh.md) 2.6。

数值和日期的格式各有自己的属性。

**数值**

```jsonc
"format": {
  "style": "number",   // none | number（省略时）| percent
  "decimals": 2,       // 0–10，省略时最多 2 位、末尾不补 0
  "grouping": true,    // 千分位，默认 true
  "unit": "wan",       // 换算单位，省略表示不换算：auto | K | wan | M | yi | B
  "prefix": "¥",
  "suffix": "元"
}
```

| 属性 | 说明 |
|---|---|
| `style` | `none`（界面上称「无」）什么样式都没有，按查询结果原样显示：不加千分位、不换算单位、不舍入小数，也不能带其他属性。`number` 按下面的属性显示，格式里省略 `style` 时就是它。`percent` 把比例显示为百分数，0.2345 显示为 23.45%；字段里存的必须是比例，已经乘过 100 的值用 `number` 加后缀 `%` |
| `decimals` | 固定的小数位数，不足时补 0。省略时最多保留 2 位，末尾的 0 不写 |
| `grouping` | 是否加千分位。分隔符和小数点的写法随界面语言 |
| `unit` | 先换算再显示。按大小排列依次是 `K`、`wan`、`M`、`yi`、`B`，即千、万、百万、亿、十亿；万、亿写作「万」「亿」，不随界面语言改变。`auto` 按界面语言给每个值各自选单位，中文用万、亿，英文用 K、M、B。`percent` 不能带单位 |
| `prefix` / `suffix` | 前缀和后缀，各最多 16 个字符，不能换行。负号写在前缀之前：`-¥1,234` |

例如 1234567.891 按上面的格式显示为 `¥123.46万元`。

- 精确小数以字符串到达前端，换算单位和百分比时移动小数点，不经过浮点数，不丢精度。舍入一律四舍五入。
- 坐标轴只用格式里的样式、单位、千分位和前后缀，小数位由刻度决定，最多 2 位。
- 格式没有默认值：字段没有格式就是「无」，按原样显示，度量和维度一样。在数据集上选「无」就是不存格式。原样显示时，精确小数保留查询返回的每一位；浮点数只取它能表示的有效数字（最多 15 位），0.1 + 0.2 显示为 0.3，而不是 0.30000000000000004。
- 坐标轴上的刻度要放得下，所以「无」的刻度在一百万以上时按界面语言缩写，如 2.5M。

**日期和时间**

状态：已实现。

```jsonc
"format": {
  "date": "slash",    // 写法：dash（省略时）| slash | chinese
  "time": "minute",   // 只用于 timestamp：second（省略时）| minute | none
  "week": "number"    // 按周分组时：range（省略时）| start | number
}
```

| 属性 | 说明 |
|---|---|
| `date` | 写法。`dash` 用横线；`slash` 用斜线；`chinese` 写成「2026年1月5日」。不随界面语言改变，与「万」「亿」相同 |
| `time` | 没有按粒度分组的时间戳写到哪里。`second` 到秒；`minute` 到分；`none` 只写日期。`date` 字段没有这一项 |
| `week` | 按周分组时怎么写。`range` 写起止日期；`start` 只写第一天；`number` 写第几周 |

写到哪一级由查询的粒度决定：维度的 `grain`（[查询 IR](query-ir.zh.md) 3.4）随结果的列返回（查询 IR 第 4 节）：

| 粒度 | `dash` | `slash` | `chinese` |
|---|---|---|---|
| 年 | 2026 | 2026 | 2026年 |
| 季度 | 2026 Q1 | 2026 Q1 | 2026年第1季度 |
| 月 | 2026-01 | 2026/01 | 2026年1月 |
| 日，没有粒度的 `date` | 2026-01-05 | 2026/01/05 | 2026年1月5日 |
| 小时 | 2026-01-05 13:00 | 2026/01/05 13:00 | 2026年1月5日 13:00 |
| 分钟 | 2026-01-05 13:45 | 2026/01/05 13:45 | 2026年1月5日 13:45 |
| 没有粒度的 `timestamp` | 2026-01-05 13:45:12 | 2026/01/05 13:45:12 | 2026年1月5日 13:45:12 |

按周分组时：

| `week` | `dash` | `slash` | `chinese` |
|---|---|---|---|
| `range` | 2026-01-05 ~ 01-11 | 2026/01/05 ~ 01/11 | 2026年1月5日 ~ 1月11日 |
| `start` | 2026-01-05 | 2026/01/05 | 2026年1月5日 |
| `number` | 2026-W02 | 2026/W02 | 2026年第2周 |

- `time` 只管没有分组的时间戳，例如明细表里的时间、按最早或最晚聚合的时间。按小时、分钟分组时照粒度写，不看 `time`。
- 起止日期的终点总写月和日，跨年时也写年：`2025-12-29 ~ 2026-01-04`。
- 第几周按工作空间的「每周起始日」和「第一周」来数（[架构总览](architecture.zh.md) 10.2）。前面的年份是这一周所属的年，不一定是它第一天所在的年：2025-12-29 开始的一周，按「至少 4 天在当年」是 2026-W01。周号补足两位。季度的 Q 和周的 W 不随界面语言改变。
- 没有格式时按默认值写：横线、到秒、起止日期，所以按月分组的值不再写成这个月的第一天。日期没有「无」：原样写出来的 `2026-01-01` 看不出是一个月。在数据集上三项都选默认值就是不存格式。
- 值已经是查询时区的当地时间（[架构总览](architecture.zh.md) 10.2），显示时不再换算。
- 用表达式截断的日期（如 `DATE_TRUNC('month', ${下单日期})`）不带粒度，按日写。
- 排序、联动和筛选用的都是原值。写出来相同的两个值仍是两个分类，例如只写日期时同一天的两个时间。

**共同的规则**

- 只有数值（`integer`、`decimal`、`float`）和日期（`date`、`timestamp`）字段可以带格式，而且属性要与类型相符：数值字段只能有数值的属性，日期字段只能有日期的属性，`date` 字段不能有 `time`。其他类型的字段不能带格式。不相符时保存拒绝。
- 在界面上改字段的类型时，新类型用不上的格式一并清除：数值与日期互换、改成其他类型时清除整个格式，`timestamp` 改成 `date` 时去掉 `time`。
- 格式随查询结果的列返回（见 [查询 IR](query-ir.zh.md) 4）：维度、指标和按求和、平均、最小、最大聚合的度量带字段的格式；计数和去重计数不带，订单金额的计数不是金额，下单日期的计数也不是日期。
- 数据探索显示 SQL 的原始结果，不经过数据集，没有格式。导出写原始值，见 [导出设计](exports.zh.md) 2.3。
- 按条件变色、负数加括号尚未支持。

## 6. 维度与度量

`role` 决定字段默认出现在哪一边，以及放进图表时怎么用。它只是字段的一个属性，数值的维度和度量可以随时互相转换；被其他字段的表达式引用、或被图表使用的字段，转换前需确认影响（见 8）。

数值有三种，区别在于聚合是谁做的：

| | `role` | 例 | 来源 | 聚合 | 可加 |
|---|---|---|---|---|---|
| 列度量 | `measure` | 订单金额 | 列名 `amount` | 图表里选聚合方式，拖进去时是求和 | 由聚合方式决定 |
| 行级计算度量 | `measure` | 已付金额 | 行级表达式 `CASE WHEN ... END` | 同上 | 同上 |
| 指标 | `metric` | 客单价 | 含聚合函数的表达式 `SUM(...) / COUNT(DISTINCT ...)` | 表达式自己做，系统不再套聚合 | 否 |

维度和度量是行级的：每一行有一个值。指标不是。

图表编辑器里放数值的位置也叫「指标」：指标直接使用；度量和维度拖进去时带上一种聚合方式，成为这张图自己的指标。聚合方式只写在图表里，数据集不规定它：度量拖进去时是求和，维度是去重计数，之后可以在图表里换。

### 6.1 聚合方式

度量只能是数值字段，非数值字段只能是维度。度量的意思是「每一行上的一个数，放进图表时要被聚合」，而对文本、日期求和没有意义。

聚合方式取值：`sum` `avg` `min` `max` `count` `count_distinct`，写在查询里（见 [查询 IR](query-ir.zh.md) 3.5）。数值类型的字段六种都可用；其他类型只能用 `count` `count_distinct` `min` `max`。维度也可以被聚合，例如对「用户 ID」做去重计数，不必先在数据集里建什么。

一个数只有一种正确的算法时，例如订单数、购买人数、单价的平均，把它写成指标（6.2），而不是指望每张图表都选对聚合方式：指标的聚合写在它自己的表达式里，任何图表用它都一样。

需要带条件的度量时，写成行级计算度量：上例的「已付金额」对不满足条件的行给出空值，求和时自然被忽略。

`sum`、`count` 是可加的，`avg`、`count_distinct` 不可加。系统据此判断能否做前端汇总、预聚合和缓存复用。

### 6.2 指标 `metric`

比率、加权平均这类数值不能由「先算每行、再聚合」得到，表达式里要自己写聚合函数：

```sql
SUM(${订单金额}) / NULLIF(COUNT(DISTINCT ${用户 ID}), 0)
```

这样的字段的 `role` 是 `metric`：

- 图表里不能再对它指定聚合方式。
- 只能出现在查询的度量位置和 `having` 中，不能用来分组、筛选明细行，也不出现在明细模式的列里。
- 一律视为不可加。
- 类型为时间的指标，结果由系统换算成查询时区的本地时间（见 [架构](architecture.zh.md) 10.2）。表达式里不要自己换算时区，否则会换算两次。

系统不解析表达式，一个字段是度量还是指标由创建者声明。声明错了会在保存时的表达式试执行中被数据库拒绝（见 8）：表达式里有聚合函数却声明为度量的，在分组查询里报聚合错误；表达式没有聚合却声明为指标的，报「必须出现在 GROUP BY 中」一类的错误。

### 6.3 表达式中引用字段的展开规则

- 引用一个行级字段（维度、度量）：展开为它的行级表达式，**不带聚合**。所以在指标里要写 `SUM(${订单金额})`，而不是只写 `${订单金额}`。
- 引用一个指标：展开为它的表达式，外面加括号。只有指标可以这样引用，例如 `${客单价} * 100`。
- 行级字段不能引用指标。

### 6.4 `${...}` 引用

表达式中引用其他字段统一用 `${...}`。它有两种形式，内容相同，只是花括号里写的东西不同：

| | 花括号里是 | 例 | 出现在 |
|---|---|---|---|
| 书写形式 | 名称 | `SUM(${订单金额}) / NULLIF(COUNT(DISTINCT ${用户 ID}), 0)` | 数据集编辑界面 |
| 存储形式 | 内部 ID | `SUM(${amount}) / NULLIF(COUNT(DISTINCT ${user_id}), 0)` | 数据库、接口 |

两者的转换由编辑界面完成，接口只接受和返回存储形式：

- 打开时：把每个 `${内部 ID}` 换成该字段当前的名称。
- 保存时：把每个 `${名称}` 换成对应的内部 ID，匹配时忽略大小写和首尾空白。找不到对应字段的名称视为错误，指出是哪个表达式里的哪个名称，不保存。
- 名称不含 `{`、`}`，所以书写形式没有歧义。

没有采用 `[名称]` 的写法：方括号在 ClickHouse、PostgreSQL 中是数组字面量和下标的语法，而表达式可以用数据源方言写，两者会冲突。

编译查询时，原生表达式对存储形式做文本替换，标准表达式按语法树输出。这套引用的作用：

- **解耦**：来源 SQL 改了列名，只需把对应字段指向新列，引用它的计算字段不用动；字段改了名称，存储的表达式不变。
- **依赖可知**：不解析 SQL 也能知道谁依赖谁，用于影响分析和循环引用检测。被其他字段引用的字段不能删除，需先解除引用。

表达式里直接写原始列名在技术上也能执行，但系统无法感知这种依赖，不推荐。

## 8. 保存时的校验

1. 结构校验：JSON Schema；内部 ID 的格式与唯一性；名称的格式与唯一性（5.2）；显示格式的取值合法，只出现在数值和日期字段上，且属性与字段类型相符（5.5）；`${...}` 引用的目标存在；无循环引用；度量是数值字段（6.1）；行级字段没有引用指标（6.3）。
2. 参数校验：SQL 中的 `{{name}}` 都已声明；`[[ ]]` 配对正确。
3. 来源试执行：`LIMIT 0` 获取列信息，对比字段映射（见 5.4）。
4. 表达式试执行：由数据库检查表达式的语法和类型，分两次 `LIMIT 0` 查询。一次不分组，选出所有行级字段；一次计算所有度量和指标，度量求和、指标按表达式本身。度量和指标声明错了的字段会在这里被数据库拒绝。试执行时不把时间换算成查询时区，数据库报的是字段本来的类型：声明为时间、实际是日期或文本的字段也在这里被拒绝。
5. 影响分析：与上一版本对比，找出被删除、类型变更、`role` 变更的字段，以及被删除或变更的参数，列出引用它们的图表。有受影响的图表时需要确认才能保存。

影响分析通过 `POST /datasets/{id}/impact` 读取当前修订及引用定义，不执行数据查询。字段引用包括图表查询、筛选、同环比时间字段、动态位置的全部选项、下钻的各层（[图表与仪表盘](chart-dashboard.zh.md) 2.10），以及计算字段的间接依赖；仪表盘全局筛选和联动单独检查，不能只靠图表的查询字段判断。参数删除、类型或多选变化，提示用到这个参数的图表：图表的参数筛选器和 `query.params` 都算（[图表与仪表盘](chart-dashboard.zh.md) 2.11）；原本不传值也能运行、现在必须传值的参数，提示该数据集的所有图表。必填性同时考虑 `required` 和 SQL 中的位置：新增 `[[ ]]` 外的无默认值占位符、把无默认值参数移出可选片段、清除必需参数的默认值均需确认；多值参数的空默认列表视为无值。新增带有效默认值的参数、修改有效默认值，或清除仅在可选片段内使用且未设 `required` 的参数默认值，不因此触发确认。

把已有参数改为 `required`，或将它移出可选片段，也需确认：查看者可能清空图表上的参数控件（单值提交 `null`，多值提交空数组），此时不会使用参数默认值，收紧必填约束会使原查询失败。

编辑器携带打开时的 `expectedRevision`，避免覆盖另一标签页或其他人的修改。更新和影响分析接口均要求此字段为正整数，省略或无效时返回 `revision_required`。有受影响资源时显示名称、变更原因和所在仪表盘，链接在新的浏览器标签页打开。确认后保存携带 `impactToken`；该令牌绑定拟保存的定义、原修订及相关资源定义。后端在保存事务内锁定并重新分析，修订不一致返回与图表、仪表盘相同的 `resource_revision_conflict`，影响确认过期返回 `dataset_impact_required`。权限规则引用的字段仍禁止删除，确认影响不能绕过权限校验。新增字段、修改显示名、格式或列映射等不触发确认。

版本冲突后保留草稿，不刷新后自动重试。统一的差异窗口比较编辑基线、当前草稿和重新读取的最新内容。名称、描述独立处理；数据源、SQL、参数及其他数据集设置仍作为一组。字段以内部 `key` 对应，不以显示名或数组位置匹配：

- 同一字段的 `label`、`description`、`format`、`hidden` 分别比较。不同字段、不同属性的修改可以同时保留；单方修改和双方相同的修改自动合并，双方对同一属性作出不同修改时才逐项选择。清空属性也是修改；`format` 整体选择，不拼接其内部设置。
- 类型、角色、公式、表达式语言、来源列或其他字段定义发生变化时，该字段按整体比较。仅一方变更可保留，双方内容不同则选一方，避免把新类型与旧格式等不兼容的配置拼接起来。
- 不同内部 ID 的新增字段可同时保留；同一 ID 新增但定义不同需要选择。一方删除、另一方未改则删除；一方删除、另一方修改需要明确选择。缺失或重复 ID 时退回完整字段列表选择。
- 字段顺序比较双方都保留的原有字段，新增、删除本身不产生顺序冲突。仅一方调整顺序就采用该顺序，双方不同的调整需选择；另一方新增或选择保留的字段插入其下一个仍在列表中的字段之前，无后续字段时追加。

窗口仅显示变化的项，并区分自动合并与待选择的冲突。合并结果仍需确认应用。关闭窗口不改动草稿或基线；应用后以服务器最新修订及内容为基线，合并内容成为未保存草稿，可继续调整。下一次保存仍执行定义校验、影响分析和确认，不因合并成功而绕过字段引用、参数、数据源等检查；期间发生的新修改仍会触发冲突。读取最新内容失败或资源已删除时保留草稿，不能跳过版本检查。

比较窗口打开期间若收到 SQL 回传、字段检测结果等新的草稿修改，旧合并方案立即停止应用。点击「重新比较」后使用当前草稿重新读取服务器内容，并清空旧选择；重新确认后才能应用，避免旧快照覆盖后到的修改。重新比较失败时仍保留草稿与原编辑基线，支持重试。


校验失败时给使用者的信息一律用名称指代字段，不出现内部 ID。

第 3、4 步依赖数据源可达。数据源不可达时允许保存为未校验状态，但不能被新图表引用。

## 9. 变更与版本

- 每次保存生成一个不可变修订快照，包括名称、描述、数据源 ID 与当时的显示名，以及包含 SQL、参数、字段和格式的完整定义。修改时间和修改人随修订记录。
- 编辑器的「修订历史」按版本倒序分页展示记录，可查看每个版本的完整配置，任选两个版本比较。SQL 逐行标记增删，字段按内部 ID、参数按名称比较属性变更，改名不会被误认为删除再新增。
- 「恢复为草稿」只替换当前数据集编辑内容；已有未保存修改时先确认。草稿仍以编辑器打开或上次保存时的修订为基线，保存继续执行正常校验、权限字段检查、影响分析及并发冲突检查，成功后生成新的修订，不改写旧历史。旧数据源已删除时仍能查看快照，需重新选择可用数据源才能保存。
- 数据权限和文件夹归属由独立接口维护，不属于定义修订；恢复不会改动它们。历史接口只向当前工作空间的数据开发和管理员开放。
- 非破坏性变更（改取数逻辑、新增字段、改名称、改列映射）直接生效。
- 破坏性变更（删除字段或参数、改类型、改 `role`、把可选参数改为必填）触发影响分析。
- 图表引用的字段已不存在时，图表显示明确的错误信息并指出缺失的是哪个字段，不影响同一仪表盘的其他图表。字段已被删除，名称取自数据集最近一个仍包含它的修订；查不到时退回内部 ID。普通用户只有在当前列权限允许查看该历史字段及其依赖时才获得名称。

## 10. 存储

- `dataset` 表：ID、工作空间、数据源、名称、当前修订号、完整定义（JSONB）、校验状态、创建人和时间。
- `dataset_revisions` 表：每个修订的完整定义、名称、描述、数据源 ID 与显示名、修改人和修改时间。
- 引用索引表：记录每个图表引用了哪个数据集的哪些内部 ID，在图表保存时维护，供影响分析查询。

## 11. v1 明确不做

| 项 | 原因 |
|---|---|
| 数据集之间的关联 | 轻量语义层的既定取舍，join 写在来源 SQL 里 |
| 基于另一个数据集建数据集 | 增加编译和权限的复杂度 |
| 物化（把结果落成表） | 属于性能优化，依赖 scheduler，后期做 |
| 维度层级（省 → 市 → 区） | 下钻的层级配在图表里（[图表与仪表盘](chart-dashboard.zh.md) 2.10），数据集的修改不会让下游图表的下钻悄悄失效；多张图表反复配同一套层级时，再在数据集里定义，作为编辑器里的预设 |
| 维度分组（把取值归并成几档） | 可以用 `CASE WHEN` 写成计算字段，专门的界面后续再做 |
| 把原生表达式和来源 SQL 翻译到另一种方言 | 没有 SQL 解析器。计算字段改用 [标准表达式](expressions.zh.md) 书写后不需要翻译 |

## 12. 已决定

1. **v1 不做草稿/发布状态**，保存即生效，靠影响分析和修订回滚兜底。草稿态已记入 [暂缓事项](../backlog.zh.md)。
2. **只读靠数据源账号权限保证**，系统只做基础检查，不引入 SQL 解析器。数据源配置界面需明确提示使用只读账号。
3. **内部 ID 不对使用者显示**。使用者只面对名称和物理字段名，表达式按名称书写，见 5.2 和 6.4。考虑过两个替代方案：
   - 把内部 ID 作为「标识」显示出来（最初的做法）：它由列名生成且不可改，在使用者看来只是列名的另一种写法，多一个要理解的概念却看不到好处。
   - 去掉内部 ID，直接以来源 SQL 的列名作为字段的身份：计算字段没有列名，仍需另起一个不可改的名字；同一列不能对应多个字段；列改名只能靠在 SQL 里写别名兜底，`table` 类型的来源没有这个办法。
4. **只有字段，分维度和度量，没有单独的指标**。去掉了 `measures` 列表，字段增加 `role` 和 `aggregated`。原来的三种指标分别变成：
   - 结构化指标（对一个字段做一种聚合）：一个度量字段，聚合方式当时写在 `defaultAgg`，后来改由图表决定，见第 6 条。
   - 带过滤条件的结构化指标：一个行级计算度量，条件写进 `CASE WHEN`。
   - 表达式指标：一个已聚合的计算度量。原来在表达式里引用结构化指标（`${revenue}`）会带上聚合，现在引用的是行级的字段，聚合函数要写出来（`SUM(${订单金额})`）。

   这样做的理由：少一个概念，数值列检测出来就能直接用，不必先为它建一条指标；可加性仍然可知，因为除了已聚合的计算度量，聚合方式都是结构化的。代价是带条件的度量从与方言无关的结构化过滤变成了用方言写的表达式；计算字段本来就用方言书写，这一点不构成新的限制。

   产品尚未发布，这是一次不兼容的修改：`specVersion` 仍为 1，不提供迁移，开发环境用 `make dev-reset` 清空后重建。

   后来把「已聚合的计算度量」从 `role: "measure"` 加 `aggregated: true` 改成了独立的 `role: "metric"`，界面上称为指标。原因：一个字段是什么只在一处说明，不再有「维度却标了已聚合」这类要靠校验排除的组合；界面、存储和使用者的说法一致；AI 生成或理解数据集定义时，三选一的枚举比「枚举加布尔值」更不容易写错。这仍然不是上面被去掉的那种「指标」：它是字段的一种，不是另一张列表，度量也照旧不必先建指标就能用。`specVersion` 仍为 1。
5. **显示格式是结构化的对象，不是格式串**。考虑过 Excel 式的格式串（`#,##0.00`），它熟悉、紧凑，但要自己实现一个解析器；写「万」「亿」很别扭（`0.0,,"万"`）；界面要么让人手写格式串，要么在表单和格式串之间来回转换。对象的每个属性直接对应浏览器的 `Intl.NumberFormat`，后端校验只是检查几个枚举，界面就是一组表单控件，AI 生成时也不容易写错。`specVersion` 仍为 1。日期也不用 `yyyy-MM-dd` 式的格式串：同一个字段按月、按日分组时要写到不同的级别，一个格式串只能写死一级，按月分组时 `yyyy-MM-dd` 又会写出这个月的第一天。所以格式只选写法，写到哪一级由粒度决定。
6. **数据集不规定聚合方式**。字段曾经有 `defaultAgg`：度量放进图表时按它聚合，图表可以选「默认」跟随它。后来去掉了，聚合方式只写在图表里，度量拖进图表时是求和。理由：
   - 一个数只有一种正确算法时，那是指标的事，指标的聚合写在自己的表达式里；默认聚合与指标的职责重叠。
   - 跟随默认的图表会在数据集改默认聚合时悄悄改变结果，图表的作者并不知道；聚合写在图表里，结果是确定的。
   - 少一个概念：数据集上没有「默认聚合」一列，图表上没有「默认」标记。

   同时规定度量只能是数值字段：文本、日期上能做的只有计数和最值，它们作为维度被聚合即可。代价是平均价格、比率这类不能求和的数值，拖进图表时默认求和是错的，要么在图表里改聚合方式，要么写成指标。`specVersion` 仍为 1。
