# 标准表达式

计算字段的表达式有两种写法：平台自己的函数（标准表达式），或数据源自己的 SQL（原生表达式）。本文说明标准表达式的语言、语义和实现。字段模型见 [数据集](dataset.zh.md)。

## 1. 定位

原生表达式绑定在一种数据库上：换数据源时，每个计算字段都要改写；系统读不懂它，类型要人来选，错误要等数据库执行才知道。

标准表达式是一门由平台定义的小语言，只包含运算符和一组函数。同一个表达式在每种数据库上含义相同，编译查询时才写成该数据库的 SQL。因此：

- 换数据源时不用改。
- 系统读得懂：保存前就能指出错误和它的位置，结果类型由表达式推断。
- 写的人不需要知道背后是哪种数据库。

它不解析数据库的 SQL。[架构](architecture.zh.md) 里“设计上绕开多方言 SQL 解析”的约束不变：这里解析的是平台自己定义的语法。

来源 SQL 仍然用数据源方言书写。来源是手写 SQL 的数据集换数据源时，SQL 还是要改；标准表达式省掉的是计算字段那一部分。

## 2. 两种写法

字段的 `syntax` 说明 `expr` 用哪种语言：

| `syntax` | 含义 |
|---|---|
| `"standard"` | 标准表达式 |
| 不写 | 原生表达式，原样拼进 SQL，只把 `${内部 ID}` 换成被引用字段的 SQL。整个表达式外面加一层括号，顶层的 `OR` 就不会把与这个字段比较或用 AND 连接的条件（包括行权限条件）吞进去 |

界面上新建的计算字段默认用标准表达式。引入标准表达式之前创建的字段都没有 `syntax`，按原生处理，不做自动转换。

两种字段可以互相引用。

一个表达式不能混用两种写法：同名函数（`ROUND`、`SUBSTR`）在平台和数据库里的参数或语义可能不同，混在一起就无法判断指的是哪一个。标准表达式里确实需要一段数据库自己的 SQL 时，用 `NATIVE()` 明确地圈出来，见第 6 节。

## 3. 语言

```
IF(${订单金额} >= 1000, '大单', '小单')
SUM(${订单金额}) / COUNT_DISTINCT(${用户 ID})
CASE WHEN ${状态} = 'paid' AND ${备注} IS NOT NULL THEN 1 ELSE 0 END
```

| 成分 | 写法 |
|---|---|
| 字段 | `${名称}`，存储时换成 `${内部 ID}`，规则同 [数据集](dataset.zh.md) 6.4 |
| 文本 | 单引号，引号本身写两个：`'it''s'` |
| 数字 | `12`、`3.5` |
| 其他字面量 | `TRUE`、`FALSE`、`NULL` |
| 算术 | `+` `-` `*` `/` `%`，一元 `-` |
| 比较 | `=` `<>`（或 `!=`）`<` `<=` `>` `>=` |
| 逻辑 | `AND` `OR` `NOT` |
| 条件 | `x IN (a, b)`、`x BETWEEN a AND b`、`x IS NULL`，及各自的 `NOT` 形式 |
| 分支 | `CASE WHEN 条件 THEN 值 … ELSE 值 END`，或 `CASE x WHEN 值 THEN 值 … END` |
| 函数 | `名称(参数, …)` |

关键字和函数名不区分大小写。没有双引号和反引号：文本只用单引号，字段只用 `${}`。裸写的词不是合法的表达式，这样把列名直接写进表达式的错误在解析时就能指出。

### 3.1 类型

值的类型就是字段的七种逻辑类型。检查时：

- 算术只用于数值。整数与小数运算得小数，有浮点数参与得浮点数。
- 比较、`IN`、`BETWEEN`、`CASE` 和 `IF` 的各个分支，两边要是同一类型，数值之间可以混用。
- 需要日期的地方写了 `'2026-01-31'` 这样的文本字面量，按日期读。
- `NULL` 和 `NATIVE()` 的类型未知，可以出现在任何位置。

表达式的类型由此推出。字段声明的 `type` 要与它一致（数值类型之间视为一致），否则不能保存。表达式里有 `NATIVE()` 而推不出类型时，以声明的为准。

### 3.2 按行与聚合

聚合函数把一组行变成一个值。检查时：

- 维度和度量的表达式不能聚合，也不能引用指标。
- 指标的表达式必须聚合。
- 按行的值不能和聚合后的值直接放在一起：`SUM(${金额}) / ${数量}` 是错的。
- 聚合不能嵌套。

## 4. 语义

各数据库不一致的地方，平台定下一种，由方言各自实现。

| 事项 | 约定 |
|---|---|
| 除法 | 不截断：两个整数相除也保留小数。除数为 0 得空值，不报错 |
| 取余 | 只用于整数。除数为 0 得空值 |
| `CONCAT` | 任何一段为空，结果为空。只接受文本，数字和日期先用 `TO_STRING` |
| 文本长度和位置 | 按字符计，一个汉字算一个。位置从 1 开始 |
| `ROUND` | 小数按四舍五入。位数必须直接写成整数 |
| `TO_INTEGER` | 丢掉小数部分，不四舍五入 |
| 时间取日期或取某一部分 | 先换算到查询所用的时区，再取。无论列存的是不带时区的时间还是时刻，结果相同 |
| `TODAY()` | 查询所用时区的当天，由服务端在编译时算出并写成字面量 |
| `WEEKDAY` | 周一为 1，周日为 7 |
| `DATE_TRUNC` 的 `'week'` | 一周从哪天开始按工作空间的设置 |
| `DATE_ADD` | 季度按 3 个月、周按 7 天。月末溢出时取该月最后一天 |
| `DATE_DIFF` | 从开始到结束跨过了多少个单位的边界：1 月 31 日到 2 月 1 日相差 1 个月 |
| 两个时间比较 | 按时刻比较，与各自的存储方式无关 |

不保证一致的地方：

- 文本比较是否区分大小写，由数据库的排序规则决定。
- 布尔类型的表达式，在没有布尔类型的数据库（MySQL、StarRocks、Doris）和 ClickHouse 上返回 0 或 1。
- `TO_STRING` 一个小数时显示几位。
- 浮点数恰好在两个值正中间时 `ROUND` 往哪边取。

## 5. 函数

### 5.1 核心函数

每种数据库都支持，结果一致。

| 分类 | 函数 |
|---|---|
| 聚合 | `SUM` `AVG` `MIN` `MAX` `COUNT`（无参数或 `*` 时数行数）`COUNT_DISTINCT`（也可写成 `COUNT(DISTINCT x)`） |
| 条件与空值 | `IF` `COALESCE` `IFNULL` `NULLIF` |
| 数值 | `ABS` `ROUND` `FLOOR` `CEIL` `MOD` `POWER` `SQRT` |
| 文本 | `CONCAT` `UPPER` `LOWER` `TRIM` `LENGTH` `SUBSTR` `LEFT` `RIGHT` `REPLACE` `CONTAINS` `STARTS_WITH` `ENDS_WITH` |
| 日期时间 | `TODAY` `DATE` `YEAR` `QUARTER` `MONTH` `DAY` `HOUR` `MINUTE` `WEEKDAY` `DATE_TRUNC` `DATE_ADD` `DATE_DIFF` |
| 类型转换 | `TO_STRING` `TO_INTEGER` `TO_DECIMAL` `TO_FLOAT` |

每个函数的参数和说明在界面的函数面板里，文案在 `web/apps/app/src/i18n/functions.*.ts`。

### 5.2 扩展函数

不是每种数据库都有，有的也不保证每个细节一致。用了扩展函数的字段不保证能换数据源。

| 函数 | 说明 | 不支持的数据库 |
|---|---|---|
| `MEDIAN` | 中位数。各数据库算法略有出入 | MySQL |
| `REGEXP_MATCH` | 正则匹配。各数据库的正则语法不完全相同 | 无 |

数据源不支持的函数：

- 不出现在函数面板和补全里（`GET /datasources/{id}/functions` 只返回可用的）。
- 写了它的表达式在检查和保存时报 `function_unavailable`，指出是哪个函数。
- 换数据源后，用了它的字段在查询编译时报同样的错误，而不是由数据库报一条看不懂的错。

## 6. `NATIVE()`

```
IF(${金额} > 100, NATIVE('json_extract({0}, ''$.tier'')', ${扩展信息}), '小单')
```

第一个参数是直接写出的 SQL 文本，其中 `{0}`、`{1}` 代表后面的参数。它原样输出，系统不检查，类型未知。

表达式里有 `NATIVE()` 时，系统知道这个字段含有不可移植的片段，检查接口返回 `native: true`，界面上有提示。

## 7. 实现

```
internal/expr       解析、类型检查、写成 SQL
internal/dialect    各数据库怎么写每个基本函数（functions.go）
internal/dataset    校验时读表达式；Spec.FieldSQL 按 syntax 分两条路
internal/query      编译时提供方言、时区、每周起始日和当天日期
```

1. **解析**：手写的递归下降解析器，得到语法树。每个节点记着它在表达式里的位置。
2. **检查**（`expr.Check`）：推出类型、是否聚合、引用了哪些字段、用了哪些函数。不依赖数据库，所以 `Spec.Validate` 里就做。
3. **输出**（`Checked.SQL`）：遍历语法树，把平台函数拆成方言的基本函数再写出来。

平台函数和方言的基本函数不是一一对应的。`DATE_DIFF('month', a, b)` 被拆成年份差乘 12 加月份差，方言只需要会取年和取月；`IF` 直接写成 `CASE WHEN`，不需要方言参与。方言接口因此保持得小：

```go
type Functions interface {
    Function(name string) (FunctionWriter, bool)
}
```

`standardFunctions` 是多数数据库的写法，各方言只覆盖有差异的。写法为 `nil` 表示这种数据库没有办法计算。函数目录里每个平台函数声明它依赖哪些基本函数（`needs`），由此得出它在某种数据库上是否可用。

### 7.1 增加一个函数

1. 在 `internal/expr/functions.go` 的目录里加一项：参数类型、结果类型、依赖的基本函数。
2. 在 `internal/expr/render.go` 里说明怎么用基本函数写出它。直接对应一个基本函数的，在 `direct` 表里加一行。
3. 需要新的基本函数时，在 `internal/dialect/functions.go` 的 `standardFunctions` 里加上，并为写法不同的方言覆盖。
4. 在 `internal/conformance/expressions.go` 里加用例：给出它在测试数据五行上的结果。每种数据库都要得到同样的结果。
5. 在两种语言的 `functions.*.ts` 里加说明。

语义一旦有人用了就很难改，所以第 4 步的期望值要先定下来。

### 7.2 接入一种新数据库

实现方言的 `Function`：从 `standardFunctions` 出发，覆盖写法不同的。然后跑一致性测试，`expressions` 一组不通过的就是需要覆盖的。

### 7.3 接口

| 接口 | 用途 |
|---|---|
| `GET /datasources/{id}/functions` | 这个数据源可用的函数 |
| `POST /datasources/{id}/check-expression` | 读一个书写形式的表达式（字段用名称引用），返回类型或错误及其位置 |

检查接口不访问数据库。编辑界面在输入时调用它，用返回的类型填写字段类型，用返回的位置标出错误。

## 8. 没有做的

| 项 | 说明 |
|---|---|
| 窗口函数 | 涉及分组和排序的语义，与查询 IR 的派生计算一起考虑 |
| 时间字面量和时间格式化 | 各数据库的格式串不同，需要先定一套平台的格式写法 |
| 数组、JSON、地理函数 | 各数据库差异大，先用 `NATIVE()` |
| `GREATEST` / `LEAST` | 遇到空值时各数据库行为不同，需要先定语义 |
| 把已有的原生表达式自动转成标准表达式 | 需要解析各方言的 SQL |
| 图表级的自由表达式指标 | 可以直接复用这门语言，见 [暂缓事项](../backlog.zh.md) |
