# 权限与工作空间模型（草案 v0）

状态：草案，待讨论。本文决定元数据库中几乎每张表的归属和可见性字段，需要在建表之前确定。

## 1. 要回答的问题

1. 谁（主体）
2. 能对什么（资源）
3. 做什么（动作）
4. 看到哪些数据（行与列）

前三个是**资源权限**，决定能不能打开、编辑某个仪表盘或数据集。第四个是**数据权限**，决定打开之后查出来的数据范围。两者独立：能看同一个仪表盘的两个人，看到的数据可以不同。

## 2. 层级结构

```
实例
 └─ 组织                租户边界：用户、用户组、认证配置属于某一个组织
     └─ 工作空间        资源边界：数据源、数据集、图表、仪表盘属于某一个工作空间
         ├─ 成员        用户或用户组，在本空间内有一个角色
         ├─ 用户属性    本空间自定义的数据权限属性及其对用户、用户组的赋值
         ├─ 数据源
         └─ 文件夹      可嵌套；仪表盘、图表、数据集各有一棵自己的文件夹树
             ├─ 仪表盘
             ├─ 图表
             └─ 数据集
```

- **实例**：一次部署。
- **组织**：租户。不同组织之间账号、用户组、资源完全隔离，同一个邮箱在两个组织是两个账号。v1 只有一个自动创建的默认组织，界面上不出现「组织」概念；多组织（多租户）以后再做。
- **工作空间**：资源的隔离边界，对应一个团队或一个业务线。资源不能跨工作空间引用。
- **文件夹**：组织仪表盘、图表和数据集，三者各有一棵树，一个文件夹只放一种资源。文件夹是权限的继承节点（继承尚未实现，目前文件夹只用于整理）。数据源不放进文件夹，直接属于工作空间。整理文件夹需要数据开发角色。

所有表都带 `org_id`，资源表另带 `workspace_id`，所有查询都按它们过滤。现在就加 `org_id` 是因为事后往每张表补隔离字段的代价很高。

### 2.1 全局管理与空间配置

全局指当前组织，v1 的单组织界面以「系统管理」呈现。用户和用户组只有全局一份，工作空间引用它们并分配空间角色；不建立空间自己的用户组。

| 内容 | 归属 | 维护者 |
|---|---|---|
| 用户账号、账号资料、启停状态、密码、系统管理员身份 | 全局 | 系统管理员；本人可在个人设置修改密码 |
| 用户组及组成员 | 全局 | 系统管理员 |
| 全部工作空间列表、创建、删除和还原工作空间（2.3） | 全局 | 系统管理员 |
| 空间名称、时区、每周起始日、第一周 | 工作空间 | 空间管理员 |
| 用户、用户组的空间访问权与角色 | 工作空间 | 空间管理员 |
| 自定义用户属性的定义与赋值 | 工作空间 | 空间管理员维护，数据开发只读 |

- 创建普通账号不加入当前空间，也不分配空间角色。通过「成员与访问」单独添加用户或用户组。
- 全局组在不同空间可以拥有不同角色。空间内的「已授权用户组」只添加已有组、修改该组的空间角色或移除访问，不能创建组或修改组成员。
- 全局组的成员变化影响所有引用它的空间。成员页同时列出直接授权、通过组授权和系统管理员身份得到的访问，并展示来源及生效角色。移除直接授权不会撤销其他来源的访问；停用账号仍阻止登录和访问。
- 属性是数据权限规则的输入，本身不授予空间或仪表盘访问权限。内置账号属性只读，自定义属性在各空间独立定义、独立赋值；暂不提供全局自定义属性或同名属性的跨层覆盖。
- 以后只有明确需要空间管理员自助组建业务小组时，再考虑空间分组；当前不引入组嵌套或两级组继承。

### 2.2 设置入口

三类设置各有独立标题、侧栏和路由，不在同一侧栏混排：

| 入口 | 位置 | 页面与路由 | 可见范围 |
|---|---|---|---|
| 系统管理 | 头像菜单 | `/settings/system/users` 用户管理；`groups` 用户组；`workspaces` 全部工作空间；`ai` AI 模型；`ai-usage` AI 用量；`audit` 审计日志；`general` 通用设置（导出限制、审计保留、查询缓存的默认有效期、MCP 总开关，见 [启动配置](configuration.zh.md) 第 10 节） | 系统管理员；不依赖当前空间 |
| 空间设置 | 顶栏导航（数据开发及以上） | `/settings/workspace/general` 基本设置；`members` 成员与访问；`attributes` 用户属性 | 空间管理员可管理全部；数据开发只能查看用户属性 |
| 个人设置 | 头像菜单 | `/settings/personal/account` 我的账号、修改密码；`mcp` MCP，本人授权过的客户端（[AI 助手](ai-assistant.zh.md) 14.5） | 所有已登录用户，包括未加入空间的用户 |

空间设置的导航栏标题始终展示「空间名称 · 空间设置」。「成员与访问」使用「用户」「已授权用户组」两个页签。系统管理的空间列表提供「管理」，进入该空间同一套设置；管理其他空间时先通过现有的草稿确认和会话切换流程，再进入目标空间的基本设置。

当前界面将组织管理员显示为「系统管理员」，内部仍使用组织级 `isOrgAdmin` 标记。用户目录、用户组目录可由系统管理员在未选空间时读取，也允许当前空间的数据开发和管理员读取以选择授权对象；普通用户不能读取目录。工作空间的属性和设置始终要求有效的当前空间。

### 2.2.1 设置页的布局与交互

三类设置用同一套页面，外观与「我的仪表盘」一致，是[架构总览](architecture.zh.md)第 12 节的岛屿式外观：

- **铺满窗口。** 左侧是定宽的导航栏，顶部写这一类设置的名称；右侧内容区铺满余下的宽度，内容多时在内容区里滚动。窄屏时导航栏移到内容上方。
- **每页一个页头。** 页名、一行说明，主按钮（添加用户、新建用户组等）在页头右侧。页名只出现一次。页内分几部分时（AI 模型的「模型用途」「供应商与模型」，我的账号的「修改密码」），各部分用小标题，以分隔线隔开。
- **表格撑开，表单不撑开。** 表格随内容区变宽，状态、角色、操作这类窄列定宽，余下的宽度给名称列。表单最宽 640px，靠左。
- **一条记录一行。** 姓名和邮箱在同一格，邮箱用灰色小字；停用的账号在名字后标「已停用」，系统管理员标「系统管理员」。
- **新建和编辑用对话框**，不在页面里展开表单。
- **行上的操作收进「⋯」菜单。** 每行最常用的一个操作留在外面，如工作空间的「管理」、模型的「测试」。
- **危险操作先确认。** 停用账号、设为或取消系统管理员、删除用户组、删除、还原或立即删除工作空间、移除用户或用户组的访问、删除属性、删除模型供应商和模型、调短审计保留期，都先在确认框里说明后果，再点一次才执行。启用账号、修改角色直接生效。
- **人多的列表能搜索。** 用户管理和成员与访问按姓名或邮箱搜索，超过 20 条分页。
- **保存结果用短暂提示。** 「已保存」「密码已修改」出现几秒后消失，不常驻在页面上。

各页的特别之处：

- **基本设置**：单列，每项左边是名称，右边是控件，说明写在控件下方；分「名称」和「日期与周」（时区、每周起始日、第一周）两组。有修改才能保存；有未保存的修改时，离开页面或切换空间先确认。
- **通用设置**（系统管理）：布局与基本设置相同，分「导出」「审计」「查询缓存」三组；输入框留空表示用默认值，占位文字就是默认值。见 [启动配置](configuration.zh.md) 10.3。
- **成员与访问**：「用户」页签分用户、角色、来源三列。角色是生效角色；来源在一行里列出每个来源给的角色，如「直接授权：普通用户 · 华东销售：数据开发」。修改或移除直接授权在「⋯」菜单里，只通过用户组访问的人也能在菜单里加直接授权。三种角色的说明放在「角色」列头的提示里。「添加用户」「添加用户组」在各自页签的搜索框那一行，在对话框里一次选多个，再选一个角色。「已授权用户组」页签的角色仍在行内直接改：一个组在空间里只有一个角色，不会出现生效角色和直接授权不同的情况。
- **用户属性**：点属性值所在的格子，编辑这一个用户或用户组的值。新增属性在页头；改名、删除在该属性列头的菜单里，不再有「属性管理」对话框；列头的提示里写属性标识。仍列出全组织的用户和用户组：成员列表只有空间管理员能读，而数据开发也能看这一页。

### 2.3 删除工作空间

删除分两步：先标为已删除，保留期满后永久删除。保留期默认 30 天，系统管理员在「系统管理 → 通用设置」里改（[启动配置](configuration.zh.md) 10.7）。在这期间可以还原，也可以立即删除。

- **只有系统管理员能删除、还原和立即删除**，与新建工作空间相同，入口在「系统管理 → 工作空间」的列表里。空间管理员不能删除自己的空间。
- **删除后对所有人隐藏**，包括系统管理员：切换列表里没有它，也切换不进去。它只留在系统管理的空间列表里，写明「已删除」和永久删除的日期，按钮换成「还原」和「立即删除」。
- **正在这个空间里的会话**：删除者自己的会话被移到他能进入的第一个空间（与登录时的选择方式相同），页面随之整页刷新，与切换空间相同。其他人的会话不自动切走，而是变成没有当前空间：他们已打开的页面再发请求会失败，提示当前工作空间已不可用、请在顶栏切换；刷新后页面请他们从顶栏选一个空间，一个空间都没有时才请他们联系管理员。这样别人填到一半的表单不会悄悄存进另一个空间。空间里排队和执行中的导出被取消，还原后不会恢复。指向这个空间的分享链接打开时提示无权访问。
- **名称仍被占用**：永久删除之前，不能新建同名空间，也不能把别的空间改成这个名称，提示先还原或立即删除它。这样还原时不会撞名。
- **还原**：空间恢复原样，成员、内容和设置都不变，再次出现在有权进入的人的切换列表里。
- **永久删除**：保留期满由每小时的维护任务执行，实际在期满后的一小时内；「立即删除」马上执行，只能用于已删除的空间。调短保留期后，已超过新期限的空间在一小时内永久删除，保存前先确认。一次删除这个空间和其中的全部内容：数据源（含保存的密码）、数据集及其修订和数据权限、图表、仪表盘及其修订、仪表盘授权、分享条件、文件夹、成员、用户属性、导出记录和导出文件。导出文件先从存储中删除，失败时这次不删除数据库里的内容，留到下一次维护再试；数据库里的内容在一个事务里删除。
- **保留**：账号和用户组属于组织，不删除。审计事件保留，照常按保留期清理；永久删除后，这个空间以前的事件在空间一栏显示 ID，删除和永久删除的事件本身记有空间名称。
- **最后一个空间也能删除**，包括安装时创建的默认空间：它只在第一次启动、创建默认组织时一起创建，永久删除后重启不会再出现。系统管理员不在任何空间里也能进入系统管理，再新建空间。
- 永久删除时关闭这个空间的数据源在本实例上的连接池，与删除数据源相同。
- **二次确认**：三个操作都是点一次后，按钮原地变成确认和取消，上方写明后果，与删除数据源的做法相同；同一行一次只展开一个确认。已删除的空间在名称下方写明永久删除的日期。
- 实现上，`workspaces.deleted_at` 非空即已删除。会话、切换、登录时选空间都只认未删除的空间；删除时在同一个事务里处理会话、取消导出。永久删除按外键依赖逐表删除，不依赖外键的级联设置；测试列出所有带 `workspace_id` 的表，检查永久删除后这个空间一行不剩，新加的表漏删时测试失败。

## 3. 主体

| 主体 | 说明 |
|---|---|
| 用户 | 组织级账号。可配置工作空间级**用户属性**（如 `regions=[华东, 华南]`），供数据权限引用，见 5.6 |
| 用户组 | 全局用户的集合，用于批量授权，在各空间分别授予角色和配置属性值。成员只在系统管理维护；以后可由 SSO 同步 |
| 全体成员 | 工作空间的所有成员，授权时可以选它，不必一个个加。不是一个真实的用户组，成员变动时自动跟着变 |
| 服务账号 | 供数据 API 和嵌入使用的非人类身份，持有密钥，同样有角色和属性 |

嵌入场景下，宿主系统用服务账号的密钥签发一个短期令牌，令牌中携带最终用户的属性。查询时这些属性的作用与普通用户属性完全相同。

## 4. 资源权限

### 4.1 角色

成员在每个工作空间里有一个角色。角色只有三个，固定不变，从低到高：

| 角色 | 面向 | 能做的事 |
|---|---|---|
| 普通用户 | 业务用户 | 看工作空间里的仪表盘和图表，使用筛选和联动；导出作者允许导出的图表数据 |
| 数据开发 | 数据分析师、工程师、报表制作者 | 加上：管理数据源连接，在数据探索里对数据源写 SQL，建和改数据集、图表、仪表盘和文件夹，配置数据集的行列权限，查看血缘和引用关系 |
| 管理员 | 空间负责人 | 加上：管理空间的成员和用户组的角色，修改空间设置 |

规则：

- 高一级的角色拥有低一级的全部能力。每个接口只登记「至少需要哪个角色」。
- 一个人可以直接是成员，也可以通过几个用户组成为成员，取其中最高的角色。
- **系统管理员**是账号上的组织管理员标记：管理全局账号、用户组和工作空间，并在组织的每个工作空间里都是管理员。
- 不提供自定义角色，也没有可勾选的权限点。数据探索的 SQL 导出要求数据开发或管理员角色。仪表盘上的图表数据导出不看角色，由图表的「允许导出数据」开关和仪表盘授权决定，开关对所有角色生效，见 [导出设计](exports.zh.md) 第 2 节。导出任务只能由发起人查看、取消和下载，不论当前在哪个空间，只要仍能进入导出所在的空间；后台执行与下载会在那个空间里重新检查权限（[导出设计](exports.zh.md) 第 6 节）。AI 助手所有角色都能用，各人只看到自己的对话；它调用的模型由系统管理员配置，见 [AI 助手](ai-assistant.zh.md) 第 8 节。MCP 服务只要求在所读仪表盘所在的空间里是普通用户，见 [AI 助手](ai-assistant.zh.md) 第 14 节。还没有的功能（订阅、嵌入）不预先占位，做到时再决定归哪个角色。
- 数据开发能直接对数据源写 SQL，能读到空间内每个数据源的连接账号看得到的全部数据。把谁设为数据开发，就是信任他能看这些数据。

这是 2026-10-17 从「权限点集合加四个内置角色，另可自定义角色」收敛而来的。原因：权限点中有一半对应的功能还没有；角色可以自己配置时，持有「管理成员」的人能把高于自己的角色分给别人或自己所在的用户组，从而提权。

### 4.1.1 普通用户的自助分析（规划）

以后普通用户可以向 AI 提问，让 AI 生成个人仪表盘。这不改变三个角色，而是给普通用户加两项能力：

- **个人内容**：只属于本人的图表和仪表盘，可用 `owner_id` 区分，不出现在共享的仪表盘里，也不影响别人。
- **自助查询**：普通用户对数据集发查询。前提是数据权限（第 5 节）已经实现，并且数据集设为允许普通用户自助查询；查询一律带上行列权限。

在此之前，普通用户只能通过别人保存的图表取数，见 4.3。仪表盘取数按查看者的身份执行，所以个人仪表盘以后分享给别人，别人看到的也只是自己数据范围内的数据。

### 4.2 仪表盘授权

第一版只对仪表盘授权，规则如下：

- **普通用户默认看不到任何仪表盘。** 数据开发或管理员把仪表盘授权给用户、用户组或「全体成员」，被授权的人才能在「我的仪表盘」里看到并打开它。新建的仪表盘也是看不到的，要授权后才对普通用户可见。
- **数据开发和管理员看到全部仪表盘**，他们本来就能编辑所有仪表盘。
- **授权只有「可查看」一种。** 编辑仪表盘仍由角色决定：数据开发和管理员都能编辑。
- **图表不单独授权。** 普通用户只能通过已授权的仪表盘接触图表：只能取这些仪表盘上图表的数据和筛选候选，图表列表里也只列出这些仪表盘上的图表。直接拿图表 ID 调接口取不到别的图表的数据。
- 一个人直接被授权，或通过任何一个所在用户组被授权，或仪表盘授权给了全体成员，都能看到。
- **数据开发和管理员都能修改仪表盘授权**，在仪表盘的「授权」设置里操作。

以后扩展成通用的资源授权：

- 对文件夹、仪表盘、数据集、数据源授予访问级别：可查看；可编辑（加上修改、删除）；可管理（加上修改该资源的授权）。
- **文件夹继承**：仪表盘默认继承所在文件夹的授权，子文件夹继承父文件夹，可以在某一层打断继承，单独设置。
- 最终权限 = 角色允许的动作 ∩ 资源授权的级别。例如普通用户即使被授予某仪表盘「可编辑」，也不能编辑。

### 4.3 仪表盘与数据集的权限关系

用户能看某个仪表盘，是否就能看到它背后数据集的数据？

草案选择：**能**。查看仪表盘不要求对数据集有单独授权。理由是业务用户不应该需要理解「数据集」这个概念，否则授权会非常繁琐。

配套约束：

- 以后有了数据集授权，**创建**图表时数据开发必须对该数据集有「可查看」。即数据集的授权控制的是「谁能用它做图」。
- 仪表盘背后的查询仍然执行数据权限（行与列），所以看到的数据范围仍然因人而异。

### 4.4 内部表达

资源授权实现后，角色决定能做哪一类动作，资源授权决定能对哪些资源做，两者取交集。

## 5. 数据权限

挂在数据集上，在查询层统一注入，对所有入口生效（仪表盘、AI、嵌入、数据 API、导出、订阅推送）。

- **只约束普通用户。** 数据开发和管理员能直接对数据源写 SQL，在数据集这条路上限制他们并不能保护数据。
- **由数据开发和管理员配置**，在数据集的「数据权限」标签页管理命名规则，支持搜索、按类型筛选、编辑、复制、删除和用户模拟验证。规则编辑器支持固定值、动态用户属性与多条件且/或组合；完成编辑后在列表统一保存。没被规则覆盖的人看什么单独设置。
- 「数据权限」标签页对数据开发和管理员提供规则编辑和用户预览；普通用户不能访问。
- **与数据集定义分开保存**：改权限不会让数据集多出一个版本，改数据集也不会碰到权限。每次修改记录修改人和时间。
- 规则可以对用户、用户组或全体成员生效。

### 5.1 行级权限

一条行级规则由「对谁」和「能看哪些行」组成。编辑器直接配置行条件，支持多个条件的「且」「或」组合，以及固定值和动态用户属性，例如 `大区 = 华东`、`门店 in (A01, A02)`。新建、编辑和复制规则都需要完整条件，不再提供「全部可见」切换。

前后端统一要求完整条件。保存与模拟验证拒绝缺失或不完整的条件；查询执行时，无效规则不放行任何行，也不会覆盖其他规则的限制。没有无条件放行的行级规则。

```jsonc
{ "subjects": [{ "group": "grp_east" }], "rows": { "field": "region", "op": "eq", "value": "华东" } }
```

一个人能看哪些行，按下面的顺序决定：

1. **被至少一条规则覆盖**（直接、通过任何一个所在用户组，或规则对全体成员生效）：只能看这些规则放行的行，多条规则之间取**并集**。例如同时在华东组和华南组，看华东加华南。
2. **一条规则都没覆盖到**：按数据集上的设置「没被规则覆盖的人看什么」：
   - **看全部**：适合大部分人照常看、只收紧个别组的情况。给华东组配「华东」，其他组不受影响。
   - **看不到**（页面首次添加规则时的默认值，已有配置保留原选择）：适合每个人都只该看自己那部分的数据集（各大区、各门店、薪资）。漏配的人看不到任何行，而不是看到全部。

被覆盖就只看规则放行的行，不会因为同时在另一个没配规则的组里而抵消限制。例如张三在华东组（只看华东）和总部组（没配规则），他只看华东。总部组需要额外范围时，应按职责配置条件。地区和部门等限制若需同时满足，须在同一条规则内使用「且」组合。

实现上：

- 解析结果是一个过滤条件，编译为包裹来源 SQL 之后的 `WHERE`（查询编译器的 `RowFilter`），对一次取数的每条 SQL 都生效：明细与聚合、合计和小计、同环比和占比的子查询、筛选候选值。这个注入点和它的一致性测试已经有了。
- 「看不到」编译为恒假的条件，查询照常执行，结果为空。
- **失效的规则按「看不到」处理。** 规则引用的字段被删除或改了类型，命中它的人看不到任何行，并在数据权限页上标出这条规则失效。保存数据集时，阻止删除被规则引用的字段。

### 5.2 列级权限

列权限的生效范围有两个方向，默认 `columnMode: "visible"`（适用成员可见，其他人不可见）；切换为 `"hidden"` 后，适用成员不可见，其他人可见。规则里的 `visibleTo` 为兼容原接口继续存储适用成员：

```jsonc
{ "fields": ["cost", "gross_margin"], "visibleTo": [{ "group": "grp_finance" }] }
```

- 没有列级规则的字段所有人可见，新加的字段也是。
- 每条规则根据生效范围得出可见结果；同一个字段的多条规则取可见结果的并集，再传播计算字段依赖。不可见方向也遵循这一语义，并非拒绝优先。
- **依赖传递**：计算字段引用了不可见的字段，它同样不可见。依赖关系来自表达式里的 `${...}` 引用。
- 对看不到的字段：数据集的字段列表里不出现；查询在任何位置引用它（显示、分组、筛选、排序、动态候选）都拒绝执行。
- 仪表盘中某个图表用到了当前用户看不到的字段，这个图表显示「无权限」，其他图表不受影响。
- 行级规则可以引用受限字段：过滤在服务端进行，不会把字段的值交给看不到它的人。

页面分为「行列权限生效范围」和「行列权限规则详情」两个区块，切换数据权限页签时保留左侧字段大纲。无任何行/列规则表示「未开启」，即使保存过 `unmatched: "none"` 也不再过滤数据；添加并保存第一条规则后开启，删除全部规则并保存后关闭。未保存时显示待开启/待关闭状态。

### 5.3 以某人身份预览

数据开发或管理员在数据权限页选一个用户，看到他在这个数据集上实际能看到的行和列。用来检查有没有配漏，尤其是设成「看全部」的数据集。

### 5.4 缓存

查询结果缓存的键必须包含生效的行级过滤条件和可见列集合，不同数据范围的用户不能共用缓存。相同数据范围的用户可以共用。

### 5.5 数据脱敏（以后）

把字段的值替换成部分遮盖的形式（如手机号只显示后四位）。要注意：如果筛选、排序仍按原值进行，就能用「手机号包含 1381234」这样的筛选反复试探出真值。所以对被脱敏的人，这个字段的每一处使用（显示、分组、筛选、排序、候选值）都要换成脱敏后的表达式。

### 5.6 用户属性

自定义属性的定义与赋值属于**工作空间**，由空间管理员维护，数据开发只读。「工作空间设置 → 用户属性」页分用户和全局用户组展示，提供属性管理和批量赋值。为全局组设置的值只在当前空间生效，不修改该组的全局资料或其他空间的值。

- 系统属性：`userId`、`email`、`displayName`，从账号读取，只读且不能重定义。推荐使用稳定的用户 ID 或邮箱识别负责人，姓名并不唯一。
- 自定义属性：稳定标识、显示名、用户/用户组的多值文本赋值。标识创建后不改；显示名可改。
- 有用户单独赋值时，完全覆盖组赋值（包括明确设置为空）。否则合并所有所属用户组的值并去重。移除用户赋值即恢复继承。
- 文本需与数据集字段精确匹配，大小写和空格保留；`*` 是普通字符，不代表全部行权限。
- 属性支持文本字段的 `in` 条件，API 表达为 `{ "field": "region", "op": "in", "value": { "userAttr": "regions" } }`，可以与固定值在 `and` / `or` 条件树中组合。
- 服务端按**实际查看者**身份解析，产生参数化的普通过滤条件后进入原有查询编译器。仪表盘取数、筛选候选和权限模拟共用这条路径；修改属性、组成员后下次查询立即生效，无需重新登录。
- 缺失属性或空值使引用它的整条行规则不放行任何行（包括嵌套的且/或/非），不会回退到未匹配成员的“看全部”。其他独立规则仍可授予权限。
- 删除属性后，引用它的规则标为失效并停止放行；用户界面在删除时明确提示影响。保存规则会拒绝未知属性或非文本字段的动态匹配。
- 原有未命名规则、固定条件和列规则保持兼容；历史的“未匹配成员看什么”设置不自动迁移。没有任何策略的数据集仍然开放。

这次重构参考了火山引擎的[数据行列权限](https://docs.volcengine.com/docs/Datawindprivatization/Datarowandcolumnpermissions?lang=en)与[配置最佳实践](https://docs.volcengine.com/docs/Datawindprivatization/BestPracticesforRowandRowPermissionsConfiguration?lang=zh)的规则列表、编辑器和用户属性表格截图，保留本项目的三种固定角色模型与允许规则的并集语义。当前不提供属性文件导入或 SSO 同步，可通过属性接口批量更新。

### 5.7 系统变量（以后）

数据集 SQL 中使用 `{{user.email}}` 与数仓权限映射表 join，以及 SSO 同步属性、嵌入令牌属性，尚未实现。

## 6. 认证

认证回答「你是谁」，与上述授权模型解耦，通过接口接入：

- 本地账号（用户名和密码）
- 单点登录：OIDC、SAML、LDAP
- 服务账号密钥、嵌入令牌
- MCP 客户端的 OAuth 授权，SupaBI 自己充当授权服务（[AI 助手](ai-assistant.zh.md) 14.4）

认证模块的产出是统一的身份：用户 ID、所属用户组、用户属性。SSO 接入时，用户组和属性可以从身份提供方同步。

## 7. 审计

审计回答「谁在什么时候对什么做了什么，看了哪些数据」。事件写入元数据库，在系统管理中查询；同时写一行应用日志，供日志系统收集和外发。

### 7.1 记录的事件

| 类别 | 事件 |
|---|---|
| 登录 `auth` | 初始化管理员、登录、退出、修改本人密码。登录失败也记录，写明原因：账号不存在、密码错误、账号已停用、尝试过多。授权 MCP 客户端和撤销授权（[AI 助手](ai-assistant.zh.md) 14.8） |
| 账号与用户组 `account` | 创建、修改账号（停用、恢复、设为系统管理员、管理员重置密码），创建、修改、删除用户组 |
| 工作空间与成员 `workspace` | 创建工作空间、修改空间设置、删除、还原、永久删除（到期自动永久删除也记录，没有操作人）；加入成员、改角色、移除；设置、移除用户组在空间中的角色 |
| 授权与数据权限 `access` | 仪表盘授权、数据集的数据权限、用户属性的设置和删除 |
| 资源 `content` | 数据源、数据集、图表、仪表盘、文件夹的创建、修改、删除，以及移动到文件夹；携带筛选条件分享仪表盘（`dashboard.share`，详情为分享的条件和有效期） |
| 查询 `query` | 每次从数据源取数，见 7.3 |
| 导出 `export` | 创建、完成、取消、下载、拒绝下载。下载是数据离开系统的时刻，单独记录 |
| 系统 `system` | 修改系统管理的通用设置（`system_settings.update`，详情为改前和改后的值）；修改邮件设置（`email_settings.update`）和发送测试邮件（`email.test`），见 [邮件](email.zh.md) 7 |

不记录：只读的操作（列表、打开编辑器、查看配置）、未登录的请求、切换工作空间，以及不返回数据的数据库调用（`LIMIT 0` 取列信息、`EXPLAIN`、测试连接）。查看审计日志本身也不记录。

每条事件的结果是成功、失败或拒绝：

- 修改只记成功和拒绝。校验不通过、保存冲突的修改没有改变任何东西；被拒绝的记下来，因为它说明有人在尝试角色以外的操作。
- 登录记成功和失败。
- 查询记成功、失败和拒绝：失败的查询也已经把 SQL 发给了数据库。
- 导出完成记成功或失败；用户取消的导出已由取消事件记录，不再记完成。
- 测试邮件记成功或失败：它会把一封信发出系统。

### 7.2 事件的内容

| 内容 | 说明 |
|---|---|
| 时间、组织、工作空间 | 登录、账号和用户组的事件不属于任何工作空间，工作空间为空；创建工作空间记在新空间下 |
| 操作人 | 用户 ID 和当时的邮箱。登录失败时可能没有用户，只有填写的邮箱；导出完成由后台执行，操作人是发起人 |
| 事件、类别、结果 | 事件名如 `dataset.update`，类别见 7.1 |
| 对象 | 类型、ID 和当时的名称。改名时详情里另记原名称；删除时记删除前的名称 |
| 详情 | 按事件不同，见下 |
| 来源 | 连接的 IP、请求头 `X-Forwarded-For` 的原文、User-Agent |

- **不建外键**：账号停用、工作空间或资源删除后事件仍在，名称靠记录时的快照。
- **`X-Forwarded-For` 不当作可信 IP**：它可以由客户端伪造，所以与连接 IP 分开、原样保存。部署在反向代理后面时，连接 IP 是代理的地址。
- **详情**：账号与用户组、成员、空间设置、授权与数据权限、用户属性、文件夹和移动，记录提交的请求内容，其中名字含 `password` 的字段替换为 `[redacted]`。数据源的请求内容含连接密码，数据集、图表、仪表盘的定义大，每次保存的定义已经存在各自的修订里（图表和仪表盘见 [图表与仪表盘](chart-dashboard.zh.md) 4.1），这些只记对象，不记内容。

### 7.3 查询

- **一次取数请求记一条事件**，包含它发给数据库的每条语句：主查询、合计、小计。每条语句记 SQL、绑定参数、数据集、数据源、耗时、行数、是否截断、是否命中缓存，失败时记错误。SQL 超过 64 KB 时截断并标明。
- **命中缓存也记**：数据仍然交给了这个人。耗时是原查询在数据库中的耗时。
- **覆盖所有取数入口**：图表和仪表盘取数、筛选器候选、数据集预览（含数据探索运行 SQL）、查询接口、数据权限的模拟预览、MCP 服务。事件的对象是请求针对的资源：图表、仪表盘、数据集或数据源。
- **导出的查询**在后台执行，记在导出完成事件上，不另记查询事件。导出创建事件记录 SQL 全文或图表、筛选取值，完成事件记录行数、文件大小和失败原因。

### 7.4 记录方式

- **审计是平台基础的一个接口**（`audit.Recorder`），现在有两个实现同时启用：写入元数据库的 `audit_events` 表；写一行结构化应用日志（`msg=audit`）。应用日志只有事件、结果、操作人、工作空间、对象和来源，不含详情：SQL、参数和请求内容只在库里。外发目前靠收集应用日志，以后按需要增加推送到 syslog 或 webhook 的实现。
- **接口事件在请求处理完后统一记录**。和权限要求表一样，有一张审计表登记每个接口记什么事件、对象从哪里取；接口不在表里时测试失败，新增接口不会漏记。登录、初始化、导出的创建与下载需要处理过程中的信息（失败原因、导出来源），由处理函数自己记录。
- **查询事件在查询层执行语句的地方收集**：与查询诊断取同一时刻的语句，命中缓存的也在内，所以任何入口都会经过。
- **拒绝在权限检查处记录**，包括按角色拦截和处理函数返回的拒绝。
- **写审计失败不撤销已经完成的操作**：错误连同整条事件写入应用日志。审计不与业务修改在同一个事务里，否则每个存储函数都要改为接受外部事务；需要强一致时再改。

### 7.5 查询界面

- 系统管理新增「审计日志」页（`/settings/system/audit`），只有系统管理员能看。登录、账号和用户组变更不属于任何工作空间，放在工作空间设置里装不下。
- 按时间范围、工作空间、操作人、类别、结果筛选，按时间倒序，每次加载 50 条。
- 展开一条事件查看详情；查询事件逐条显示 SQL 和参数。
- 以后可在工作空间设置中给空间管理员一个只看本空间事件的视图。

### 7.6 保留与清理

- 默认保留 180 天，系统管理员在「系统管理 → 通用设置」里修改，`0` 表示永久保留；存在元数据库，各实例读到同一个值，调短时先确认（[启动配置](configuration.zh.md) 第 10 节）。清理由 worker 执行。AI 助手的用量记录也用这个保留期，见 [AI 助手](ai-assistant.zh.md) 13.5。
- scheduler 每小时为每个组织投递一个维护任务，跨实例去重，由 worker 执行：删除过期会话，按保留期分批删除审计事件，删除一天前的登录失败计数，删除七天前已结束的维护任务记录，删除过期的 OAuth 请求和令牌，以及注册后 24 小时内没人授权的 MCP 客户端（[AI 助手](ai-assistant.zh.md) 14.9）。
- 表按组织和时间建索引。数据量大到按行删除变慢时，再改为按月分区、整区删除。

## 8. 能力范围

全部能力都开源（Apache 2.0），不区分版本。下表是规划的完整范围，实现进度见第 13 节。

| 能力 | 范围 |
|---|---|
| 组织 | 先只有单个默认组织；之后支持多组织（多租户） |
| 工作空间 | 多个 |
| 角色 | 普通用户、数据开发、管理员三个固定角色 |
| 文件夹与资源授权 | 先做仪表盘授权；以后按文件夹继承、对数据集和数据源授权 |
| 用户组 | 手工维护，或从 SSO 同步 |
| 认证 | 本地账号；OIDC、SAML、LDAP |
| 数据权限 | 行级权限、列级权限；动态用户属性；以后加数据脱敏 |
| 嵌入 | 公开链接、基础嵌入、带用户属性的签名嵌入、白标 |
| 审计 | 应用日志；落库、查询界面、外发 |

数据权限的**注入点在查询层**：「权限解析」接口返回行过滤条件和可见列集合，行级策略、列级策略和脱敏规则都在这一个实现里解析。编译流程只有一条路径。

## 9. 对元数据库的影响

- 所有表：`org_id`。
- 所有资源表：`workspace_id`、`created_by`、`created_at`、`updated_by`、`updated_at`。
- 仪表盘、图表、数据集：`folder_id`；文件夹：`kind`（放哪一种资源）和 `parent_id`。
- 主体：`user`、`user_group`、`user_group_member`、`service_account`；工作空间属性存于 `user_attributes`（定义与用户/组赋值），账号原有 JSONB 属性预留字段仍未使用。
- 角色：`workspace_member.role`，取值 `viewer`、`developer`、`admin`。
- 成员关系：`workspace_member`（主体、角色）。
- 仪表盘授权：`dashboard_grants`（仪表盘、主体），主体是用户、用户组或全体成员，三者恰有其一；仪表盘、用户或用户组删除时，授权随之删除。以后扩展为通用的 `resource_grant`（资源类型、资源 ID、主体、访问级别），文件夹上的记录通过继承生效。
- 数据权限：`dataset_policies`，每个数据集一行，存在数据集定义之外：没被覆盖的人看什么、行级规则和列级规则（各为一个 JSON 数组，规则里的主体写成 `{user}`、`{group}` 或 `{everyone}`）、修改人和时间。没有这一行的数据集不限制任何人。规则整体读写，所以存成 JSON；用户或用户组删除后，引用它们的规则不再覆盖任何人。

## 10. v1 明确不做

| 项 | 原因 |
|---|---|
| 资源跨工作空间共享 | 破坏隔离边界 |
| 拒绝优先的混合规则（deny override） | 列权限支持全局可见/不可见方向，各规则的可见结果仍取并集 |
| 审批流（申请访问某仪表盘） | 流程类功能，后续 |

## 11. 已决定

1. **组织层**：在工作空间之上加「组织」作为租户边界。所有表带 `org_id`，v1 只有一个默认组织。
2. **仪表盘可见即数据可见**：查看仪表盘不要求对数据集单独授权，数据范围由数据权限约束。
3. **全部开源**：不区分开源版和企业版，行列权限、脱敏、SSO 等全部以 Apache 2.0 开源。早先的划分是行级权限开源、列级权限和数据脱敏放企业版，2026-10-17 取消。
4. **角色**：普通用户、数据开发、管理员三个固定角色，不提供自定义角色，见 4.1。

## 12. 后续决定

1. **账号和用户组属于组织，成员关系与自定义用户属性属于工作空间。** 账号和组由系统管理员统一维护；创建账号与加入空间是两个操作。空间管理员只能从已有账号或全局组中选取授权对象，不提供空间用户组。
2. **管理入口分为系统管理、工作空间设置、个人设置。** 具体路由、可见范围和授权来源展示见 2.2。

实现中确定的细节：

- **会话**存在元数据库中，浏览器只持有随机令牌，库里只存令牌的哈希。Cookie 为 `HttpOnly`、`SameSite=Lax`，无活动超过登录会话有效期后失效，有效期默认七天，在「系统管理 → 通用设置」里改（[启动配置](configuration.zh.md) 10.7）。过期的会话由每小时的维护任务删除，见 7.6。
- **跨站请求防护**：除 `SameSite` 外，服务端拒绝来源与自身不一致的写请求。
- **密码**用 Argon2id 哈希，参数随哈希一起存储，以后可以调高而不影响已有密码。每次哈希或校验要占 19 MiB 内存，所以每个进程最多同时进行四个，不论用途：登录、初始化、改密码或重置密码、建账号。其余的排队等候，客户端离开就不再等。不加限制时，同时 64 个校验占了 1.2 GB，而且任何能打开登录页的人都能发起。同时四个每秒仍能校验约 250 个密码，况且能校验多少本来就受 CPU 限制。
- **登录失败**对"账号不存在"和"密码错误"返回完全相同的结果，并消耗相近的时间，避免被用来探测账号是否存在。同一邮箱五分钟内失败五次后，在这五分钟结束前不再接受登录。失败次数存在元数据库中，所有实例共用同一个计数，时间以数据库为准；成功登录后清零，一天前的记录由每小时的维护任务删除。每次尝试在校验密码之前就计数，用一条语句完成：窗口里已有五次时直接拒绝；登录成功再清零。如果校验之后才计数，同时发出的尝试都会在任何一次计数之前通过检查：同时 40 次全部进了校验。被拒的尝试不再累加，所以窗口仍在第一次失败五分钟后结束。
- **角色变更立即生效**，不需要对方重新登录；停用账号或重置密码会立即结束对方的所有会话。
- **管理员不能修改自己的角色、状态或组织管理员身份**，也不能把自己移出工作空间，避免把自己锁在外面。
- **迁移**：从权限点角色改为三个角色时，持有「管理成员」的成员成为管理员，持有「编辑数据集」的成为数据开发，其余成为普通用户。迁移只会让人失去能力、不会多出能力，需要的由管理员重新提升：原来的「编辑者」成为普通用户；只有「管理数据源」而没有「编辑数据集」的自定义角色失去数据源管理；只有「管理空间设置」而没有「管理成员」的自定义角色失去空间设置。
- **三类操作的门槛**：公开（登录相关）；在当前工作空间内至少是某个角色；需要组织管理员（改变组织本身：账号、用户组、工作空间）。
- **各接口所需角色**：看图表和仪表盘、取它们的数据和筛选候选，分享仪表盘和打开分享的条件（[图表与仪表盘](chart-dashboard.zh.md) 3.10），导出仪表盘上允许导出的图表数据，要普通用户；查看、取消和下载本人的导出只要已登录，不要求当前空间，每个导出在它所在的空间里检查；数据源、数据探索、数据集、图表和仪表盘的编辑及草稿预览、文件夹、血缘和引用关系，要数据开发，SQL 导出及其下载也是；成员和空间设置，要管理员。普通用户没有直接查询数据集的入口。
- **新增接口必须登记权限要求**，否则默认拒绝，有测试保证权限表与接口定义一致。
