# Deferred items

Items that a design discussion explicitly decided to "not do now, do later or re-evaluate". Each item records why it is deferred and when to re-evaluate it, so that none is forgotten.

## Gaps in the current implementation

Parts of features that already exist and that are known to be missing. The difference from the "deferred" items below: these are not decided against, they are just not done yet.

| Gap | Impact |
|---|---|
| Missing parts of the account feature | There is no password recovery (a forgotten password can only be reset by an administrator); an account can be disabled but not deleted; there are no email invitations |
| A session does not switch away automatically when its workspace permission is revoked | The user sees a no-permission message and has to switch to another workspace by hand |
| Missing parts of the audit | Only system administrators can view it; workspace admins have no view limited to their own workspace; forwarding events outside relies on collecting the application logs, with no push to syslog or a webhook; the audit and the business change are not in one transaction, so when writing the audit fails the change still takes effect and the event stays only in the application log; an export job that is still interrupted after three retries is marked failed directly, with no "Export finished" event. See [Access control and workspaces](design/access-control.md) section 7 |
| The data permission simulation preview shows only the first 100 rows | Paging through or exporting the simulation result is not supported yet |
| StarRocks and Doris are tested on one version only | The tests use the latest version of the StarRocks single-node image and Doris 2.1.0; `make test` does not run them by default, `make test-olap` is needed |
| Trino is tested on two versions only | `make test-olap` runs Trino 483; the minimum supported version, 418, was run by hand once on 2026-10-21. The tests use the `memory` catalog; the types and metadata of connectors such as Hive and Iceberg are untested |
| Differences between databases are not all smoothed over | Text case, numeric representation and so on, see [Architecture overview](design/architecture.md) 9.1 |
| The Workbench opens only one resource at a time | There are no multiple tabs; users switch back and forth through Recently opened in the search panel; whether multiple tabs are needed is decided after real use |
| The run history of Data exploration lives only in the browser | The preview shows at most 1000 rows; background CSV/XLSX export is supported, but the query run history is still kept only in the browser, the latest 50 entries |
| Folders are only for organizing | They take no part in permissions; a non-empty folder cannot be deleted, its contents must be moved out first |
| Only the tables in the current catalog are listed | When StarRocks or Doris has several catalogs, the Tables panel shows only the one the connection is in, so the tree has no catalog level. Trino lists all catalogs |
| SQL editor completion does not know catalogs | After typing `catalog.` it does not suggest the schemas and tables in it; for a table in another catalog on Trino, click the table name in the Tables tree to insert the full name |
| The display format has only the basic options | There are no parentheses for negative numbers (for coloring by condition see the conditional formatting in [Charts and dashboards](design/chart-dashboard.md) 2.8); a date has only three styles, hyphen, slash and Chinese, and it cannot follow the interface language (such as `Jan 5, 2026`), use a custom style, omit the year, or show the weekday, a 12-hour clock or a relative time (3 days ago); a date truncated by an expression carries no granularity and is written by day. See [Dataset model](design/dataset.md) section 5.5. The chart editor cannot set a format or conditional format for dynamic positions, only the API can. The format of a field is also used on detail rows: a unit chosen for the total (such as "万") is applied to a single row and may show as `¥0.03万` |
| Table-level lineage reads the table names in the SQL, it does not parse | It recognizes only the names after `FROM` and `JOIN` (skipping comments, strings and names that `WITH` defines itself). Tables read through a function (`remote(...)` in ClickHouse, `dblink(...)` in PostgreSQL and so on) are not found, and the dataset is then still linked straight to the data source; views are not expanded. Lineage is computed each time it is viewed and is not stored |
| Tables in the lineage graph are told apart by how the SQL writes them | `orders` and `public.orders` are two nodes, and so are names that differ in case; merging them requires querying the database for the default schema, and then lineage would depend on the data source being online |
| There is no field-level lineage | It knows only which table is read, not which columns; a real SQL parser is needed |
| The builder in the chart editor has limited abilities | Filters can only be combined with "AND"; dynamic positions cannot set a sort; a chart created through the API that contains a query-level filter or `offset` is read-only in the interface |
| Cascading is limited to exact selection | Only an `in` selection at the detail level can be a cascading node; dates, fuzzy matching and aggregate results cannot; the choices of a global cascade query only the dataset of one source chart and do not query across datasets, see [Charts and dashboards](design/chart-dashboard.md) 2.5 |
| Extensions of chart links | Single selection of a static field, cross-dataset mapping and date ranges are supported for bar charts, horizontal bar charts, pie charts and tables; multiple selection, dynamic dimension sources and more chart types are not supported yet |
| Finer-grained merging of save conflicts | Version checks are enforced for datasets, charts and dashboards, a three-way comparison is supported and the result is applied as a draft; the display name, description, format and hidden state of dataset fields are merged per property. The data source, SQL and parameters are still taken as a group, and when a definition changes, such as a field type or formula, the whole field is chosen; the chart configuration, the dashboard layout, and filters and chart links are not merged automatically inside yet |
| Missing parts of chart styles | Data labels do not avoid each other; colors can only be set per metric, not per dimension value; the labels of a combo chart may overlap the labels at the tops of the bars. See [Charts and dashboards](design/chart-dashboard.md) 2.8 |
| Missing parts of the Sankey chart | The height of a node is the sum of its links, so it comes out too large when the flow is a non-additive metric such as distinct count; later layers are not colored by source; a link merged into "Other" is the sum of its parts |
| Missing parts of pivot tables and totals | Totals are not shown when the chart has a condition on the result (`having`); with many columns there is no virtual scrolling and all cells are drawn at once; totals and subtotals send one extra query per item (up to 16 with subtotals) and are not merged with `GROUPING SETS` / `ROLLUP`; subtotals cannot be shown when there are more than 16 dimensions; subtotals cannot be collapsed, and row-only or column-only subtotals are not available |
| Each chart on a dashboard sends its own query | Identical queries are merged, results are cached and each data source has a concurrency limit ([Query IR](design/query-ir.md) section 6), but the queries of different charts are not combined into one SQL |
| Interactive queries have no asynchronous execution | The Data exploration preview and chart queries still run synchronously inside the request, up to the query timeout (60 seconds by default); the full CSV/XLSX export already uses a background job |
| The query cache has no management interface and no metrics | The hit rate, usage and entries cannot be seen and it cannot be cleared by hand; there is only a log with one line per statement. With Redis it can be inspected in Redis directly |
| Background jobs are currently used only for exports and cleanup | Implemented: the Postgres queue, lease recovery, cancellation, CSV/XLSX generation, file retention, dashboard chart data export and the unified export center, plus an hourly maintenance job that cleans up expired sessions and audit events; export files can be kept in the data directory or in S3-compatible object storage; timed exports, subscriptions and email delivery are not implemented yet, see [Exports](design/exports.md) |

## Permissions

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Granting access to dashboards by folder, and granting access to datasets and data sources | The first version grants access to single dashboards only, which has the fewest concepts | When there are so many dashboards that granting one by one is a burden, or when it is needed to limit which data sources developers can use |
| Data masking | Every use of a field has to be replaced with the masked expression, otherwise a filter can be used to probe the real value, see [Access control and workspaces](design/access-control.md) 5.5 | When there are fields such as phone numbers and ID numbers that must be shown in part |
| SQL system variables | Row-level rules can already reference workspace user attributes; system variables such as `{{user.email}}` in SQL are not implemented yet | When permissions are kept in a mapping table in the data warehouse and SQL needs to join on the current user |
| Managing other workspaces directly from System administration | The APIs for members, user attributes and so on all work on the current workspace of the session, so "Manage" first has to switch the current workspace | When system administrators often have to look after several workspaces at the same time |
| Seeing which workspaces a person is in and which workspaces a group is granted to | Needs a new API; for now the only way is to enter each workspace and check | When there are so many workspaces that checking one by one is a burden |
| The user attributes page lists only the people the workspace can access | The member list can be read only by workspace admins, and developers can also see the attributes page, see [Access control and workspaces](design/access-control.md) 2.2.1 | When the organization has so many users that the attribute table is hard to browse |

## Charts

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Choosing per table column whether to merge equal values | One switch already covers the common use: each column merges only within the range where the columns to its left are equal, so the last dimension usually does not merge. See [Charts and dashboards](design/chart-dashboard.md) 2.8 | When only some dimension columns need to merge, for example merging the region but writing out the city on every row |
| A merged cell keeps showing its value while scrolling | The value is written at the top of the cell; when the cell is taller than the visible area, it scrolls out of sight; the row dimensions of a pivot table behave the same | When merged cells are often taller than one screen |
| Freezing the first several columns | Freezing the first column pins only one column; when the first column is in a header group, the group cell scrolls away horizontally with the table. See [Charts and dashboards](design/chart-dashboard.md) 2.7 | When several columns on the left, or a whole group, need to stay fixed |
| Totaling only the rows the table shows | The total is computed by the database over all the data; totaling only the first N groups that were fetched would need the total's SQL to add a "belongs to these groups" condition, databases match null in different ways, and the basis of the total for a share column would also have to be set. For now only the total row says "Total (all data)". See [Charts and dashboards](design/chart-dashboard.md) 2.1 | When numbers such as "total of the top N" are needed |
| Paging in the database | Table paging only turns through the rows already fetched, up to the returned row limit (10000 rows by default). Querying once per page needs a separate total row count, a stable sort, and a cache keyed by page, and export and merging equal values would have to be reconsidered. See [Charts and dashboards](design/chart-dashboard.md) 2.7 | When a dashboard needs to browse detail beyond ten thousand rows |
| Paging for pivot tables | A pivot table has groups and subtotals; when a group is split across two pages, how to show the group name and subtotal has to be decided | When pivot tables have many rows and need paged viewing |
| Color scales and data bars for conditional formatting | For now only coloring by rule. Color scales and data bars need decisions on which rows the minimum and maximum come from (on the frontend only the fetched rows; with paging, all fetched rows or the current page), which way a data bar for a negative number is drawn, and whether the subtotals of a pivot table take part. See [Charts and dashboards](design/chart-dashboard.md) 2.8 | When authors often need to see at a glance how large the numbers in a column are, rather than pick out those that pass a threshold |
| Conditional formatting that compares with another column | A rule compares only with a fixed number. Comparing with another column in the same row (actual below target) needs that column to be in the result too; a pivot table has to take the other measure of the same cell, and what the rule does when the compared column is hidden or removed from the chart also has to be decided | When "actual vs target" tables are common |
| Text color and whole-row coloring for conditional formatting | Only the cell that meets the condition gets a light background color. Text color is hard to read on light colors such as yellow, so a darker shade would have to be set, and dark mode too; whole-row coloring needs a rule for whose color wins when the rules of several columns are met at once | When users insist on the "red text for negatives" style, or want to mark a whole row |
| Conditional formatting for KPI cards and text columns | A KPI card can already be compared with another metric, with ▲▼; coloring a text column by value ("Status = overdue") needs a separate text condition | When there is a need to color a KPI card by a threshold, or a cell by status |
| Dragging a field to another bar | Each bar accepts different fields (a metric cannot be a dimension, a filter first needs its condition set), and moving between bars would also have to decide what happens to the original calculation, alias and format; for now only sorting within the same bar. A pivot table moves between rows and columns through the field menu. See [Charts and dashboards](design/chart-dashboard.md) 2.1 | When authors often need to move a field from one bar to another, starting with moving between the rows and columns of a pivot table |
| Continuing the chart link at the next level after a drill-down, or filtering other charts while drilling down | A drill-down changes only this chart; to filter other charts, use a chart link. A chart link maps the target by the field of the first level, and after drilling down to the next level the column has a different field, so a drill-down column can link only at the first level. To link at every level, the fields of the target chart must be mapped for each level separately, which amounts to one chart link per level. See [Charts and dashboards](design/chart-dashboard.md) 2.10 | When viewers often want to link other charts after drilling down |
| Drilling down to detail (seeing the raw rows behind a value) | Detail would expose columns that are not on the chart, and viewers can currently run only the query saved with the chart ([Charts and dashboards](design/chart-dashboard.md) 3.5), so which columns can be seen has to be decided | When viewers often need to trace which records make up a summary number |
| Drill-down for more chart types, and expanding and collapsing pivot tables | The first version covers only charts where clicking one category determines the next level. A point of a scatter chart, a cell of a heatmap and a treemap with groups each correspond to two dimensions, the nodes of a Sankey chart sit in different layers, and the layers of a funnel chart have an order; expanding a pivot table adds a level in place rather than replacing this one | When there is a concrete need, starting with expanding and collapsing pivot tables |
| Choosing a dimension on the fly to look further into a clicked value | The viewer would have to choose from the fields of the dataset, and a viewer cannot read the dataset and can run only the queries saved with the chart | When there is a need for exploratory analysis, starting with the author offering a few dimensions to choose from, like a dynamic dimension |
| Display names for the options of a parameter dropdown | Options show the value itself. A display name would need one more item stored in each option, and whether the share summary, exports and query diagnostics write the value or the display name also has to be decided. See [Charts and dashboards](design/chart-dashboard.md) 2.11 | When the values of a parameter are codes (such as `APP`) that viewers cannot read |

## Dashboards

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Printing and full rendering (all charts fetch data at once, a ready signal) | A print style was tried on 2026-10-20; in Chrome with ⌘P the right side of the charts was still cut off or left blank, and it was rolled back. The Chrome print dialog does not shrink a page that is too wide, while headless printToPDF does, so script verification could not reproduce it; the grid is positioned in pixels by screen width and does not reflow when printing. See [Charts and dashboards](design/chart-dashboard.md) 3.11 | When printing or PDF export is needed, or server-side screenshots or subscription delivery are built |
| Viewing, comparing and restoring old versions of charts and dashboards | The result of a chart also depends on the dataset it reads, and a dashboard also depends on the charts it references; rolling one back to an old version when the upstream has already changed does not give how it looked then, and the result is not controllable. Only revisions and the definition at that time are recorded, see [Charts and dashboards](design/chart-dashboard.md) 4.1 | When old definitions often have to be traced by querying the database directly, starting with read-only viewing |
| A retention limit for chart and dashboard revisions | Every save stores the full definition and all are kept, which has the fewest concepts | When the revision table grows large enough to affect backups or queries, keep the definitions of only the latest few versions per resource, with the list staying complete as before |
| Multiple query containers (placing a query container on a page of a dashboard) | Showing global filters by page already lets a filter that belongs to one page appear only on that page; multiple containers would need rules for the scope of each one's "Query" button and reset, whether the query mode and control style follow the container or the dashboard, whether a cascade can cross containers, and what happens to the filters in the original container when a chart changes pages. See [Charts and dashboards](design/chart-dashboard.md) 3.13 | When authors need to put a filter that belongs to one page next to the charts on that page |
| Linking a global filter to dataset parameters | In the first version parameters can be changed only on each chart ([Charts and dashboards](design/chart-dashboard.md) 2.11). To link a global filter to parameters, it must be decided how to match the case where the same filter maps a field on one chart and a parameter on another: a field filter has ranges and various operators, while a parameter is only a value or a set of values; where the dropdown options come from also has to be decided | When several charts on one dashboard use the same parameter (such as a snapshot of the same day) and one place should change all of them |

|---|---|---|
| Building the chat interface with AI Elements and Streamdown | Measured on 2026-10-22:<br>1. **Styles**: Streamdown adds the `tw:` prefix to class names only at run time, so the Tailwind scan of its published package cannot see the prefixed form, and 46 of the 105 class names actually used have no styles. A prefixed allowlist would have to be generated from its published package (12 KB more CSS), regenerated on every upgrade, and the `sidebar` color variables it uses would have to be added.<br>2. **Size**: the message component of AI Elements pulls in four plugins directly, for code highlighting, math, Mermaid and CJK typography; the build output grows from 3.5 MB (25 files) to 17.4 MB (430 files), and all of it is embedded in the Go binary; the first load of the AI assistant page grows from 182 KB to 1.1 MB. | Administrators viewing conversation content | A conversation can be seen only by its owner, and users ask questions with that expectation; which data the AI looked at is already recorded in the query events of the audit log. See [AI assistant](design/ai-assistant.md) 13.2 | When someone reports a wrong answer and an administrator needs to review it, starting with the user sending the conversation to the administrator, rather than administrators being able to see it at any time |
| A list of the details of each model call | The summary on the usage page already shows who, which model and which day spent how much; the details have only the time and tokens and do not show the conversation content, so they are of limited use for troubleshooting | When a failed call needs to be traced, or one person's usage on one day is abnormal |
| A usage trend chart, exporting usage | The per-day summary table already shows the change | When the time range is so long that the per-day rows are hard to read, or the cost has to be handed to finance or used for a budget |
| Filtering the audit log by "From the AI assistant" | It is already noted in the details of a query event and is visible when expanded | When the AI's data fetches are so many that they are hard to find in the audit log |
| Workspace admins seeing only the AI usage of their own workspace | Models and costs belong to the whole organization; the audit log too can be seen only by system administrators | When each workspace needs to control its own cost; do it together with the workspace view of the audit log |
| A separate retention period for AI usage | It shares one retention period with the audit log, one less setting, see [AI assistant](design/ai-assistant.md) 13.5 | When cost records must be kept longer than audit events, such as budgeting by year |

As of 2026-10-13 the latest npm version is still 2.3.0, and the matching upstream [Issue #2303](https://github.com/react-grid-layout/react-grid-layout/issues/2303) and [PR #2304](https://github.com/react-grid-layout/react-grid-layout/pull/2304) are neither closed nor merged | When upstream releases a stable version that contains the fix, or when this dependency is upgraded again |

Acceptance conditions for removing the patch:

1. Run the [GridLayout regression test](../web/packages/ui/src/GridLayout.test.tsx) on a candidate version without the local patch, and confirm that all of these work: continuous dragging, accumulating displacement within the start threshold, the mouse grab point after auto-scroll, drop placement and collision avoidance, dragging in an outside chart, and scroll cleanup after release or unmount. 2. Do not check only whether the PR is merged: as of the date above, PR #2304 fixes only the continuous refresh during dragging and resizing, and does not yet cover the start displacement accumulation, scroll position compensation and unmount cleanup in the local patch; these behaviors still have to be verified one by one.
3. After verification passes, upgrade the dependency, delete the patch file and the `patchedDependencies` configuration, update the lock file through pnpm, keep the regression test, and close this item after the frontend type check, lint, the full tests and the build are done.

## Data connections

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Support for MySQL 5.7 | Measured on 2026-10-20 on the official `mysql:5.7` (5.7.44): the default encryption mode cannot connect (it accepts only RSA key exchange, and Go 1.27 lists such cipher suites as insecure and does not offer them by default); with encryption turned off, ordinary charts work, but share, the difference and growth rate of period-over-period comparison, `TO_FLOAT` and running total fail with SQL syntax errors. Supporting it requires: reading the version when the connection pool is built and storing it in the data source record (saving and the editor both need it, so it cannot connect to the database each time); adding the AES-GCM suites of RSA key exchange to the encryption mode that does not verify certificates; on 5.7 writing the cast to float as `x + 0E0` and the regular expression as `x REGEXP y` (measured, only these two places change, and all consistency tests except running total pass); the dialect declaring that window functions are not supported, so running total cannot be chosen in the editor; using `tx_read_only` before 5.7.20; and a separate test target. For now only the connection test says that 8.0 is required, see [Architecture overview](design/architecture.md) 9 | When it is confirmed that a user must connect to MySQL 5.7 |
| MariaDB | Its version numbers differ from MySQL's, and the connection test does not decide by version; before 11.1 there is no `transaction_read_only`, so it cannot connect; there is no `REGEXP_LIKE` either. Not measured | When a user needs to connect to MariaDB |
| Kerberos, JWT and OAuth2 login for Trino | The first version does only user name and password, see [Architecture overview](design/architecture.md) 9.3. Kerberos needs a keytab and krb5.conf on every machine that runs SupaBI; a JWT token expires and someone has to renew it regularly | When a user's Trino has only these kinds of authentication enabled |
| PrestoDB | After the split from Trino the protocol headers differ, and the Trino Go driver cannot connect | When a user needs to connect to PrestoDB |
| Writing the data of files or other systems into the user's OLAP database (data integration) | The earlier upload feature turned a file into a table that lived only in the built-in DuckDB, which could not be analyzed together with the data already in the user's database; it was removed on 2026-10-19 ([Architecture overview](design/architecture.md) 9.2). The data should be written into the user's own database, which needs per-database table creation, type mapping and batch writing, and also the management of an account with write permission; not designed yet | When users need to analyze Excel, CSV or the data of other systems together with existing data |

## Datasets

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Two states, draft and published | Every API of datasets and charts would gain the question of "which version to read" | When analysts give feedback that they need to edit a dataset for a long time without affecting the live dashboards |
| Parameters that replace table names and column names (such as tables split by month) | It cannot be done with bound parameters and carries an injection risk | When there is a real need for split tables; the direction is an enumerated parameter with an allowlist |
| Associations between datasets (a full semantic layer) | Compiling automatic joins is complex, and metrics are easily added up twice | When analysts report that there are too many wide-table datasets to maintain |
| Building a dataset on top of a dataset | It adds complexity to compilation and permissions | Same as above |
| Materialization (writing the result into a table and refreshing it regularly) | It is a performance optimization and depends on a scheduler | When a slow dataset appears that the cache cannot solve |
| Defining dimension hierarchies in the dataset (province → city → district) | The drill-down levels are configured in the chart ([Charts and dashboards](design/chart-dashboard.md) 2.10), without depending on the dataset, so a change to the dataset cannot quietly break the drill-down of downstream charts | When several charts repeatedly configure the same set of levels; a hierarchy in the dataset would serve only as a preset in the editor, filled into the chart |
| Specifying a catalog in the table source | Every dataset in the interface is generated from SQL in Data exploration; the table source (`type: table`) exists only in the API and can write only `schema` and `table`; on Trino it can point only to tables in the default catalog. See [Architecture overview](design/architecture.md) 9.3 | When the interface is to build a dataset by choosing a table |

## Queries

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Pushing the pivot (columns to rows) down to the database | Databases differ greatly in support, and the interaction with `limit` is complex | When the frontend pivot has performance problems on large result sets |
| Ranking, moving average | v1 does period-over-period comparison, share and running total first | The `compute` of the query IR already reserves the types; add them one by one as needed |
| Running total of averages, distinct counts and dataset metrics | They cannot be derived from the values of the groups in sequence: an average needs the sum and the count fetched separately; a distinct count has to be rewritten as "in which group each value first appears", then counted and accumulated, which adds a subquery; the expression system of a dataset metric is not parsed, so it is not known whether it can be added up. For now the running total covers only sum, count, min and max, see [Query IR](design/query-ir.md) 3.5 | When there is a need such as "running total of users", do the distinct count first; when authors often write additive numbers as dataset metrics and so cannot get a running total, consider letting authors mark that a metric can be added up |
| Starting the running total before the filter range | The time condition would have to be rewritten as in period-over-period comparison, it makes sense only for a time dimension, and all of the history has to be read every time | When the historical running total needs to be shown within a recent time range |
| Stacked derived calculations (running share, Pareto and so on) | A metric has only one derived calculation; stacking needs the order of the calculations and the basis of the total to be decided first | When there is a need for Pareto analysis |
| Filling in groups that have no data | It needs a continuous series of dates generated by granularity and then joined, written differently in each database; without filling, the running total is still right, only that row is missing | When a missing point on a line chart causes a misreading |
| Cross-instance query merging and concurrency limits | The cache can be placed in Redis and shared by the instances, but merging identical queries and the concurrency limit are still per instance: doing it across instances needs a distributed lock and a shared counter | When there are so many instances that "number of instances × limit per instance" overwhelms the data source, or the same query is clearly repeated on several instances |
| Cache validity at the dataset and chart level | The first version has only the server default and the override at the data source level, which has the fewest concepts | When the datasets under one data source differ greatly in update frequency |
| Per-user query fairness and query priority | In the first version the concurrency limit is first come, first served per data source only | When one person opening a big dashboard crowds out others, or scheduled jobs (subscriptions, materialization) start to compete with interactive queries for the data source |
| Free-expression measures (chart level) | The expression parser and the dialect output already exist ([Standard expressions](design/expressions.md)); what is missing is the entry point in the query IR and the chart editor interface | When there is a need for chart-level temporary metrics |

## Multiple languages and time zones

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| Multiple languages for user content (dashboard titles, field display names and so on switching by language) | These properties would have to change from strings to maps by language, with a translation management interface | When the same dashboard needs to be viewed by users of different languages. The spec carries a version number, so it can be migrated then |
| Interface languages other than English and Simplified Chinese | First make sure the mechanism is correct | When there are community contributions or customer needs |
| The starting month of the fiscal year | It affects grouping by year and by quarter, and the need is relatively small | When there is a need for the fiscal year basis; it is a workspace-level setting like the first day of the week |

## Foundations

| Item | Why deferred | When to re-evaluate |
|---|---|---|
| SQL parser | The Go ecosystem lacks a mature multi-dialect parser, only ones that each handle one dialect (pg_query_go, TiDB parser, clickhouse-sql-parser). Table-level lineage makes do with reading table names through `internal/sqlrefs`; when switching to a parser, only the implementation of this package needs replacing, and it can be done one dialect at a time | When field-level lineage is needed, column-level permissions on hand-written SQL, strict blocking of write operations on the system side, or when reading table names misses too much for some dialect |
| JDBC bridge process | The first databases all have usable Go drivers | When data sources that have only a mature JDBC driver need support, such as Hive, Impala and Kerberos environments |
| Subscription and alert scheduling in the scheduler | For now it only enqueues export file cleanup and maintenance jobs, and cross-instance deduplication is implemented | When building timed exports, subscription delivery or alerts |
| Data connections to APIs / SaaS | Syncing and ETL fit better in a data integration system | According to actual need |
| Splitting into multiple services | The modular monolith can already scale horizontally over several pods | When the resource profile or release cadence of one role clearly differs from the others |
| A command that only checks the configuration without starting the service | The configuration is already fully validated at startup, see [Startup configuration](design/configuration.md) section 9 | When the configuration needs to be checked before pushing it to the configuration center or before a release |
| Reloading the configuration while running | The listen address, metadata database, storage and role cannot be switched while running, and reloading only a part is easy to misread; after changing the configuration, restart the process. Settings with one value for the whole organization are already stored in the metadata database and take effect at once when changed, see [Startup configuration](design/configuration.md) section 10 | When a setting appears that needs frequent adjustment and is inconvenient to restart for |
| Listing the running instances in System administration | Export storage, S3, the query cache and Redis must be the same on every instance, which still relies on a shared config file; when they differ, downloads fail or the cache cannot be shared, but nothing is computed wrongly. Each instance would have to write its role, version and these settings into the metadata database on a schedule, see [Startup configuration](design/configuration.md) 10.6 | When there are so many instances that the config file cannot keep them in line, or a download has failed because the configuration differed |
| Replacing the secret-key | At startup the secret keys of the instances are already checked to be the same ([Startup configuration](design/configuration.md) section 11); replacing it means decrypting all values with the old key and encrypting them again with the new one, and the instances must stop in the meantime. If the secret key is lost, clear the values with `supabi clear-secrets` and fill them in again | When the secret key may have leaked and needs rotating, or when there is a compliance requirement for regular rotation |
