# 暂缓事项

设计讨论中明确决定「现在不做、以后要做或要重新评估」的事项。每项记录暂缓的原因和重新评估的时机，避免遗忘。

## 当前实现的缺口

已经做出来的功能里，明确知道还缺的部分。与下面「暂缓」的区别是：这些不是决定不做，而是还没做到。

| 缺口 | 影响 |
|---|---|
| 账号功能还缺的部分 | 没有找回密码（忘记密码只能由管理员重置）；账号只能停用不能删除；没有邮件邀请 |
| 会话所在的工作空间被收回权限后不会自动切走 | 用户会看到无权限提示，需要手动切换到别的工作空间 |
| 审计还缺的部分 | 只有系统管理员能看，空间管理员没有只看本空间的视图；外发只能靠收集应用日志，没有推送到 syslog 或 webhook；审计与业务修改不在同一个事务里，写审计失败时修改照常生效，事件只留在应用日志中；导出任务重试三次仍中断时直接标为失败，没有「导出完成」事件。见 [权限设计](design/access-control.zh.md) 第 7 节 |
| 数据权限模拟预览只显示前 100 行 | 尚不支持翻页或导出模拟结果 |
| StarRocks 和 Doris 只在一个版本上测试过 | 测试用的是 StarRocks 单机镜像的最新版和 Doris 2.1.0；`make test` 默认不跑它们，需要 `make test-olap` |
| Trino 只在两个版本上测试过 | `make test-olap` 跑 Trino 483；最低支持的 418 只在 2026-10-21 手动跑过一遍。测试用的是 `memory` catalog，Hive、Iceberg 等连接器的类型和元数据没有测过 |
| 数据库之间的差异没有全部抹平 | 文本大小写、数值表示等，见 [架构总览](design/architecture.zh.md) 9.1 节 |
| 工作台一次只能打开一个资源 | 没有多标签页，靠搜索面板里的最近打开来回切换；是否需要多标签，等实际使用后再定 |
| 数据探索运行历史只在浏览器里 | 预览最多显示 1000 行；后台 CSV/XLSX 导出已支持，查询运行历史仍只保存在浏览器里，最近 50 条 |
| 文件夹只用于整理 | 不参与权限；非空文件夹不能删除，需要先移走里面的内容 |
| 只列出当前 catalog 里的表 | StarRocks、Doris 有多个 catalog 时，库表结构只显示连接所在的那一个，因此树上没有 catalog 这一层。Trino 列出全部 catalog |
| SQL 编辑器的补全不认 catalog | 写 `catalog.` 后不提示其中的 schema 和表；Trino 上其他 catalog 的表要从库表结构树点表名插入全名 |
| 显示格式只有基本项 | 没有负数加括号（按条件上色见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.8 的条件格式）；日期只有横线、斜线、中文三种写法，不能按界面语言写（如 `Jan 5, 2026`）、自定义写法、省略年份，也不能写星期几、12 小时制或相对时间（3 天前）；用表达式截断的日期不带粒度，按日写。见 [数据集模型](design/dataset.zh.md) 5.5 节。图表编辑器里不能给动态位置设格式和条件格式，只能通过接口。字段的格式也用在明细行上：按合计选的单位（如「万」）放到单行上，可能显示成 `¥0.03万` |
| 表级血缘靠读 SQL 里的表名，不是解析 | 只认 `FROM` 和 `JOIN` 后面的名字（跳过注释、字符串和 `WITH` 里自己起的名字）。通过函数读到的表（ClickHouse 的 `remote(...)`、PostgreSQL 的 `dblink(...)` 等）找不到，这时数据集仍直接连到数据源；视图不展开。血缘每次查看时现算，不落库 |
| 血缘图上的表按 SQL 里的写法区分 | `orders` 和 `public.orders` 是两个节点，大小写不同也是；合并需要去数据库查默认 schema，血缘就得依赖数据源在线 |
| 没有字段级血缘 | 只知道读了哪张表，不知道读了哪些列；需要真正的 SQL 解析器 |
| 图表编辑器的构建器能力有限 | 筛选器之间只能是「并且」；动态位置不能设置排序；通过接口创建的含查询自带过滤条件或 `offset` 的图表在界面上只读 |
| 级联只限精确选择 | 只有明细层的 `in` 选择能做级联节点，日期、模糊匹配、聚合结果不行；全局级联的候选只查一个来源图表的数据集，不跨数据集联查，见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.5 节 |
| 图表联动的扩展 | 已支持柱状图、条形图、饼图和表格的静态字段单选、跨数据集映射及日期区间；多选、动态维度来源、更多图表类型暂未支持 |
| 更细粒度的保存冲突合并 | 数据集、图表和仪表盘均已强制版本校验，支持三方比较并应用为草稿；数据集字段的显示名、描述、格式和隐藏状态已支持逐属性合并。数据源、SQL、参数仍成组，字段类型与公式等定义变化时整字段选择；图表配置、仪表盘布局与筛选联动尚不做内部自动合并 |
| 图表样式还缺的部分 | 数据标签之间不做避让；颜色只能按指标指定，不能按维度取值指定；组合图的标签可能与柱子顶端的标签重叠。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.8 节 |
| 桑基图还缺的部分 | 节点高度是连线相加，流量是去重计数等不可加的指标时会偏大；后面各层没有按来源着色；合并为「其他」的连线是相加所得 |
| 透视表和合计还缺的部分 | 图表有按结果筛选的条件（`having`）时不显示合计；列很多时没有虚拟滚动，一次画出全部单元格；合计和小计每项多发一次查询（带小计最多 16 次），没有用 `GROUPING SETS` / `ROLLUP` 合并；维度多到超过 16 项时不能显示小计；小计不能折叠，也不能只要行或只要列的小计 |
| 仪表盘上每个图表各发一次查询 | 相同的查询会合并、结果会缓存、每个数据源有并发上限（[查询 IR](design/query-ir.zh.md) 第 6 节），但不同图表的查询不会合成一条 SQL |
| 交互查询没有异步执行 | 数据探索预览和图表查询仍在请求里同步执行，最长到查询超时（默认 60 秒）；完整 CSV/XLSX 导出已使用后台任务 |
| 查询缓存没有管理界面和指标 | 看不到命中率、占用和条目，不能手动清空；只有每条语句一行的日志。Redis 时可以直接在 Redis 里看 |
| 后台任务目前只用于导出和清理 | 已实现 Postgres 队列、租约恢复、取消、CSV/XLSX 生成、文件保留、仪表盘图表数据导出和统一的导出中心，以及每小时清理过期会话和审计事件的维护任务；导出文件可以放在数据目录或 S3 兼容的对象存储；定时导出、订阅、邮件推送尚未实现，见 [导出设计](design/exports.zh.md) |

## 权限

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 按文件夹授权仪表盘，对数据集、数据源授权 | 第一版只对单个仪表盘授权，概念最少 | 仪表盘多到逐个授权吃力，或需要限制数据开发能用哪些数据源时 |
| 数据脱敏 | 要让字段的每一处使用都换成脱敏后的表达式，否则能用筛选试探出真值，见 [权限与工作空间模型](design/access-control.zh.md) 5.5 | 有手机号、身份证号等需要部分展示的字段时 |
| SQL 系统变量 | 行级规则已能引用工作空间用户属性；SQL 中的 `{{user.email}}` 等系统变量尚未实现 | 权限关系由数仓里的映射表维护，需要在 SQL 中关联当前用户时 |
| 在系统管理里直接管理其他空间 | 成员、用户属性等接口都按会话的当前空间，「管理」要先切换当前空间 | 系统管理员经常要同时照看多个空间时 |
| 看一个人在哪些空间、一个组被哪些空间授权 | 要新接口；现在只能逐个进入空间核对 | 空间多到逐个核对吃力时 |
| 用户属性页只列本空间能访问的人 | 成员列表只有空间管理员能读，数据开发也能看属性页，见 [权限与工作空间模型](design/access-control.zh.md) 2.2.1 | 组织里的用户多到属性表难以浏览时 |

## 导出

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 工作空间级的导出限制 | 导出限制在「系统管理 → 通用设置」里，全组织一个值，见 [启动配置](design/configuration.zh.md) 第 10 节 | 某个工作空间需要比系统更严的限制时，在工作空间设置中加只能调低的值 |
| 图表编辑器中的导出 | 数据开发可以在数据探索中导出，首版只在仪表盘上导出 | 作者常需要在编辑时取完整数据时 |
| 导出合计与小计、透视表按交叉表导出 | 合计是额外的查询；交叉表的列随数据变化，写 XLSX 要先确定列 | 用户需要直接拿到与屏幕一致的透视结构时 |
| 导出时套用显示格式 | 原始值便于在 Excel 中继续计算；XLSX 的数字格式与图表格式需要逐项对应 | 用户需要导出即报表、不再加工时 |
| 导出时带上表头分组 | 导出只写一行列名；XLSX 要写多行表头和合并单元格，CSV 写不出来。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.7 | 用户需要导出的表头与屏幕一致时 |

## 邮件

SMTP 设置、测试邮件和发信的函数已实现；还没有功能发邮件。见 [邮件](design/email.zh.md) 第 10 节。

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 队列、重试和发送记录 | 信怎么发、怎么重试，取决于发的是什么、谁在等它 | 第一个发邮件的功能 |
| 附件、HTML 模板和共用的版式 | 还没有设计任何一封信；附件只有订阅和定时导出要用 | 第一个发邮件的功能，以及做订阅时 |
| Microsoft 365 和 Gmail 的 OAuth 2.0 登录（`XOAUTH2`） | 要在供应商那里注册应用，还要在后台刷新令牌 | 组织的邮件服务不再接受密码时 |
| 跳过证书校验 | 网络上任何人都能借此读到密码；可以把内部 CA 加进信任证书 | 部署环境改不了信任证书时 |
| 每个工作区不同的发件人 | 还没有东西从工作区发出 | 工作区要用自己的名义发订阅时 |
| 服务端知道每个人的界面语言 | 界面把选择存在浏览器里，`users.locale` 没有用上；测试邮件用发送它的页面的语言 | 第一个给别人发邮件的功能 |

## 公告

系统公告、空间公告、横幅和铃铛已实现。见 [公告和通知](design/announcements.zh.md) 第 9 节。

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 用邮件发送公告 | 它会成为第一个发邮件的功能，要先定队列、重试和每个人的语言 | 大家因为不打开 SupaBI 而错过公告时 |
| 只发给某些用户组或角色 | 空间已经区分了受众 | 一个空间里有需要不同消息的受众时 |
| 在登录页显示系统公告 | 那样公告就成了不登录也能读的数据 | 需要通知登录不了的人停机维护时 |
| 谁读过某条公告 | 没有人提出 | 管理员需要知道谁看过时 |
| 分级和颜色 | 目前决定不做 | 普通公告淹没了紧急公告时 |

## 图表

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 表格每列单独选择是否合并相同值 | 一个开关已能覆盖常见的用法：每列只在左边各列相同的范围里合并，最后一个维度通常不会合并。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.8 | 需要只合并部分维度列时，如合并大区、但每行都写出城市 |
| 合并后的格子在滚动时一直显示值 | 值写在格子顶部，格子比可见区域还高时，往下滚就看不到；透视表的行维度也是这样 | 合并后的格子常常高过一屏时 |
| 冻结前几列 | 冻结首列只固定一列；第一列在表头分组里时，分组那一格随表格横向滚走。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.7 | 需要固定左侧几列或整个分组时 |
| 只合计表格显示的行 | 合计由数据库对全部数据算；只合计取回的前 N 组要给合计的 SQL 加上「属于这些组」的条件，各数据库匹配空值的写法不同，占比列的合计口径也要另定。目前只在合计行写明「合计（全部数据）」。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.1 | 需要「前 N 名合计」这类数字时 |
| 在数据库里分页 | 表格的分页只翻已经取回的行，最多到返回行数上限（默认 10000 行）。每页查一次要另查总行数、排序必须稳定、缓存按页算，导出和合并相同值也要重新考虑。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.7 | 需要在仪表盘上翻看超过一万行的明细时 |
| 透视表分页 | 透视表有分组和小计，一组被分到两页时，组名和小计怎么显示要另定 | 透视表行很多、需要分页查看时 |
| 条件格式的色阶和数据条 | 先只做按规则上色。色阶和数据条要另定最小、最大值取自哪些行（前端只有取回的行；分页时是全部取回的行还是当前页）、负数的数据条往哪边画、透视表的小计是否参与。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.8 | 作者常要一眼看出一列数的大小，而不是挑出过了门槛的数时 |
| 条件格式与另一列比较 | 规则只和固定的数比。和同一行的另一列比（实际低于目标）要那一列也在结果里，透视表要按同一个格子的另一个度量取值，被比较的列隐藏或从图表上拿掉时规则怎么办也要另定 | 常见「实际 vs 目标」的表格时 |
| 条件格式的文字颜色、整行上色 | 只给满足条件的那一格上浅底色。文字颜色在黄色等浅色上看不清，要另配一档深色，暗色模式也要另定；整行上色要规定几列的规则同时满足时用谁的颜色 | 用户坚持「负数红字」的写法，或者要把整行标出来时 |
| 指标卡和文本列的条件格式 | 指标卡已能与另一个指标对比，带 ▲▼；文本列按值上色（「状态 = 逾期」）要另做文本的条件 | 有按门槛给指标卡上色、或按状态给格子上色的需求时 |
| 把字段拖到别的栏 | 每栏接受的字段不同（指标不能当维度，筛选器要先设置条件），换栏还要决定原来的计算、别名和格式怎么处理；先只做同一栏里的排序。透视表的行和列之间用字段菜单移动。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.1 | 作者常要把字段从一栏换到另一栏时，先考虑透视表的行和列之间 |
| 下钻后在下一层继续联动，或下钻时同时筛选别的图表 | 下钻只改这张图，要筛选别的图表用联动；联动按第一层的字段映射目标，下钻到下一层后这一列换了字段，所以下钻列只在第一层能联动。要在各层联动，得给每一层分别映射目标图表的字段，等于每层一条联动。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.10 | 查看者下钻后常常还要再去联动别的图表时 |
| 下钻到明细（查看构成一个值的原始行） | 明细会露出图表上没有的列，而普通用户现在只能执行图表保存的查询（[图表与仪表盘](design/chart-dashboard.zh.md) 3.5），要另定哪些列能看 | 查看者常要追查一个汇总数由哪些记录组成时 |
| 更多图表的下钻、透视表的展开和折叠 | 第一版只做点一个类目就能确定下一层的图表。散点图的点、热力图的格子、带分组的矩形树图各对应两个维度，桑基图的节点分在不同的层，漏斗图的层有先后；透视表的展开是在原处多出一层，不是换掉这一层 | 有具体需求时，先考虑透视表的展开和折叠 |
| 点中一个值后临时选维度往下看 | 查看者要从数据集的字段里选，而普通用户读不到数据集，也只能执行图表保存的查询 | 有探索式分析的需求时，先考虑由作者给出几个可选的维度，像动态维度那样 |
| 参数下拉选项的显示名 | 选项直接显示值本身。显示名要在每个选项里多存一项，分享的摘要、导出和查询诊断里写值还是写显示名也要另定。见 [图表与仪表盘](design/chart-dashboard.zh.md) 2.11 | 参数的值是编码（如 `APP`）、查看者看不懂时 |

## 仪表盘

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 打印和完整渲染（全部图表立即取数、就绪信号） | 2026-10-20 试做过打印样式，在 Chrome 里按 ⌘P 时图表右侧仍被截断或留白，已撤回。Chrome 的打印对话框不缩小过宽的页面，而 headless 的 printToPDF 会缩小，所以脚本验证复现不了；网格按屏幕宽度用像素定位，打印时不会重排。见 [图表与仪表盘](design/chart-dashboard.zh.md) 3.11 | 需要打印或导出 PDF，或者做服务端截图、订阅推送时 |
| 查看、比较和恢复图表和仪表盘的旧版本 | 图表的结果还取决于它读的数据集，仪表盘还取决于它引用的图表；单独退回一个旧版本，上游已经变了，得不到当时的样子，结果也不可控。只记录修订和当时的定义，见 [图表与仪表盘](design/chart-dashboard.zh.md) 4.1 | 经常需要直接查库追查旧定义时，先考虑只读查看 |
| 图表和仪表盘修订的保留上限 | 每次保存都存完整定义，全部保留，概念最少 | 修订表大到影响备份或查询时，按资源只留最近若干个版本的定义，列表照常完整 |
| 多个查询容器（在仪表盘的页里另放查询容器） | 全局筛选按页显示已经能让只属于一页的筛选器只在那一页出现；多个容器要另行规定各自「查询」按钮和重置的范围、查询方式和控件样式按容器还是按仪表盘、级联能否跨容器、图表换页后原容器里的筛选器怎么办。见 [图表与仪表盘](design/chart-dashboard.zh.md) 3.13 | 作者需要把只属于一页的筛选器放在这一页的图表旁边时 |
| 全局筛选器关联数据集参数 | 第一版参数只能在各图表上改（[图表与仪表盘](design/chart-dashboard.zh.md) 2.11）。全局筛选器关联参数，要规定同一个筛选器在一张图上映射字段、在另一张图上映射参数时怎么对上：字段筛选有范围和各种操作符，参数只是一个值或一组值；下拉选项也要另定取自哪里 | 一个仪表盘上几张图用同一个参数（如同一天的快照），需要一处改全部时 |

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 个人令牌 | 大家用的 MCP 客户端都支持 OAuth，Claude 的连接器和 ChatGPT 只接受 OAuth；手动复制的令牌只有脚本用得上 | 做数据 API 时，或有脚本要以某个人的身份取数时 |

| Client ID Metadata Documents | 服务端要去互联网上取客户端的描述文件，部署在公司内网的往往做不到；而一旦声明支持，客户端就改用它、不再注册，然后失败。动态注册在 MCP 规范里标为弃用，但现在用的客户端都支持 | 有重要的客户端只支持 Client ID Metadata Documents 时，或规范取消动态注册时；到时只在服务端能访问互联网时才声明支持，比如由系统设置控制 |
| 在浏览器里运行的 MCP 客户端 | `Origin` 指向别的站点的请求会被拒绝，以防 DNS 重绑定；要支持就得允许跨域访问 `/mcp` 和令牌端点 | 需要在网页里运行的客户端时 |
| 管理员查看所有人的授权 | 授权和撤销都记在审计日志里，关掉总开关就全部停用 | 管理员需要看谁连了哪个客户端，或替某人撤销时 |
| `list_dashboards` 的空间参数 | 第一次列出这个人能访问的所有空间，对模型最简单 | 空间多的人列出来的内容撑满了客户端的上下文时 |

## 数据接入

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 支持 MySQL 5.7 | 2026-10-20 在官方 `mysql:5.7`（5.7.44）上实测：默认的加密方式连不上（它只接受 RSA 密钥交换，Go 1.27 把这类套件列为不安全、默认不提供）；关掉加密后，普通图表正常，占比、同环比的差值和增长率、`TO_FLOAT`、累计报 SQL 语法错误。要支持需要：建连接池时读版本并存进数据源记录（保存校验和编辑器都要用到，不能每次连库）；在不校验证书的加密模式里补上 RSA 密钥交换的 AES-GCM 套件；5.7 上把转浮点写成 `x + 0E0`、正则写成 `x REGEXP y`（实测只换这两处，除累计外的一致性测试全部通过）；方言声明不支持窗口函数，累计在编辑器里不可选；5.7.20 之前用 `tx_read_only`；单独的测试目标。目前只在测试连接时说明需要 8.0，见 [架构总览](design/architecture.zh.md) 9 | 确认有用户必须连 MySQL 5.7 时 |
| MariaDB | 版本号与 MySQL 不同，测试连接不按版本判断；11.1 之前没有 `transaction_read_only`，连不上；`REGEXP_LIKE` 也没有。未实测 | 有用户需要连 MariaDB 时 |
| Trino 的 Kerberos、JWT 和 OAuth2 登录 | 第一版只做用户名和密码，见 [架构总览](design/architecture.zh.md) 9.3。Kerberos 要在每台运行 SupaBI 的机器上放 keytab 和 krb5.conf；JWT 令牌会过期，要有人定期更新 | 有用户的 Trino 只开了这几种认证时 |
| PrestoDB | 与 Trino 分家后协议头不同，Trino 的 Go 驱动连不上 | 有用户需要连 PrestoDB 时 |
| 把文件或其他系统的数据写进用户的 OLAP 数据库（数据集成） | 早先的上传功能把文件转成只在内置 DuckDB 里的表，不能和用户数据库中已有的数据一起分析，2026-10-19 已移除（[架构总览](design/architecture.zh.md) 9.2）。数据应当写进用户自己的数据库，这需要按数据库实现建表、类型映射和批量写入，还要管理有写权限的账号，尚未设计 | 用户需要把 Excel、CSV 或其他系统的数据和已有数据一起分析时 |

## 数据集

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 草稿/发布两个状态 | 会让数据集和图表的每个接口都多出「读哪个版本」的问题 | 出现分析师需要长时间修改数据集且不能影响线上仪表盘的反馈时 |
| 参数替换表名、列名（如按月分表） | 无法用绑定参数实现，有注入风险 | 有分表场景的实际需求时；方案方向是带白名单的枚举型参数 |
| 数据集之间的关联（完整语义层） | 自动 join 的编译复杂，且易出现指标重复累加 | 分析师反馈需要维护的宽表数据集过多时 |
| 基于数据集建数据集 | 增加编译和权限的复杂度 | 同上 |
| 物化（结果落成表并定期刷新） | 属于性能优化，依赖 scheduler | 出现慢数据集且缓存无法解决时 |
| 在数据集里定义维度层级（省 → 市 → 区） | 下钻的层级配在图表里（[图表与仪表盘](design/chart-dashboard.zh.md) 2.10），不依赖数据集，数据集的修改不会让下游图表的下钻悄悄失效 | 多张图表反复配同一套层级时；数据集里的层级只作为编辑器里的预设，填进图表 |
| 选表来源指定 catalog | 界面上的数据集都由数据探索里的 SQL 生成，选表来源（`type: table`）只在接口里有，只能写 `schema` 和 `table`；在 Trino 上只能指向默认 catalog 里的表。见 [架构总览](design/architecture.zh.md) 9.3 | 界面上要做选表建数据集时 |

## 查询

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| 透视（列转行）下推到数据库 | 各数据库支持差异大，与 `limit` 交互复杂 | 前端透视在大结果集上出现性能问题时 |
| 排名、移动平均 | v1 先做同环比、占比和累计 | 查询 IR 的 `compute` 已预留类型，按需求逐个加 |
| 平均值、去重计数和数据集指标的累计 | 不能由各分组的值依次得出：平均值要另取和与个数；去重计数要改写成「每个值第一次出现在哪个分组」再计数累加，多一个子查询；数据集指标的表达式系统不解析，不知道能不能相加。累计先只做求和、计数、最小、最大，见 [查询 IR](design/query-ir.zh.md) 3.5 | 有「累计用户数」这类需求时先做去重计数；作者常把可加的数写成数据集指标、因而无法累计时，再考虑让作者标出指标可以累加 |
| 从筛选范围之前开始累计 | 要像同环比那样改写时间条件，只对时间维度有意义，而且每次都要读全部历史 | 需要在近期的时间范围里显示历史累计总量时 |
| 叠加的派生计算（累计占比、帕累托等） | 一个指标只有一种派生计算；叠加要先定计算的先后和合计的口径 | 有帕累托分析的需求时 |
| 补齐没有数据的分组 | 要按粒度生成连续的日期再关联，各数据库写法不同；不补时累计值仍然对，只是少了这一行 | 折线图上缺的点造成误读时 |
| 跨实例的查询合并与并发限额 | 缓存可以放在 Redis 里各实例共用，但合并相同查询和并发限制仍按实例：跨实例做需要分布式锁和共享计数 | 实例多到「实例数 × 每实例上限」压垮数据源，或同一查询在各实例重复执行明显时 |
| 数据集、图表级的缓存有效期 | 第一版只有服务端默认值和数据源级覆盖，概念最少 | 同一数据源下的数据集更新频率差别很大时 |
| 按用户的查询公平性、查询优先级 | 第一版并发限制只按数据源先到先得 | 一个人打开大仪表盘挤占别人，或定时任务（订阅、物化）开始和交互查询抢数据源时 |
| 自由表达式指标（图表级） | 表达式解析器和方言输出已经有了（[标准表达式](design/expressions.zh.md)），还差查询 IR 里的入口和图表编辑界面 | 有图表级临时指标的需求时 |

## 基础能力

| 事项 | 暂缓原因 | 何时重新评估 |
|---|---|---|
| SQL 解析器 | Go 生态缺少成熟的多方言解析器，只有各管一种方言的（pg_query_go、TiDB parser、clickhouse-sql-parser）。表级血缘用 `internal/sqlrefs` 读表名顶着，换成解析器时只需替换这个包的实现，可以一种方言一种方言地换 | 需要字段级血缘、对手写 SQL 做列级权限、系统侧严格拦截写操作，或某种方言读表名漏得多时 |

| API / SaaS 数据接入 | 同步与 ETL 更适合放在数据集成系统 | 按实际需求 |
| 拆分为多个服务 | 模块化单体已能多 pod 水平扩展 | 某个角色的资源特征或发布节奏明显不同于其他角色时 |
| 只检查配置、不启动服务的命令 | 启动时已经完整校验配置，见 [启动配置](design/configuration.zh.md) 第 9 节 | 需要在推送到配置中心或发布前预先检查配置时 |
| 运行中重新加载配置 | 监听地址、元数据库、存储和角色都不能在运行中切换，只重载一部分容易误解；改配置后重启进程。全组织一个值的设置已存进元数据库，改了立即生效，见 [启动配置](design/configuration.zh.md) 第 10 节 | 出现需要经常调整、又不便重启的配置项时 |
| 在系统管理里列出运行中的实例 | 导出存储、S3、查询缓存、Redis 各实例要一致，仍靠共用配置文件；不一致时下载失败或不能共用缓存，不会算错。要各实例定时把角色、版本和这些配置写进元数据库，见 [启动配置](design/configuration.zh.md) 10.6 | 实例多到靠配置文件管不住，或出现过因配置不一致而下载失败时 |
| 更换 secret-key | 启动时已核对各实例的密钥一致（[启动配置](design/configuration.zh.md) 第 11 节）；更换要用旧密钥解开、新密钥重新加密全部值，期间各实例要停下。密钥丢了用 `supabi clear-secrets` 清掉后重新填写 | 密钥可能泄露、需要轮换，或有定期轮换的合规要求时 |
